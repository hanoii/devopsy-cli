History, not rules: `internals/export-import.md` wins where they differ.

- The `volumes` tar takes only files, directories and links, hard links as files of their own and holes kept (review after v0.52.1): a FIFO in the data made an export its import refused, a hard link to a link or across entries did too, and a database's holes came back as zeros, the copy larger than its source.
- An owned entry an import extracted goes to its owner before the import counts as complete, in a container of its own (review of 2026-10-23, round 3): `--resolved` once started the services on the tar maker's owners.
- The whole tar is read with `archive/tar` to its end-of-archive blocks: `tar -t` took a tar cut at a member boundary for complete, and a check of the spool's last bytes passed the last member's own zeros (a sparse file, a database's pages).
- Members reaching out of their entry refused: GNU tar extracted them through to another entry, refused them only once the entries were emptied, or, with `../x` into `.` before `.` went, emptied the container's root.
- A symbolic link's target is the data's own (decided after v0.52.1): an app's absolute link, `storage/latest -> /app/storage/f`, made devopsy's own export refuse its import; the extraction mounts its entry alone, so nothing of the host is in its way.
- Links walked as the host resolves them (review of 2026-10-23, round 4): `path.Clean` read `storage/w -> x/x/../../etc/shadow`, with `storage/x -> .`, as `storage/etc/shadow`, and on the server it was `/etc/shadow`.
- One pax global header, first (review of 2026-10-24, checked in `devopsy-util:2`): `archive/tar` reports it as no member, but GNU tar applies its records to every member after it, so a `path` or `linkpath` record renamed members and retargeted links the checks never saw.
- Only files, directories and links as members (review of 2026-10-23, round 3): GNU tar as root made device nodes on the host, where bind mounts are not nodev, and the owners' step gave one to the entry's owner, a block device of the server's disk; FIFOs and the rest went with them, since a tar of data never needs them.
- Each entry extracted in a container of its own (decided, review of 2026-10-23, round 3): the service whose entry it is may run (`never` is the default stop), and its owner swapped a directory the extraction had just made for a link to `../<another entry>`, which GNU tar followed as root, planting files in another entry (demonstrated); the cost, the spool read once per entry, was accepted.
- The spool mounted into the container, never sent on its stdin (measured 2026-10-26): Docker's stream ran at 8 MB/s on a small DigitalOcean Droplet, a restore of 1 GiB taking 131 s against some 9 from a file. What tar leaves past its end blocks is drained because zstd's SIGPIPE failed the pipe on a tar of large records (review).
- A failure after the first write keeps the set down rather than restoring (decided, over restoring with or without a mark): drupal11's import drops the database first, so a cut dump restored served an empty site. The writer's own result decides from the byte on; a session lost during the load cancelling it was rejected.
- The `writer <pgid>` line before the hook runs (decided 2026-10-24): the line came after the start, its failure ignored, so a devopsy killed in between left a loader nobody recorded, which the next import ran beside; a loaded macOS CI runner hit it. A mark written only on failure was rejected: a devopsy killed or a server rebooted mid-load would leave none.
- The byte before the first write: once the end line came nothing read stdin, so a session lost between the spool and the first write was noticed only through SIGPIPE, asynchronously, and a session cut halfway reached the server as a plain EOF.
- The writer does not hold the release lock: after a SIGKILLed devopsy the orphaned load held the lock to its end, and every lock-taker waited 600 s and failed. An import's leftover writer is ended explicitly by the next lock-taker, unlike a fetch's children, which inherit the lock on purpose.
- Containers named after devopsy's pid (review of 2026-10-23, round 3): `docker run` refused the name a killed devopsy's container still held, hence `dockerRunFresh`.
- One service at a time under an import's mark: two partial services would need a rule for every combination, and an import's mark over a sync's would lift the guard off its partial copy; a sync clears an import's mark only by copying that service, since with any one entry a sync completed over a half-written entry the parent lacks and cleared the mark.
- A marked environment's release refuses in `UploadScript` before `LockedMarker`: one more session per release was rejected, at the accepted cost that the release's local `before` steps run first.
- `--resolved` is for targets only (decided): locally nothing tells a failed import's stops from deliberate ones. Rejected names: `--accept`, `--force` (`mariadb --force`), `--continue`, `--fake`, `--clear`, `--repair`.
- Prompts ask for the target's full name, never the service: the prompt's text names the service, and one word serves every destructive prompt.
- The restore's compose calls in their own process group: a terminal's Ctrl-C reached the whole foreground group and left the larger sets down without a word.
- The export's images as a pax global header (checked 2026-10-24): GNU tar and bsdtar skip it, so a tar made by devopsy stays one any tar extracts.
- `--resolved` keeps the history when its window starts with an `import` line written since the mark (review of 2026-10-24): an import whose data completed and held its service but failed after left both, and starting over forgot what wrote the data; a second round found that neither the hold nor the newest line tells, since every release holds its data service and an export's window ends with its own lines, so it checks the line's time against the mark's.
- The hold only in the service's own repository (decided 2026-10-24): the header is whoever made the tar's, so an image from another repository is a name the data never ran; `localHold`'s fallback to the record's repository once pulled and ran a reference of the service's repository with another repository's digest (review of 2026-10-24). The taken-over history ends on a line in that repository (review of snapshots, round 4: a record whose image line or last history line named another repository made it the data's newest image, which a rollback then pulled and ran) and keeps every line, by identity (round 5: dropped, a mirror's tag gone back ran an older image on the data). Its first line is timed at the import so `--resolved` keeps it: the export's time, when its environment first ran the image, came before any mark here.
- `imagesShared` takes the image lock in two short windows, never across the load, so a removal elsewhere waits only for them. `ImportScript` passed the record, the lock and the mode as `img` got them (review of 2026-10-24): without the record, the names the take-over gave up leaked. Since 2026-11-02 the server's devopsy finds them itself (`serverImages`).
- `export-images` is a named feature: an older server would export without the record and import unchecked.
