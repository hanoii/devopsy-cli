# Syncs

`cmd/devopsy/sync.go`, `cmd/devopsy/writers.go`, `cmd/devopsy/clone.go` (shared with snapshots), `internal/remote/sync.go` (the scripts), `internal/images/sync.go` (the data images); the labels are in `internals/data-labels.md`, inherited variables in `internals/inherit.md`.

## Parents and when

- `parent:` names a concrete environment: a pattern is an error, an environment naming itself has none (so `defaults: {parent: prod}` works), and a cycle is an error, since neither could be released first.
- A parent resolves one level only, at the child's instance, its server from the usual variables and never from the child's (`ParentTarget`, whose own parent stays nil): a guess would copy the wrong data.
- An unresolvable parent is recorded (`ParentErr`) rather than failing the load, so every other command works on the child; only `--sync` and a `--release` that syncs fail with it (`failParent` lists the fixes), and `DescribeTarget` resolves it leniently.
- A sync runs on a child's first release, on `--release-sync`, never on `--release-no-sync`, and on `@<child> --sync`, which asks for the name as `--destroy` does and reruns the deployed release's run step (`--release-steps release run`), never the checkout's.
- Every release of a child opens one extra session (`CurrentExistsScript`: `current` or `none`, then `incomplete` on a partial copy).
- `--from <address>` (`@` optional) on `--release`, `--release-sync` and `--sync` copies from that address instead of `ParentTarget`, `ParentErr` ignored: a child's only, on `--release` only a first one, and `--release-no-sync --from` is an error.
- Everything that can fail is checked before the upload or the holder (`syncPreflight`): a run step, the parent released, and across servers a local agent with keys (`agentHasKeys`; `SSH_AUTH_SOCK` set is no agent) and a child reachable without `ProxyCommand` or `ProxyJump`.
- The child's side stops its set before it knows what the parent copies, so with nothing to copy its `import` services are down for seconds: knowing first costs a session per sync, accepted.

## Sessions and the decision

- A sync is two sessions, both from the operator (`runSyncSession`): the holder on the child's server (`HolderScript`, or `ActivateScript` with `SyncOptions` between `make_current` and the run step) takes the release lock, runs prepare and prints the marker (`SyncMarker`, with `$base` and the sync's id, taken out by a `LineMarker`); then the push on the parent's (`PushScript`, `devopsy --sync-push`, shared on its release lock and exclusive on `SyncLockFile`, so syncs from one parent serialize), with `ForwardAgent=yes` across servers.
- The push's exit gives `go` or `abort` to the holder; the holder's exit is the command's, and a push that failed after a complete copy (the parent's services not back) fails it too.
- Both ssh processes ignore SIGINT (`remote.WithoutInterrupt`), so devopsy alone ends them, in order: a terminal's Ctrl-C reaches the whole foreground group, and a `-T` ssh quits on it.
- The holder opens a gate before its marker (`SyncOpenFile`, named by the sync's id, which the push passes on as `SyncIDEnv`) and removes it right before deciding; the child's side of the push claims it right before its first write (`claimWrite`, `ClaimWriteScript`: a rename to `SyncStartedFile`, which one of the two wins), so a push that outlived its connection writes nothing once the holder decided.
- The claimed file is the sync's record of its writers: each import appends a `WriterLine` before it writes, the last write appends a `DoneLine` with the sync's id, both on the child and never creating the file (`recordWrite`).
- Across servers the receive script removes its rsync container once the holder decided (a watchdog on `SyncStartedFile`): after a silent cut between the servers the rsync would wait for TCP to give up, and rsync's `--timeout` only counts its own keepalives.
- The decision (`syncBlock`) takes the record in one move (`mv` to `SyncTakenFile`), so a writer appending after it finds no file and stops: a done line of its own sync is `go` (an `abort` after it too), a record taken without one is `partial`, nothing taken on a marked environment is `partial`, else the answer; the taken record goes once finish is done.
- `finish partial` starts again only what this sync stopped itself (`restoreOwnStops`, the record's `own <sync id> <name>` lines), never another sync's, so what was down before stays down.
- No write outlives its sync (`endWriters`): before a partial copy is marked or settled, the recorded imports' devopsy gets SIGTERM (only a pid `/proc` still shows as `--sync-services import` in the child's directory, `isSyncImport`, Linux only), the sync's own containers (`SyncContainerPrefix` and its id, never another sync's) are removed, the imported services are stopped, since nothing else ends what `docker exec` started in them, and recorded when they ran before, their one-off containers removed, then the imports are waited for (`writersWait`) and killed.
- A partial copy keeps everything off the data: `finish partial` leaves what the child's side stopped down (the record's `stop` lines) and writes `SyncIncompleteFile`; `finish go` removes it; a failing `finish child go` writes it, since a sync completes only once its finish accepts the copy.
- While the mark is there `partialGuard` refuses a release that does not sync and a rollback, the restart after a failed release is skipped, `CurrentExistsScript` says `incomplete` so the operator refuses before uploading (`--release-no-sync` included), a push from it refuses, `--export` warns and `--status` shows it; only what the child's side stopped is kept off partial data.
- The mark says why (`remote.IncompleteLine`: since, parent, code, why, tab separated on one line, which shell reads with `cut`): `copy` (cut), `write` (another sync's push wrote after its holder decided), `settled` (a holder killed before deciding), `finish` (a complete copy the project's `finish child go` refused); a later mark keeps the first one's time and says its own why, and the refusals and `--status` print it.
- A holder killed before deciding is settled by the next lock-taker (`--sync-services settle`, run by the next sync's prepare and by `partialGuard`): it takes the record as the holder would, ends what it names, marks the data as not completed (keeping a mark the holder wrote), runs `finish child partial` and removes what syncs left (`syncLeftovers`: streams' spools, stale pending inherited variables); a sync's files while nothing holds the lock (`LockBusy`) are leftovers, a running sync's are not.
- The answer comes on fd 3, never stdin: the holder reads it from a fifo the watcher writes (`--answer-fd`, both ends opened before the watcher starts, so no open waits) and gives every command `/dev/null` as stdin, so nothing it runs can eat or wait on the answer.
- Without an answer (devopsy interrupted, the connection lost) the holder writes to `$base/.devopsy-sync.log` (trimmed past `SyncLogMax` bytes to its last `SyncLogKeep` lines, on both sides) and finishes as the files say: a write to the dead session would kill what restores the services. From prepare until the services are restored it ignores SIGPIPE, and it restores before it reports.
- An interrupt stops the push first, then lets the holder decide (SIGINT, SIGTERM in `runSyncSession`): before the marker devopsy writes `abort`, closes the holder's stdin and waits, saying so after 5 seconds, a second interrupt ending the session (`endHolder`); after the marker the push's ssh gets SIGTERM (`remote.SSHContext`, SIGKILL after `SSHKillDelay`) and is waited for, then the holder gets `abort` and finishes as the files say, exit 130, or 0 when the copy had completed. After `go`, during the run step, the first Ctrl-C only says the step goes on and a second cuts the session.
- A holder ending first (its connection dropped) has restored the child on its way out, so the push is cancelled the same way and the sync fails.
- The push watches its session: its stdin is a pipe devopsy keeps open (`SyncWatchEnv`, `watchSession`), so `--sync-push` sees the session's end (EOF, or the heartbeat's silence) at once, not at its next write, which a silent copy may not make for minutes.
- A session gone, SIGINT, SIGTERM, SIGHUP or SIGPIPE cancels the push: the same-server rsync container is removed (`dockerRun`; killing the docker client leaves the container copying), the `-R` session ends, a running export (its own process group, `runDataHook`) and import get SIGTERM, spools go, no export starts, and the parent's services are restored; from then on `errOut` also appends to the parent's `$base/.devopsy-sync.log` (`quietWriter.keep`). What runs inside a container on its own (an import in `docker exec`) runs to its end.
- A server's command writes to `errOut`, never an `*os.File`: a gone session cannot kill it with a broken pipe.
- In the tests the fake ssh runs through dash on Linux, which never execs the last command of `sh -c`, so cancelling closes the pipe as sshd would, rather than signalling ssh.

## The child guard

- Each side reads its own labels, and the parent checks the child's before changing anything: `--sync-push` asks the child for `--sync-services list` (through `--sync-exec`, one more session across servers) and refuses (`syncConflicts`) when a child service mounting a copied entry is running or restarting and not copied as `volumes` there, and (`streamMismatches`) when a parent `custom` service is not `custom` on the child, whose import would refuse it after the rsync, or a child `custom` service is `volumes` on the parent; a stop word differing between the sides is named (`stopMismatches`).
- The list (`runSyncServices`) has per service its name, `<copy>+<stop word>` (`none` without data too), state, entries, owners (`<entry>=<uid>:<gid>`, `listOwners`), volumes and reflink, tab separated, then `!import\t<service>` for an import's mark (`listMark`) and a `!restore` line per service of a restore's (`listRestore`); it refuses two owners on one entry. Only a devopsy with `data-copy` and `mnt-owner` reads it, from a child checked for both (`childNeeds`, `internals/releases.md`).
- A label from an inherited variable cannot lag, since the child reads the pending file (`internals/inherit.md`); one in the child's own `shared/.env` can still differ between the sides.

## Order and state

- The child's side (`--sync-services prepare`): `settle`, the state record, an import's leftover writer ended (`endLeftoverImport`, when its mark is there: a sync never streams into a database still loading), the import check, the `prepare child` hook, then one `compose stop` of its set (`cli.DataStops`, `SyncChild`), kept one call so Compose orders them by `depends_on`, dependents first; `finish go|abort` starts them and waits until healthy, `partial` leaves them down, every spool left goes, then `finish child` runs with the word. Stopped services stay down through the imports.
- The parent's side (`runSyncPush`): the checks (labels, the child's import mark, the `export` script of every `custom` service, the child guard, the util image) before anything, then `prepare parent`, stop, rsync, streams, start (healthy) and `finish parent go|abort`; a failing prepare aborts before its side stops anything, and on the same server a child gate gone already (its holder decided) refuses.
- Hooks run from Go (`runDataHook`, `--capability data ...` in its own process group), only where their file is, with that side's label lists and the operation's set in their environment (`cli.DataLists`, `dataHookEnv`: `DEVOPSY_DATA_STOP` from labels at prepare, export, import and `finish ... go|abort`, from the record at `finish child partial` and `settle`) and the sync's addresses and arguments (README); the holder's scripts (`syncPrepare`, `syncFinish`) only call `--sync-services`.
- A hook runs in the foreground: what it leaves running in its group ends when it returns, said; what it starts outside its group (`setsid`, `docker exec -d`) is its own.
- The state record exists before anything can fail, stopping recording what it stops in `$base/.devopsy-sync.services` (`syncState`, `stop <name>` lines), the child's prepare creating it before its hook and `stopServices` before its first `ps` (`startSyncState`): no record means restore the side's whole set, one down on purpose included.
- A record left by an earlier sync or import that could not restore is kept and added to (`syncRecord`, rewritten whole, `writer <pgid>` lines kept), and what a sync stops itself is marked `own <sync id>`.
- Restoring brings back only the recorded services, whatever their labels say now, from container state (exited), so a service down before the sync stays down and an interrupted sync is recovered the same way; it waits for every service it started to be running and healthy (`waitHealthy`, one gone fails) and removes the record once all are back.
- Service states come from one `docker compose ps --format json` (`serviceStates`, `servicesIn`), one-off containers left out (`serviceEntries`): a hook's `run --rm` still running would read as its service running, which then never started again. The sync tests' fake docker remembers stops and starts to answer it.
- What a killed operation left stopped starts with the next settle (`settleStops`): the record's `stop` lines with no mark (a push killed outright on the parent, an export on a target, an import before its mark, a release between its switch and its run step), only those the current release has, their `own` lines going with them, one whose container runs another image than the current release gives it made again (`startStops`, `images.Recreate`); a mark keeps them down, a start that fails only warns and keeps them, and `--status` names them while nothing holds the locks (`left`).
- Every settle's caller holds the release lock and runs it before it stops anything, so such a line is a leftover, except a killed sync holder's (its claimed or taken record there, which the settle makes its mark), in a data hook (`HeldStopsEnv`, set by `runDataHook`) and in the activation that made them (`HeldStopsEnv`, exported past `release-record live`): started there, a database ran on a half copy, or under the new code on the old data.
- A server's devopsy killed by a signal in an import, a restore's data step or a take's stopped pass says nothing of it, so its script, still holding the locks, says the mark and its ways out after the first write (`killedSays`), else settles at once and says nothing was written.
- A child's first release gets its data services and its side's set before its finish hook: a release with nothing current before it (`prepare first`), or no container at all when prepare started, is a `first` line in the record, and on go, before the hook, those services (the ones with data and the child side's set by labels, not in a profile that is not up, `SyncService.Active`) are created in one `up -d --wait`, since `up` creates dependencies but never dependents and the hook sanitizes through them.
- An aborted first sync creates nothing, and no later sync creates a missing service: it was removed on purpose.

## The data images

- The child takes the parent's pulled data services' images with its data (`img data`, `sync-check`, `sync-done`): the parent's images (their containers', else the history's last) and history are read in the preflight session (`ParentCheckScript`, `images.Set.ParentData`, its `image` and `ran` lines passed through by `remote.ParseParentData`), passed to the child's side (`images.SyncImagesEnv`) and their checksum to the push (`SyncImagesSumEnv`), which refuses before stopping anything when the parent's changed since.
- `ParentData` holds only `devopsy.data.copy=volumes` services as the parent's config resolves them now, counting one with a named volume as copied, and leaves out a service whose entries are all missing on the parent, so the child keeps its own data and image; it sends at most `ParentHistoryLines` history lines in all, 10 at least per service, since they ride in the child's script as one argument.
- The holder checks before its prepare, and a release that syncs at its record, in place of its own check for those services: the parent's image or name passes; one the child's data moved past, or a name it never ran, needs `--accept-image` on every sync (`imagesAccept`), and then the child runs its own image on the copy, its history one `forced` line (`SyncDone`). The child's image checked, and the one its history's last line names, is what its own name holds on its server (`ownImage`), never the parent's it is held on.
- The parent's image is pulled by digest when missing, held in the child's own repository when its server has it there (`localHold`), and listed at once as a `sync:<service>` entry of the child's release (bookmarked, removed with it); a check or a restore that fails removes what it pulled. The holder checks and pulls while its watcher is still armed, so an abort or a session gone during a long pull stops nothing.
- On a complete copy, whatever the answer, `sync-done` holds the child on the parent's image and replaces its history with the parent's window (first line `sync <parent>`), adding a line naming the image as the child does only when the child ran that very image; failing, the child is marked (`finish`) and stays down. Only `volumes` copies take the parent's image: a `custom` one goes through the child's own.
- Only `finish go` makes services again on the parent's image: `restoreServices` recreates (`up --no-deps --wait`) a service whose container's `devopsy.digest` label differs from the release's `ComposeFile` (`images.Recreate`) before starting the rest, since `compose start` would run the old image on the new data; an abort in a release that syncs restores the child's own data, which the release's never-live images must not touch.
- Holds and labels are spelled as Docker shows digests (`repoKey`), so holding the same image never changes the reference compose sees; a pull refused for having no build for the server's platform (`otherPlatform`) says so with its platform, naming `--accept-image`; a signal during `img names` stops the fetch before it pulls; the parent's images are unset with the sync's variables before the run step.

## Streams

- Per `custom` service, in `depends_on` order over every service (`SyncCustomServices`: dependencies first, ties alphabetical, a cycle an error), the parent runs the capability's `export <service>` (`exportStream`) into the child's spool, `$base/.devopsy-sync.stream.<service>.<sync id>` (`remote.StreamSpool`, one per sync, so an export that outlived its push never writes into the next sync's), on the same server directly and across servers through `cat >` in a session to the child (`exportInto`).
- Only once every export exited 0 do the parent's services start again and the child's `--sync-services import <service>` run, in the same order (`importStream`), never a pipe into the import: a cut export never reaches it, and the parent is down for its exports only, never through the child's loads.
- The import brings the service up (`upFor`, `--no-deps` except on a first release, where Compose would otherwise start a dependency the sync stopped) unless the child's side stopped it, runs `import <service>` with the spool as stdin, takes the service down again if it was down, and removes the spool whatever happens; its stdin is a pipe the push keeps open, so across servers the session's end cancels it too.
- Every file a sync leaves in `$base` starts with `.devopsy-sync.`.

## The copy

- rsync always runs in `UtilImage` (`devopsy-util:3`, built on each host from `UtilDockerfile`, which also holds GNU tar, find, chown and zstd for the other copies) as root with `--numeric-ids`, so owners and modes survive and the deploy user's permissions do not matter; never devices, FIFOs or sockets (`--no-D`): as root rsync made them on the child's host, where bind mounts are not nodev.
- Times are compared to the nanosecond (`RsyncCopy`, `--modify-window=-1`): to the second, rsync skipped files of the same size that both sides wrote in the same second, and the child's database opened its old tablespaces under the parent's dictionary.
- An entry the child's labels own gets `--chown=<uid>:<gid>` from the child's list (`syncRsync`, the receive script's options): the child's owner for every file written, whatever the parent's are.
- `UtilImage`'s tag is bumped whenever `UtilDockerfile` changes: a new tag is built at its first use on each host, where the old one is rebuilt only once a week old.
- The util image floats on `alpine:3` and is rebuilt weekly (`ensureUtilImage` before every use, through the hidden `--util-image`; past `UtilImageMaxAge`, `build --pull --no-cache`, the replaced image removed without `-f`): it runs as root on the data and serves rsync across servers, so patches must reach it. A rebuild that fails warns and goes on with the image there, since a registry out of reach must never stop a sync, an import or `--destroy`; a missing one that fails to build fails. One implementation, in Go, never in a script.
- Entries are the top-level entries of `mnt` that `volumes` services bind-mount (`docker compose --profile '*' config`, lexical and resolved paths): one missing on the parent is skipped with a notice, the child's left as it is; one that is a file on the parent is copied as one, `--inplace`, so the container bind-mounting it sees the new content (a bind mount is the file's inode).
- A named volume is copied in a util container mounting both by name on the same server, and through the daemon's module of its key (`/vol/<key>`) and the receive script's `copyvol` across; a missing child volume fails a copy before its claim, nothing written, and the child's prepare makes them first (`ensureVolumes`).
- Across servers the parent's daemon serves only what is copied, one module per entry (`rsyncdConf`) and per volume, named with the sync's id and labeled with the parent's `mnt`, so the next push from the parent, holding its sync lock, removes one an earlier push left.
- rsync's exit 24 (files vanished during the copy) is a notice (`RsyncVanished`); any other failure aborts.
- Where the parent's data clones by reflinks, the stop lasts the clone (`syncClone`, the helpers in `clone.go`): once `stopServices` stopped a `volumes` service with data, its data is cloned into `$base/.devopsy-sync.clone.<sync id>`, the set started, and the rsync copies from the clone (`dataSet.in`), which goes after, on a cancel too; the reflink check and the room's `du` run before the stop (`cloneCheck`), and a cancel during the check stops nothing.
- With a clone the streams run before the start when the set holds a `custom` service or one stopped `always`, so its files and the dump are of one moment, and after it otherwise, told nothing is stopped (`DEVOPSY_DATA_STOP` empty); the rsync is then the last write.
- The clone's containers are `<SyncContainerPrefix>parent-<id>-...` (`cloneContainer`), never the sync's own prefix, which the child's holder removes as writers into the child, and never under `snapshots/.clone`, which a take's leftovers step removes; one a killed devopsy left goes with the next holder of the sync lock (`removeLeftoverClones`, its containers by `sourceLabel`) and with `--destroy-data`, and an `--export` of a `volumes` service on a target clones the same way (`export.<pid>`).
- `devopsy.data.copy.reflink=true` on the child's service (`DataCopyReflinkLabel`, `childShares` from the list) clones its entries and volumes from the parent's, or the clone, into the child's on one server (`shareInto`): the entry emptied, never removed, `cp -a --reflink=always`, then `ownMnt` for owned ones; file entries and syncs across servers always rsync, and no named feature gates it, since one devopsy does both sides on one server.
- Before a share empties anything (`shareable`): an entry that is a link on either side is rsynced, since Docker would mount its target alone, which the clone empties as root; a missing one is made (`makeEntry`); the script tries one file at the real destination (`shareScript`, exit 4), and the first that will not clone has the rest rsynced, said once; a source holding a device node, FIFO or socket is rsynced (exit 3), one made meanwhile deleted after the clone; the clone runs twice when the first fails, as `cloneData` does, and one that fails falls back to the rsync, which replaces what it left; mounts go by `--mount` (`shareMount`), so any entry name works.

## SSH and environment

- The child's sessions from the parent never get the operator's agent (`ChildSSH`, through `DEVOPSY_SSH_COMMAND` too): `ForwardAgent=no` whatever the parent's ssh config says, `BatchMode=yes` (a refused key fails instead of prompting), `ConnectTimeout=30` (an unreachable child fails before the TCP timeout, the parent's services stopped meanwhile) and `StrictHostKeyChecking=accept-new`; the parent can use every key in the operator's agent for its session (README).
- The rsync session keeps its forwarding: `-R` to the parent's daemon, `--network host` on the child, `ExitOnForwardFailure=yes` and never `ClearAllForwardings`, which clears command-line forwardings too; a taken port retries another (3 tries, 20000-60000); `--sync-exec`'s session and a stream's `cat` keep `ClearAllForwardings`.
- All of a sync's sessions pass `KeepAlive`: the holder is quiet for the whole copy.
- A refusal says what it means: no agent on the parent with `DEVOPSY_SYNC_TO` set means a `restrict`ed key or sshd's `AllowAgentForwarding no`; a `restrict`ed key also refuses the `-R`, which sshd reports like a taken port, so after the last try both are said.
- The child's devopsy never sees the parent's environment: on the same server `--sync-exec` runs it with `cleanEnv` (`cleanEnvKeys`: the machine's variables, the sync's own, Docker's and devopsy's settings, the child's `COMPOSE_PROJECT_NAME`), since the caller's environment wins over a project's `.env`; across servers `SyncExecScript` exports the sync's own (`syncExecEnv`) into the clean login environment.
- The hidden flags, dispatched in `main.go` before anything else: `--sync-push [reset]`, `--sync-exec <devopsy args>` (both need the push's `DEVOPSY_SYNC_TO_DIR` and `DEVOPSY_SYNC_TO_PROJECT`) and `--sync-services prepare [first] | finish go|abort|partial | settle | import <service> [last] | list | wipe` (`runSyncServices`).
- A sync takes no rsync arguments: it copies environments whole, and what must never be copied is a label (`devopsy.data.exclude`).

## --reset

- `devopsy @<child> --reset` is a sync that starts the child over (`runSync` with reset): everything a sync checks, the same two sessions, the push given `--sync-push reset` and passing `SyncResetEnv` on to the child's devopsy; every refusal on a marked child names it (`remote.ResetFix`) as the way out of data nothing else fixes.
- The wipe is the copy's first write, at whichever claim comes first (the same-server rsync's, through `--sync-exec --sync-services wipe`; the receive script's `wipe`; a stream's import, before its `upFor`), never in prepare: a push that refuses or never reaches the child leaves it as it was, and once claimed the partial rules hold.
- `--sync-services wipe` (`wipeData`) removes an import's leftover containers, runs `compose --profile '*' down --volumes --remove-orphans` (no `--rmi`: the release's images stay), empties `mnt` (`emptyMnt`, shared with `--destroy-data`, in a container named `<SyncContainerPrefix><id>-wipe` so a holder deciding meanwhile removes it), makes the volumes again and sets the record to `first` with nothing stopped, so `finish go` creates the services with data and the child's set and the run step the rest; the child's `shared/.env` and release stay.
- The wipe's `down` takes every container, a holding service too, so the child answers nothing until its run step is done: accepted.
- A reset skips the child guard, since nothing of the child runs under the copy, and the import mark's `copiesService`, since it replaces everything; the stream mismatches stay. It refuses on a parent with no data (that would only empty the child, which `--destroy` does), on one whose labeled entries are all missing there with no stream (nothing would claim and wipe), and without a parent (`syncPreflight`).
- `reset` is a named feature, found by `--sync-push reset` and `--sync-services wipe`: an older parent would sync without wiping.
