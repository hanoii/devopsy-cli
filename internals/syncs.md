# Syncs

`cmd/devopsy/sync.go`, `cmd/devopsy/record.go` (the record and the mark), `cmd/devopsy/services.go` (stops, starts, compose calls), `cmd/devopsy/writers.go`, `cmd/devopsy/clone.go` (shared with snapshots), `internal/remote/sync.go` (the scripts), `internal/images/sync.go` (the data images); the labels are in `internals/data-labels.md`, inherited variables in `internals/inherit.md`.

## Parents and when

- `parent:` and its resolution (`ParentTarget`, `ParentErr`) are internals/config.md's; only `--sync` and a `--release` that syncs fail on a parent that cannot be resolved (`failParent` lists the fixes).
- A sync runs on a child's first release, on `--release-sync`, never on `--release-no-sync`, and on `@<child> --sync`, which asks for the name as `--destroy` does and reruns the deployed release's run step (`--release-steps release run`), never the checkout's.
- Every release of a child opens one extra session (`CurrentExistsScript`: `current` or `none`, then `incomplete` on a partial copy).
- `--from <address>` (`@` optional) on `--release`, `--release-sync` and `--sync` copies from that address instead of `ParentTarget`, `ParentErr` ignored: a child's only, on `--release` only a first one, and `--release-no-sync --from` is an error.
- Everything that can fail is checked before the upload or the holder (`syncPreflight`): a run step, the parent released, across servers a child reachable without `ProxyCommand` or `ProxyJump`, and on a release (whose child check read them) both sides of one kind and the child's host keys readable; on `--sync` the holder checks those before its prepare.
- Two addresses are one server (`job.sameHost`) when `ssh -G` resolves them alike (`sameHost`), or when they resolve to one user and the parent's check writes a marker of random content (`SameMachineMark`, in `/dev/shm`, memory, so never in a home another server shares) that a session to the child's address reads back the same (`sameMachine`): a machine that never saw it cannot answer with it, and a child wrongly taken for the parent's server would choose where the parent's server writes. The same-environment refusal comes after it.
- On one server the push goes only into the child's own directory under its release root (`syncToOwn`), whatever its holder named, and removes the marker (`SameMachineClear`); markers over an hour old go at the next check.
- Both sides of a sync are project users, or both deploy users (`KindsDiffer`, `syncKinds`, the parent's kind from `ParentCheckScript`, the child's from its own `id -nG`): a door parent's data would drive a deploy user's child, and a door child would talk to a deploy user's push and rsync daemon. A deploy-user parent and a project-user child on one machine are not `sameHost` (the user differs), so they take the across-servers path and its check, with no exception for one server.

## Sessions and the decision

- A sync is two sessions, both from the operator (`runSyncSession`): the holder on the child's server (`HolderScript`, or `ActivateScript` with `SyncOptions` between `make_current` and the run step) takes the release lock, runs prepare and prints the marker (`SyncMarker`, with `$base` and the sync's id, taken out by a `LineMarker`); then the push on the parent's (`PushScript`, `devopsy --sync-push`, shared on its release lock and exclusive on `SyncLockFile`, so syncs from one parent serialize), across servers with the sync's key (below), never the operator's agent.
- The push's exit gives `go` or `abort` to the holder; the holder's exit is the command's, and a push that failed after a complete copy (the parent's services not back) fails it too.
- Both ssh processes ignore SIGINT (`remote.WithoutInterrupt`), so devopsy alone ends them, in order: a terminal's Ctrl-C reaches the whole foreground group, and a `-T` ssh quits on it.
- The holder opens a gate before its marker (`SyncOpenFile`, named by the sync's id, which the push passes on as `SyncIDEnv`) and removes it right before deciding; the child's side of the push claims it right before its first write (`claimWrite`, `ClaimWriteScript`, a rename to `SyncStartedFile`, which one of the two wins: the same-server rsync, `SyncClaimScript` across servers, a stream's import in `syncImport`), so a push that outlived its connection writes nothing once the holder decided.
- The claimed file is the sync's record of its writers (`recordWrite`, on the child, never through another session and never creating the file, the receive script checking its first line first): each import appends a `WriterLine` (the service, its devopsy's pid, the service's state before) before it writes, and the last write appends a `DoneLine` with the sync's id, the rsync's when no stream follows, else the last import's (`import <service> last`).
- Across servers the receive script removes its rsync container once the holder decided (a watchdog on `SyncStartedFile`): after a silent cut between the servers the rsync would wait for TCP to give up, and rsync's `--timeout` only counts its own keepalives.
- The decision (`syncBlock`) comes once the holder's read of the answer ends, however it ends, and takes the record in one move (`mv` to `SyncTakenFile`), so a writer appending after it finds no file and stops: a done line of its own sync is `go` (an `abort` after it too), a record taken without one is `partial`, nothing taken on a marked environment is `partial`, else the answer; the taken record goes once finish is done.
- A sync that wrote nothing (no record taken) keeps the mark as it was and starts again only what it stopped itself (`restoreOwnStops`, the record's `own <sync id> <name>` lines, none when its prepare failed before stopping), never another sync's, so what was down before stays down.
- No write outlives its sync (`endWriters`), run before a partial copy is marked or settled:
  - the recorded imports' devopsy gets SIGTERM, only a pid `/proc` still shows as `--sync-services import` in the child's directory (`isSyncImport`, Linux only);
  - the sync's own containers (task `sync-<id>`, never another sync's, internals/data.md) are removed;
  - the imported services are stopped, since nothing else ends what `docker exec` started in them, and recorded when they ran before, their one-off containers removed;
  - then the imports are waited for (`writersWait`) and killed.
- A stop is recorded before it runs (`stopSet`, `stopServices`, `stopRecording`): a stop can fail partway with some services down, and what the record leaves out no completing copy starts again.
- A partial copy keeps everything off the data: `finish partial` leaves what the child's side stopped down (the record's `stop` lines) and writes `SyncIncompleteFile`; `finish go` removes it; a failing `finish child go` writes it, since a sync completes only once its finish accepts the copy.
- While the mark is there `partialGuard` refuses a release that does not sync and a rollback, the restart after a failed release is skipped, `CurrentExistsScript` says `incomplete` so the operator refuses before uploading (`--release-no-sync` included, a sync being the fix, `--release-sync` when the sync itself needs a code fix), a push from it refuses, `--export` warns and `--status` shows it; only what the child's side stopped is kept off partial data.
- The mark says why (`remote.IncompleteLine`, since, parent, code and why, tab separated on one line, which shell reads with `cut`): `copy` (cut), `write` (another sync's push wrote after its holder decided), `settled` (a holder killed before deciding), `finish` (a complete copy the project's `finish child go` refused); a later mark keeps the first one's time and says its own why, and the refusals and `--status` print it.
- A holder killed before deciding is settled by the next lock-taker (`--sync-services settle`, run by the next sync's prepare and by `partialGuard`): it takes the record as the holder would, ends what it names, marks the data as not completed (keeping a mark the holder wrote), runs `finish child partial` and removes what syncs left (`syncLeftovers`, streams' spools and stale pending inherited variables); a sync's files while nothing holds the lock (`LockBusy`) are leftovers, a running sync's are not.
- The answer comes on fd 3, never stdin: the holder reads it from a fifo the watcher writes (`--answer-fd`, both ends opened before the watcher starts, so no open waits) and gives every command `/dev/null` as stdin, so nothing it runs can eat or wait on the answer.
- Without an answer (devopsy interrupted, the connection lost) the holder writes to `$base/.devopsy-sync.log` (trimmed to its last `SyncLogLines` lines, on both sides) and finishes as the files say: a write to the dead session would kill what restores the services.
- From prepare until the services are restored the holder ignores SIGPIPE, and it restores before it reports.
- An interrupt stops the push first, then lets the holder decide (SIGINT, SIGTERM in `runSyncSession`).
- Before the marker devopsy writes `abort`, closes the holder's stdin and waits, saying so after 5 seconds, a second interrupt ending the session (`endHolder`): the watcher, armed during the lock wait or before a release's switch, ends the holder; past that the holder reads the abort after its prepare and restores in the session, so the operator sees how it ends.
- After the marker the push's ssh gets SIGTERM (`remote.SSHContext`, SIGKILL after `SSHKillDelay`) and is waited for, then the holder gets `abort` and finishes as the files say, exit 130, or 0 when the copy had completed.
- After `go`, during the run step, the first Ctrl-C only says the step goes on and a second cuts the session.
- A holder ending first (its connection dropped) has restored the child on its way out, so the push is cancelled the same way and the sync fails.
- The push watches its session: its stdin is a pipe devopsy keeps open (`SyncWatchEnv`, `watchSession`), so `--sync-push` sees the session's end (EOF, or the heartbeat's silence) at once, not at its next write, which a silent copy may not make for minutes.
- A session gone, SIGINT, SIGTERM, SIGHUP or SIGPIPE cancels the push: the same-server rsync container is removed (`dockerRun`; killing the docker client leaves the container copying), the `-R` session ends, a running export (its own process group, `runDataHook`) and import get SIGTERM, spools go, no export starts, and the parent's services are restored; from then on `errOut` also appends to the parent's `$base/.devopsy-sync.log` (`quietWriter.keep`).
- What runs inside a container on its own (an import in `docker exec`) runs to its end.
- A server's command writes to `errOut`, never an `*os.File`: a gone session cannot kill it with a broken pipe.
- In the tests the fake ssh runs through dash on Linux, which never execs the last command of `sh -c`, so cancelling closes the pipe as sshd would, rather than signalling ssh.

## The child guard

- Each side reads its own labels, and the parent checks the child's before changing anything: `--sync-push` asks the child for `--sync-services list` (through `--sync-exec`, one more session across servers) and refuses (`syncConflicts`) when a child service mounting a copied entry is running or restarting and not copied as `volumes` there, and (`streamMismatches`) when a parent `custom` service is not `custom` on the child, whose import would refuse it after the rsync, or a child `custom` service is `volumes` on the parent; a stop word differing between the sides is named (`stopMismatches`).
- The list (`runSyncServices`) has per service its name, `<copy>+<stop word>` (`none` without data too), state, entries, owners (`<entry>=<uid>:<gid>`, `listOwners`), volumes and reflink, tab separated, then `!import\t<service>` for an import's mark (`listMark`) and a `!restore` line per service of a restore's (`listRestore`); it refuses two owners on one entry.
- Only a devopsy with `data-copy` and `mnt-owner` reads the list, from a child whose holder needs `sync-key`, newer than both (internals/releases.md).
- A label from an inherited variable cannot lag, since the child reads the pending file (`internals/inherit.md`); one in the child's own `shared/.env` can still differ between the sides.

## Order and state

- The child's side (`--sync-services prepare`): `settle`, the state record, an import's leftover writer ended (`endLeftoverImport`, when its mark is there, since a sync never streams into a database still loading), the import check, the `prepare child` hook, then one `compose stop` of its set (`cli.DataStops`, `SyncChild`), kept one call so Compose orders them by `depends_on`, dependents first.
- `finish go|abort` starts them and waits until healthy, `partial` leaves them down, every spool left goes, then `finish child` runs with the word; stopped services stay down through the imports.
- The child's side stops its set before it knows what the parent copies, so with nothing to copy its `import` services are down for seconds; knowing first costs a session per sync, accepted.
- A copy has one plan for both paths, from the parent's labels and the child's list, made before anything stops: an entry or a volume the child's labels do not name is skipped and said (`childNamed`), and an entry the child has as another kind (`listKinds`, the list's eighth field) refuses unless a reset wipes it (`kindMismatch`), a link, or an empty directory for a file, only across servers (on one server the rsync mounts the child's mnt whole, a link there is its data on another disk, and an empty directory is what a first release made for an entry it did not know is a file, which the rsync replaces): on one server the copy wrote what the child mounts nowhere, and across servers the receive refused it past the stop, the entries before it written.
- The parent's side (`runSyncPush`): the checks (`pushChecks`: labels, the child's import mark, the `export` script of every `custom` service, the child guard, the util image) before anything, then `prepare parent`, stop, rsync, streams, start (healthy, in `copyOrder`'s order) and `finish parent go|abort`; a failing prepare aborts before its side stops anything, and on the same server a child gate gone already (its holder decided) refuses.
- Hooks run from Go (`runDataHook`, `--capability data ...` in its own process group), only where their file is, with that side's label lists and the operation's set in their environment (`cli.DataLists`, `dataHookEnv`: `DEVOPSY_DATA_STOP` from labels at prepare, export, import and `finish ... go|abort`, from the record at `finish child partial` and `settle`) and the sync's addresses and arguments (`docs/capabilities.md`); the holder's scripts (`syncPrepare`, `syncFinish`) only call `--sync-services` (`childPrepare`, `childFinish`).
- A hook runs in the foreground: what it leaves running in its group ends when it returns, said; what it starts outside its group (`setsid`, `docker exec -d`) is its own.
- The state record exists before anything can fail, stopping recording what it stops in `$base/.devopsy-sync.services` (`syncState`, `stop <name>` lines), the child's prepare creating it before its hook and `stopServices` before its first `ps` (`startSyncState`): no record means restore the side's whole set, one down on purpose included, for a sync, and nothing for an import or `--resolved`, whose mark and record are written together.
- A record left by an earlier sync or import that could not restore is kept and added to (`syncRecord`, rewritten whole, `writer <pgid>` lines kept) under a mark, and unmarked the settle first starts it (`settleStops`); what a sync stops itself is marked `own <sync id>`.
- Restoring brings back only the recorded services, whatever their labels say now, from container state (exited), so a service down before the sync stays down and an interrupted sync is recovered the same way; it waits for every service it started to be running and healthy (`waitHealthy`, one gone fails) and removes the record once all are back.
- Service states come from one `docker compose ps --format json` (`serviceStates`, `servicesIn`), one-off containers left out (`serviceEntries`): a hook's `run --rm` still running would read as its service running, which then never started again.
- The sync tests' fake docker remembers stops and starts to answer it.
- What a killed operation left stopped starts with the next settle (`settleStops`): a take's `snapshot` lines (internals/snapshots.md) and the record's `stop` lines with no mark (a push killed outright on the parent, an export on a target, an import before its mark, a release between its switch and its run step), only those the current release has, their `own` lines going with them, one whose container runs another image than the current release gives it made again (`startStops`, `images.Recreate`).
- A mark keeps them down; a `stop` line that fails to start only warns and stays, a `snapshot` line that fails to start fails the settle; `--status` names them while nothing holds the locks (`left`).
- Every settle's caller holds the release lock (a push and an export on a target shared, with the sync lock) and runs it before it stops anything, so such a line is a leftover, except a killed sync holder's (its claimed or taken record there, which the settle makes its mark), in a data hook (`HeldStopsEnv`, set by `runDataHook`) and in the activation that made them (`HeldStopsEnv`, exported past `release-record live`): started there, a database would run on a half copy, or under the new code on the old data.
- A server's devopsy killed by a signal in an import, a restore's data step or a take's stopped pass says nothing of it, so its script, still holding the locks, says the mark and its ways out after the first write (`killedSays`), else settles at once and says nothing was written.
- A child's first release gets its data services and its side's set before its finish hook, created in one `up -d --wait` on go: `up` creates dependencies but never dependents, and the hook sanitizes through them.
- A first release is a `first` line in the record, written with nothing current before it (`prepare first`) or no container at all when prepare started; a later sync that finds containers drops it.
- The services created are the ones with data and the child side's set by labels, without the running filter (an unlabeled app following its `own` database, an `import` app without data), but none in a profile that is not up (`SyncService.Active`, `COMPOSE_PROFILES`): an `up` naming a service starts it whatever its profiles.
- An aborted first sync creates nothing, and no later sync creates a missing service: it was removed on purpose.

## The data versions

- A sync is a landing (`SyncLanding`, internals/images.md): the parent's windows are read in the preflight session (`img data`, `ParentCheckScript`, `images.Set.ParentData`, `remote.ParseParentData`), passed to the child's side (`images.SyncImagesEnv`) and their checksum to the push (`SyncImagesSumEnv`), which refuses before stopping anything when the parent's changed since.
- `ParentData` holds what the copy writes (`Set.Copied`), `devopsy.data.copy=volumes` services with something there, and sends at most `ParentHistoryLines` history lines in all, 10 at least per service, cut by `compact` to what the rule reads: they ride in the child's script as one argument.
- A `custom` copy carries nothing, and the child's window and hold stay as they were: a dump is loaded by the image that runs.
- The holder checks before its prepare (`img sync-check`), while its watcher is still armed, and a release that syncs at `img check`, before it builds anything; a refusal needs `--accept-image` on every sync (`imagesAccept`), which runs the child's own image on the copy, its history one `forced` line.
- A reset's check runs whatever the parent sends, and as a reset (`resetOr`, `resetExport`): its wipe lands on every data service.
- The child always runs its own image on the copy; on a complete copy, whatever the answer, `sync-done` takes the parent's window over (first line `sync <parent>`), and failing, the child is marked (`finish`) and stays down, the reason on stdout for the holder's words and the mark's.
- Only `finish go` makes services again: `restoreServices` recreates (`up --no-deps --wait`) a service whose container's `devopsy.digest` label differs from the release's `ComposeFile` (`images.Recreate`) before starting the rest, since `compose start` would run the old image on the new data; an abort in a release that syncs restores the child's own data, which the release's never-live images must not touch.
- Holds and labels are spelled as Docker shows digests (`repoKey`), so holding the same image never changes the reference compose sees.
- The parent's windows are unset with the sync's variables before the run step.

## Streams

- Per `custom` service, in `depends_on` order over every service (`SyncCustomServices`: dependencies first, ties alphabetical, a cycle an error), the parent runs the capability's `export <service>` (`exportStream`) into the child's spool, `$base/.devopsy-sync.stream.<service>.<sync id>` (`remote.StreamSpool`, one per sync, so an export that outlived its push never writes into the next sync's), on the same server directly and across servers through `cat >` in a session to the child (`exportInto`).
- Only once every export exited 0 do the parent's services start again and the child's `--sync-services import <service>` run, in the same order (`importStream`), never a pipe into the import: a cut export never reaches it, and the parent is down for its exports only, never through the child's loads.
- Every spool is on the child's disk at once; accepted.
- The import brings the service up (`upFor`) unless the child's side stopped it, runs `import <service>` with the spool as stdin and removes the spool whatever happens; its stdin is a pipe the push keeps open, so across servers the session's end cancels it too.
- The `up` is `--no-deps` unless a first release stopped nothing: a dependency the sync stopped stays down through the imports.
- On a first release a stream's service imported stays up, unless its profile is not up; otherwise one down before the sync goes down again after.
- Every file a sync leaves in `$base` starts with `.devopsy-sync.`.

## The copy

- rsync always runs in `UtilImage` (internals/data.md) as root with `--numeric-ids`, never devices, FIFOs or sockets (`--no-D`): as root rsync makes them on the child's host, where bind mounts are not nodev.
- Times are compared to the nanosecond (`RsyncCopy`, `--modify-window=-1`): to the second, rsync skips a file of the same size both sides wrote in the same second, and a child's database then opens its old tablespaces under the parent's dictionary.
- An entry the child's labels own gets `--chown=<uid>:<gid>` from the child's list (`syncRsync`, `planReceive`): the child's owner for every file written, whatever the parent's are.
- Entries are the top-level entries of `mnt` that `volumes` services bind-mount (`docker compose --profile '*' config`, lexical and resolved paths): one missing on the parent is skipped with a notice, the child's left as it is; one that is a file on the parent is copied as one, `--inplace`, so the container bind-mounting it sees the new content (a bind mount is the file's inode), its module across servers `/mnt` filtered to it.
- A named volume is copied in a util container mounting both by name on the same server, and through the daemon's module of its key (`/vol/<key>`) across, the volume alone mounted in the receive; a missing child volume fails a copy before its claim, nothing written, and the child's prepare makes them first (`ensureVolumes`).
- Across servers the parent's daemon serves only what is copied, one module per entry (`rsyncdConf`) and per volume: nothing else under `mnt` can be asked for.
- The receive goes over SSH sessions alone, one per entry and volume (`receiveSession`): the session's stdout into the daemon's `docker exec -i` (`door.DaemonServe`, rsync's daemon over a pipe) and the daemon's stdout into the session's stdin, through pipes nothing of devopsy's writes to; at the child's end `--sync-child`'s receive (`receiveOne`) runs rsync as the daemon's client over its own stdin and stdout (`remote.ReceiveShim`). No port listens on either server, which a root rsync on the host's network would reach for anyone, so the daemon has no password, and neither container a network.
- The receive mounts the one entry or volume it writes (`planReceive`): a whole `mnt` would let the parent's daemon replace an entry with a link, which the child's next start binds. An entry's kind is the child's where it has the entry, the parent's word only for one it has not yet, and a mismatch refuses, unless a reset's claim wipes the entry first: the parent never turns the child's directory into a file. A missing entry is made as the import makes one (`readyEntry`).
- The daemon's settings are written last, and a listing of its modules proves them there before the first session.
- The daemon is named with the sync's id and labeled with the parent's `mnt`, so the next push from the parent, holding its sync lock, removes one an earlier push left.
- rsync's exit 24 (files vanished during the copy) is a notice (`RsyncVanished`); any other failure aborts.
- Where the parent's data clones by reflinks, the stop lasts the clone (`syncClone`, the helpers in `clone.go`): once `stopServices` stopped a `volumes` service with data (only a stop the labels ask for, so nothing stopped means nothing cloned), its data is cloned into `$base/.devopsy-sync.clone.<sync id>`, the set started, and the rsync copies from the clone (`dataSet.in`), which goes after, on a cancel too; the reflink check and the room's `du` run before the stop (`cloneCheck`), and a cancel during the check stops nothing.
- The parent's pages written while the clone exists fragment its files on XFS, and the fragments stay after the clone goes (`xfs_fsr` undoes it); accepted.
- With a clone the streams run before the start when the set holds a `custom` service or one stopped `always`, so its files and the dump are of one moment, and after it otherwise, told nothing is stopped (`DEVOPSY_DATA_STOP` empty); the rsync is then the last write.
- The clone's containers are the parent's `source` task (`cloneContainer`), never the sync's own task, which the child's holder removes as writers into the child, and the clone is never under `snapshots/.clone`, which a take's leftovers step removes; one a killed devopsy left goes with the next holder of the sync lock (`removeLeftoverClones`, its containers by their `source` task, as the daemon's) and with `--destroy-data`, and an `--export` of a `volumes` service on a target clones the same way (`export.<pid>`).
- `devopsy.data.copy.reflink=true` on the child's service (`DataCopyReflinkLabel`, `childShares` from the list) clones its entries and volumes from the parent's, or the clone, into the child's on one server (`shareInto`): the entry emptied, never removed, `cp -a --reflink=always`, then `ownMnt` for owned ones; file entries and syncs across servers always rsync, and no named feature gates it, since one devopsy does both sides on one server.
- Before a share empties anything (`shareable`):
  - an entry that is a link on either side is rsynced, since Docker would mount its target alone, which the clone empties as root;
  - a missing entry is made (`makeEntry`);
  - the script tries one file at the real destination (`shareScript`, exit 4), and the first that will not clone has the rest rsynced, said once;
  - a source holding a device node, FIFO or socket is rsynced (exit 3), and one made meanwhile is deleted after the clone;
  - the clone runs twice when the first fails, as `cloneData` does, and one that fails falls back to the rsync, which replaces what it left;
  - mounts go by `--mount` (`shareMount`), so any entry name works.

## SSH and environment

- Across servers the parent reaches the child with a key made for that sync, never the operator's agent: the operator's devopsy makes the pair in memory (`remote.NewSyncKey`, OpenSSH's format written by hand); the holder, once prepared, authorizes the public half (`devopsy --sync-key add`, the same command whatever its user: the deploy user's own `authorized_keys` under the `--ssh-keys` lock, a project user's through the door into its sync keys, `remote.DoorSyncKeysFile`) and removes it once it decided; the push gets the private half first on its stdin, before the beats (`takeSyncKey`, read a byte at a time), never in its script, which every user sees in `ps`.
- A sync key's line is built in one place (`remote.SyncKeyLine`), its options never from a request: `restrict`, with no forward of any kind (a forward works with no command run, so with no sync open, `ssh -N`, and a remote one plants a unix socket where its user writes), an `expiry-time` in UTC two days on (it only bounds a key nothing removed: a sync's streams log in late), and `command=` devopsy's absolute path as `--sync-child <id> <base> <to> [reset]`; the id, the path and the address are checked by one rule (`remote.CheckSyncChild`) wherever the line is built or read, since a quote or a comma would add options.
- A sync key does nothing its user cannot already: a sync's gate is in the user's tree, so for the door it is no boundary; the door checks the forms, writes its own options and expiry, one key per sync, an environment in the caller's tree. A leaked project key could add one, so removing any of that user's keys drops its sync keys too (internals/door.md). An add sweeps the expired lines and those of an earlier sync into the same environment, a dead holder's; that holder's gate goes with whatever takes the lock next (`settleNeeded`, `childSettle`), so its key answers nothing meanwhile.
- `--sync-child` refuses unless that sync is open in that environment (`syncOpen`: its gate, or the record the first write renamed it to, still naming that sync), reads one request from `SSH_ORIGINAL_COMMAND` (`syncRequest`, JSON, unknown fields refused, never a shell), and builds the script itself from the child's facts (`syncChildScript`): `--sync-services list`, `wipe` only on a reset, `import <service>` of a custom service, `--util-image`, the receive of one entry or volume the child's labels name, run in Go (`receiveOne`), a stream's spool under the name the child computes.
- The child's sessions from the parent (`ChildSSH`) go with the sync's key alone (`-i`, `IdentitiesOnly=yes`), `ForwardAgent=no`, `BatchMode=yes` (a refused key fails instead of prompting), the child's host key checked against what its holder read in `/etc/ssh` and sent with its marker (`HostKeyAlias=devopsy-sync-<id>`, a known hosts file of those, `StrictHostKeyChecking=yes`), and the connect timeout and keepalive every session has (internals/sessions.md), so an unreachable child fails before the TCP timeout, the parent's services stopped meanwhile.
- The child's devopsy never sees the parent's environment: on the same server `--sync-exec` runs it with `cleanEnv` (`cleanEnvKeys`, the machine's variables, the sync's own, Docker's and devopsy's settings, the operator's command, the child's `COMPOSE_PROJECT_NAME`), since the caller's environment wins over a project's `.env` and the parent's secrets and project name would reach the child's commands; across servers `--sync-child` exports the sync's own, from its own facts and the gate, into the forced command's clean environment.
- Both give the child's devopsy the child's address for its hints, the one the push has for it (`childAddress`, `SyncToTargetEnv`, across servers the key's own `<to>`), never the push's session's, which names the parent; the operator's command goes no further than the same server, a sync's request riding on the parent's ssh command line, every user's to read there.
- The hidden flags, dispatched in `main.go` before anything else: `--sync-push [reset] [key]`, `--sync-key add|remove`, `--sync-child <id> <base> <to> [reset]`, `--sync-exec <devopsy args>` (both need the push's `DEVOPSY_SYNC_TO_DIR` and `DEVOPSY_SYNC_TO_PROJECT`) and `--sync-services prepare [first] | finish go|abort|partial | settle | import <service> [last] | list | wipe` (`runSyncServices`).
- A sync takes no rsync arguments: it copies environments whole, and what must never be copied is a label (`devopsy.data.exclude`).

## --reset

- `devopsy @<child> --reset` is a sync that starts the child over (`runSync` with reset): everything a sync checks, the same two sessions, the push given `--sync-push reset` and passing `SyncResetEnv` on to the child's devopsy; every refusal on a marked child names it (`remote.ResetFix`) as the way out of data nothing else fixes.
- The wipe is the copy's first write, at whichever claim comes first (the same-server rsync's, through `--sync-exec --sync-services wipe`; the receive script's `wipe`; a stream's import in `syncImport`, after its writer line and before its `upFor`), never in prepare: a push that refuses or never reaches the child leaves it as it was, and once claimed the partial rules hold.
- `--sync-services wipe` (`wipeData`) removes an import's leftover containers, runs `compose -p <name> down --volumes --remove-orphans` with no `-f` (`composeDownProject`, no `--rmi`: the release's images stay), since with files compose leaves the networks and volumes only an older release named, empties `mnt` (`emptyMnt`, shared with `--destroy-data`, in a container of the sync's task, `sync-<id>`, so a holder deciding meanwhile removes it), makes the volumes again and sets the record to `first` with nothing stopped, so `finish go` creates the services with data and the child's set and the run step the rest; the child's `shared/.env` and release stay.
- The wipe's `down` takes every container, a holding service too, so the child answers nothing until its run step is done: accepted.
- A reset skips the child guard, since nothing of the child runs under the copy, and the import mark's `copiesService`, since it replaces everything; the stream mismatches stay.
- A reset refuses on a parent with no data (that would only empty the child, which `--destroy` does), on one whose labeled entries are all missing there with no stream (nothing would claim and wipe), and without a parent (`syncPreflight`).
- `reset` is a named feature, found by `--sync-push reset` and `--sync-services wipe`: an older parent would sync without wiping.
