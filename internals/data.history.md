History, not rules: `internals/data.md` wins where they differ.

- The owner label came because `shared/mnt` starts empty and the deploy user's, Docker makes a missing bind source root's, the deploy user cannot chown, and devopsy copies owners exactly: every template started as root for its mounts (an entrypoint's chown, an `init` service), and files from elsewhere (an import, a sync, an upload by hand) left a non-root app unable to write. Rejected: a shared group with setgid directories and default ACLs (tar and rsync set owner and mode explicitly, and a chmod sets the ACL mask), capability hooks (none runs after a `volumes` import, a plain `up` or an upload by hand), and a root `init` service in every template.
- Numbers only, 0 to 4294967294: names cannot be resolved from the host; past a `uid_t`'s 32 bits, or at 4294967295 (chown's -1), an owner passed the checks before the switch and failed in `find` and `chown` after it.
- Explicit, never from `user:` (decided): changing `user:` must not silently change the data's owner, and a default would need rules for names, root, images that drop privileges themselves and tools; a variable keeps the two alike.
- One container per owned entry (review of 2026-10-23, round 2): before, `-execdir` ran one chown per directory, so a directory the app swaps for a link during the scan could lead chown out of the entry; measured on 20,200 directories of 40,201 inodes in `devopsy-util:2`, container included, 15.3 s with `-execdir`, 0.34 s with one `find -exec ... +` per entry.
- Only files, directories and links (round 4 of the same review): a device node given to the entry's owner, a block device of the server's disk, was its raw disk for the app's UID.
- A failing scan looked at again (round 2): a directory find could not read passed silently. `-ignore_readdir_race` on both looks (review of 2026-10-23): a file a service removed after find saw it failed the release after its switch; rsync's exit 24 is the same race.
- Every owned entry scanned whole (decided): what devopsy did not write has the wrong owner deep under a correct top; measured 0.24 s warm, 0.75 s cold for 500,000 files. A fallback for huge trees (`-type d` only) was noted, never built.
- `--mnt-owners` ignores SIGTERM, SIGINT, SIGHUP and SIGPIPE (round 3): nothing interrupts after the switch, and Go keeps no inherited ignored SIGTERM, so the script's `trap ''` alone did not protect it.
- `--mnt-owners restored` warns instead of failing on labels it cannot read (review of 2026-10-23): a rollback to a release with the old `devopsy.sync` labels failed, for the reason rollbacks never check roles or imports; a chown failing on labels it read stays a failure.
- A `volumes` import's owners never locally on macOS (round 2): as before `up`, Docker Desktop's file sharing may refuse a chown. A snapshot's `--no-code` restore left the tar's owners until it applied the restored code's labels (review of 2026-10-25).
- Owners before compose's starting commands locally (round 3): `restart` starts containers too, and Docker makes a missing entry root's. `run --rm app composer update --dry-run` starts the app, so `--dry-run` counts only where cobra parses it (round 4). Never in a release on a server (round 2): a rollback's plain `up` failed on labels `--mnt-owners restored` only warned about. Unreadable labels and an owned entry that is a link only warn locally (round 3): `makeEntry` refused the link and every `up` failed before compose.
- macOS never checks owners: Docker Desktop and OrbStack let any container user write the Mac's files and show them the owner Docker asks for.
- The mounts check reads labels through `cli.SyncServices` (review of 2026-10-23, round 2): it parsed compose's output itself, passed a leftover sync capability, and the release failed after its switch on labels the owners' step could not read.
- Each bind source resolved as well as lexical (round 3): the check was lexical, so a release-tree link to below an owned entry, or a `shared/mnt` link into the release, passed.
- `throughMnt` (round 4): a bind source through links was resolved whole, so a link in `mnt` leading out of `mnt` lost it, and the owned-entry rule with it.
- `HiddenBinds` (review after v0.52.1): a 0700 directory of the app's hid a link to `/`, which the deploy user could not resolve and Docker did as root.
- `LeavingBinds` and its readers: a restored snapshot's link outlived the code its restore was checked in, and a rollback went live on it (review of snapshots, round 3); a full restore was refused by a link in the data it would replace and called itself a rollback (round 4); a sync's `finish go` started services on a copy that brought such a link (round 4). The start gate under all of them came after review round 5, whose every hole was a start no check per flow preceded. A push was refused for a start that never came, so a take, an export and a push check only when something of their set runs (review after v0.52.1). The child's side refused the `--reset` it named as the way out, so under `--reset` it skips the check (review).
- A bind source below an owned entry refused (decided, review of 2026-10-23, round 2): before, devopsy made such paths itself, the owner's, a directory at a time (`OwnedPaths`, gone), which the entry's owner could swap for a link to `/`. Below an unowned entry stays allowed (decided scope): such an entry is written from the host.
- `./mnt` whole is no entry (decided): no project needs it, it gave every entry one owner and carried every service's data, and its special cases (a sync's notice, the module `mnt`, an import emptying every entry, links between entries allowed) caused a review bug, a tar member `../x` into `.` emptying a container's root. The check refuses it writable on any service because once its mount was no entry the child guard no longer saw a service writing every entry (review of 2026-10-23: a sync rsynced under a running file manager).
- `--destroy` empties `mnt` through a plain `docker run`: `compose run` brought the project's network back after `down`.
- Containers named after devopsy's pid are started through `dockerRunFresh` (review of 2026-10-23, round 3): `docker run` refused the name a killed devopsy's container still held.
- `mnt-owner` is a named feature rather than a protocol bump: an older parent rsynced the parent's owners, an older child listed none, an older server's import kept the tar's; a release refuses through its own flags.
