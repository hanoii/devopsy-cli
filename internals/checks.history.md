History, not rules: the root's Checks section, Workflow's "Tests and checks" and `internals/e2e.md` win where they differ.

- "Every change carries its test" came from the reviews of October 2026, which found bugs in code that worked when written and broke under a later change nobody re-tested; the accepted cost is that the fakes grow with the code.
- Running the checks in Docker on Linux measured about three times faster than on macOS (50 s against 150 s): macOS checks each new executable on its first run, and the tests write thousands of fake scripts.
- The 26 `sleep 1.1` between releases in the tests went on 2026-10-24, once the server picked release ids; no sleep is needed for ids, locks or files since.
- Unit tests went parallel on 2026-10-24: on Linux with 4 CPUs, as CI's runners, 200 s serial became 50 s with all CPUs busy; on macOS (10 CPUs) 410 s became 145 s, most of what is left being the first exec of each new script (macOS checks every new executable), so the next lever there is fewer new scripts, the setups' fakes written once and copied only for a test that changes them.
- The race detector runs only over the packages that test in process: the script tests of `cmd/devopsy` and `internal/remote` run devopsy as a binary built by `TestMain`, which `-race` does not instrument, and under it they are several times slower and fail on time.
- The end-to-end lanes are processes, not `t.Parallel` (decided 2026-10-24): the tests keep their globals (`op`, `srv`, `server`) and everything they change (iptables, `tc`, the login shell, a Ctrl-C) belongs to their lane's containers, so no test needs to know about lanes; `resetLane` came when a Ctrl-C reached an earlier test's devopsy once the order changed.
- Measured on OrbStack (10 CPUs): 40 minutes serial, 11 with four lanes; the run takes about the larger of the slowest test (`TestSyncDestroy`, 144 s) and the tests' total over the lanes (about 2400 s over 4), so the slowest-first order keeps a long test from starting last.
- The test server's dash login shell found the watcher signalling only the script, where devopsy-server's bash hid it.
- The deploy user's home became a tmpfs on 2026-10-27: on OrbStack's btrfs the container's overlay cloned by reflinks, on CI's ext4 not, so a sync ran in another order locally than in CI and six tests failed only locally.
- The Docker Hub mirror came with the lanes, so four lanes pull from Docker Hub no more than one did.
- On 2026-11-03 the root's CI warning (200 lines, then 250) went, and Workflow's Docs got the number as a guide instead: Claude Code's memory docs advise under 200, but adherence drops gradually, the root at 205 made the warning fire on every run, where it was ignored, and the line is followed when a rule is written, by an agent that has Workflow loaded.
- `testfile.Write` came on 2026-11-05, after two script tests each failed once in a hundredth of a second in a combined run of `cmd/devopsy` and `internal/remote`, their messages lost, and about 170 reruns under outside load showed nothing: the trigger is forks from the same test binary during the write, which outside load cannot make. Forced in place on older code, about once in 400 iterations of those tests with a storm of forks added; the two original failures cannot be proven the same, though no other cause fits that speed. Go's own `os/exec` test retries on this race; the lock was taken instead, since a retry would have to wrap every script's first call.
- The checks' command went from root to a plain user on 2026-11-05: a door test used a fixed `/space`, which only root could make, so it passed in the command and failed on CI's plain user, and the release workflow's tests with it, which left v0.60.0 tagged with no release. It needs a user of the image's, `useradd` and not `--user`: a uid with no name fails what asks for one (`ssh-keygen`, `user.Current`). The go cache has a volume of its own, as the root one's files stay root's, and the checkout is read-only, which the tests already respect.
- Measured on 2026-11-11, after `--server-setup` and its firewall added 92 tests to `cmd/devopsy` and 21 to `internal/remote` (563 and 145 against v0.65.0's 471 and 124): `cmd/devopsy` took 117 s on Linux in Docker (10 CPUs) for 141 CPU-seconds, so its tests mostly wait, and 243 s limited to 4 CPUs (CI's runner, where go test runs 4 at once), 99 s there at `-parallel 16` and 96 s at 32, the same 634 results by name; on macOS 230 s for 886 CPU-seconds, 564 of them the kernel's (a process costs 2 ms of CPU there, devopsy's 6 ms), so CI's three-CPU macOS runner is CPU-bound and keeps the default. The Checks' command, `ci.yml` and `release.yml` run the script tests at `-parallel 16` since.
- Most of a release's 0.85 s in those tests, on Linux, is two fixed waits of the scripts: `followOutput`'s EXIT trap sleeps half a second before killing its tail, and `waitBeat` polls every 0.2 s. Shortened by hand (an experiment, not kept) they took `cmd/devopsy` from 121 s to 87 s, but cut the last lines the tail had not copied yet: shortening them needs the tail to end once it copied everything, a change to `internals/sessions.md`'s rule on how the tail ends, left for a decision. The heartbeat's whole seconds likewise keep `TestWaitBeatWithoutWatcher` at 20 s, `internal/remote`'s whole run.
- The slowest test, `TestReleaseSnapshotCases/interrupted` (43 s on Linux, 47 s on macOS), and `TestRestoreNoCodeInterruptDuringReleaseSnapshot` (22 s) waited for the fake's held tars to reach their own bound, 20 s a tar, since the stopped pass completes its tars whatever the session does: they let them go once the watcher took the session for gone (`goOnOnceGone`), 3.5 s and 5 s since.
- The sync setup's five fakes were written anew by each of about 460 setups a run: macOS checks every new executable on its first run (0.17 s alone, 22 ms each at ten at once, nothing for a hard link to one it ran), so they are written once and hard-linked (`syncBinOnce`). Sharing every executable `testfile.Write` writes, by content, was tried first: macOS's `cmd/devopsy` went from 257 s to 226 s, but `--server-setup` writes into and checks the mode of files a test planted, which changed the shared copy under other tests (its check at the run's end caught two), so it was dropped. The fake docker's sed and dirname on every call went too (a release's processes 182 to 160). With the held tars, macOS's `cmd/devopsy` went from 230 s to 207 s (two runs each, alternated), its CPU unchanged.
- Three tests failed in one day's CI on macOS, each a cause of its own. `TestRunDoorRead`, parallel, cleared the whole process's environment (`doorEnvironment`, in process), so every test after it lost `TMPDIR` and took `/tmp`, where macOS gives new files the group wheel: `TestMntScripts`, whose files must have the user's group, failed, every time when run with it. It runs the binary since, and `TestMain` fails a run that leaves the environment changed. `TestDestroyCutLeavesMovedBase` staged a leftover with pid 4242, which a run's own processes take now and then on macOS (pids wrap at 99999): staged leftovers use 2147483646 since, as one already did. `TestSyncImportCancelled` missed its 10 s once in CI's slowest run (933 s); 50 runs on macOS under two full suites never did, so it runs serially, as a latency check, and lists the processes left when it fails.
