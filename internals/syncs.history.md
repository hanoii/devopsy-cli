History, not rules: `internals/syncs.md` wins where they differ.

- The copy decides, never the answer: an answer lost after a complete copy once restored the child on the parent's data unsanitized, and one lost mid-copy ran the child on a mix of old and new data. The gate is named by the sync's id so a write left from an earlier sync can never claim a newer gate, and the claim is the rename alone, with no check of the content before it that another gate could slip under.
- The receive script's watchdog on `SyncStartedFile` came from a silent cut between two servers: the rsync waited for TCP to give up, since sshd sends nothing on a quiet forward and rsync's `--timeout` counts its own keepalives into the forward's local socket.
- Nothing taken on a marked environment is `partial`, decided: nothing written leaves an earlier sync's partial copy as it was, even when the parent's labels cover nothing now. `finish partial` starts again only this sync's own stops because a record of what was down before, written in prepare, missed a prepare failing earlier and started the import's set.
- A cut write ends with its services stopped, not restarted, decided: the service holds a half-loaded database, and a partial copy keeps everything off its data. The `/proc` check before signalling a recorded import's pid exists because a pid reused after a reboot may be another environment's import.
- The mark is one tab-separated line rather than JSON because the scripts read it with `cut`.
- The settle's sweep of leftovers (`syncLeftovers`) came from review round 9 of the data labels: a dump-sized spool stayed until the next finish.
- The holder writes to `$base/.devopsy-sync.log` when its session is gone because a write to the dead session killed what restores the services. The log was trimmed past `SyncLogMax` bytes to its last `SyncLogKeep` lines until 2026-11-01, two constants in two units, then by lines alone (`SyncLogLines`).
- The push watches its session's stdin because a silent copy may not write for minutes, so it only noticed a gone session at its next write; the fake ssh in the tests runs through dash on Linux, which never execs the last command of `sh -c`, so cancelling closes the pipe as sshd would.
- The state record is created before anything can fail because without one the side's whole set was restored, one down on purpose included.
- `settleStops` came from review round 5, found by hand on OrbStack: a push killed outright left the parent down through a take, `--status` silent, until a child synced. Round 6: `compose start` ran the old code under the new current, hence `images.Recreate` for a container on another image; and a killed holder's stops started first ran the database on a half copy, hence the settle makes them its mark. Round 7: a hook's `devopsy --export` started what its export had stopped, hence `HeldStopsEnv`. A start that fails only warns because a start gate refusing a link would otherwise fail every release that could remove it.
- A child's first release creates its data services and its side's set before the finish hook because a template's hook sanitizes through the app: without it, the parent's passwords reached a child. The `first` line also covers no container at all when prepare started, since a stream's import creates its container before finish looks, and a first release killed before its `firstDown` may have left one.
- The data images' rules were settled over four reviews (2026-10-24 and after): only `volumes` services as the parent resolves them now are in `ParentData`; the holder checks and pulls while its watcher is still armed; the parent's image is held by digest in the child's own repository, since Docker finds a digest only under the repository named and a child may reach only its mirror; the child's history ends with a line naming the image as the child does, so its own name moving forward needs no `--yes`, and a parent drifted back to an image the history has adds no line; `ParentHistoryLines` is a total of 100 because the lines ride in the child's script as one argument, capped at 128 KB on Linux; only `finish go` recreates on the parent's image, since an abort in a release that syncs restores the child's own data, which the release's never-live images must not touch; the line naming the image as the child does is added only when the child ran that very image (a mirror), never for another series let through; the child's image checked is what its own name holds (`ownImage`), never the parent's it is held on, so a child on another series is refused on every sync; a check or restore that fails removes what it pulled by digest. The platform refusal's words (`otherPlatform`) cover both Docker stores' messages.
- Every export runs before any import, decided 2026-10-27: an import reads its spool, never the parent, so a parent stopped for its exports was down through the child's load too, often several times the dump; the cost accepted is every spool at once on the child's disk. A cut export never reaches an import because the import reads a spool, never a pipe.
- Reflink clones on the parent came from reviews of the sync's downtime: the reflink check and the `du` moved before the stop (only the clone is downtime); streams run before the start when the set holds a `custom` service or one stopped `always` so its files and the dump are of one moment; otherwise after it, told nothing is stopped (round 2: a script following the contract would `run --rm` beside the running service); a cancel during the check stops nothing (round 2); the clone's containers never carry the sync's own prefix, since the child's holder removes those as writers and could kill the clone's removal. Measured on XFS (2026-10-27): the parent's pages written while a clone exists fragment its files, about two extents per 16 KiB page written, which stay after the clone goes (`xfs_fsr` undoes it), as snapshots' clones already did; accepted.
- `devopsy.data.copy.reflink` is opt in and for files only because every page a database writes while a child shares it lands elsewhere (4,000 writes made 5,600 extents of one file). Its reviews: an entry that is a link on either side is rsynced; the probe goes to the real destination (round 2: one probe into the child's mnt took a volume on another disk for no reflinks at all); an emptied entry rsynced again was a full copy every sync on ext4, hence the first failure switches the rest to rsync; a live source's file removed during `cp` fails it, hence the second try (round 2).
- rsync runs in the util image as root with `--numeric-ids` so owners and modes survive and the deploy user's permissions do not matter. `--no-D` came from review round 4 of 2026-10-23: as root rsync made device nodes on the child's host, where bind mounts are not nodev, and `--chown` gave a block device to the entry's owner. Nanosecond times came from a test server on 2026-10-23: to the second, rsync skipped a datadir's files of the same size that both sides wrote in the same second (the child stops right before the parent), and the child's database opened its old tablespaces under the parent's dictionary.
- The util image is rebuilt weekly since 2026-10-23: it was built once per host and never again, so patches to `alpine:3` never reached it. One implementation in Go because the receive script once built it in shell, where a weekly check would need GNU `date`, which macOS, where the tests run the scripts, lacks.
- A sync takes no rsync arguments, decided 2026-10-23: it copies environments whole, and what must never be copied is a label.
- `--reset`'s `down` takes every container, a holding service (for example `alwaysup`) included, decided 2026-10-27: keeping what no label stops would leave containers across a start-over.
- The child's words and the push's checks and copy order became functions of their own, decided 2026-11-04: `--sync-services` and the push had grown to about 285 and 360 lines. `copyOrder` is a pure function so its order has a table test with no fake docker; `finish`'s word stayed two ifs, too little for a function, and the push's closures stayed, since they share state.
- `place` holds what a child-side word runs in, decided 2026-11-04, and only those words take it: every call site would have been a sweep for little. It leaves out `services`, read at a moment (a restore reads the restored code's, a finish reads them again), and `snapshotPaths` stays apart: `filepath.Dir(cwd)` is not one answer for an environment's directory, since `--snapshot-step check-tars` runs in the new release's code.
- The sync's session variables stay read where they are used, decided 2026-11-04: about 20 small functions in two processes read them, so a struct would be that sweep too. `runSyncPush` and `syncRsync` read theirs once.
- No names for the `signal.Ignore` sets and no shared `undo`, decided 2026-11-04: leaving TERM out looks deliberate in each set, so a name says less than the comment at its site, and an import's undo overrides the exit code while a take's says other words, so one function would shrink nothing.
- A stop recorded before it runs (decided 2026-11-04): `stopSet` and `stopServices` did so, but `endImport` and `endWriters` recorded only after a stop that succeeded. An import failing whose end's stop failed partway left services down outside the record, so the retry that completed cleared the mark with them still down, and the failure's message named only what the record held. Found by measuring which failure paths no test reached.
- `--reset` moved to a down by the project's name alone on 2026-11-05, as `--destroy` had the day before (`internals/data.history.md`): it said every volume goes, but with `-f` compose left a volume only an older release named, its data still there for a rollback to that release to find.
- The receive across servers moved onto its sessions on 2026-11-09. It had gone through a reverse forward, first to a daemon on the parent's loopback guarded by a password, then, under the project users' firewall, to a unix socket the push relayed. A review round found the forward itself the problem. The receive's root rsync ran on the child's host network and connected to whatever port the request named, so a project user, or a hostile parent, read the first line of any local service. And a forward works with no command run, so a sync key kept one open with no sync, for up to its two days, and could plant a unix socket where its user writes. Checking the port as the caller's own listener was weighed and set aside as a fix of the symptom. Now rsync's daemon protocol runs over each entry's session (`ReceiveShim`, `receiveSession`): no port listens on either server, no container has a network, the key is plain `restrict`, the password went, and the receive mounts only the entry it writes, which another finding of the same round needed (a hostile daemon replacing a deploy user's child's entry with a link). The cost is one session per entry and volume.
