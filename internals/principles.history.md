History, not rules: the root's Principles section wins where they differ.

- `devopsy-compose.yaml` was decided on 2026-10-23 as the one file devopsy adds beside a release: a hold by digest is the one fact compose can only take as a service's `image:`, which no variable or label can express; the accepted cost is that a plain `docker compose` on a server lacks the file.
- "Nothing is frozen before 1.0.0" and the two limits on reviews (no tests of specific older versions, no code for an older operator's or server's scripts, no version-skew edge cases) were decided on 2026-10-26, after review rounds were spent on mixed-version edge cases; mixed versions are not a concern beyond the gate itself, since a new behavior an older server lacks is a named feature or a protocol bump that refuses before anything changes.
- devopsy replaces itself with the command it runs so that `devopsy up` behaves as `docker compose up` does; the accepted cost is that nothing runs after the command (no cleanup, no notice), hence the detached `--upgrade-check` and the server scripts for what must happen after.
- Push over pull was chosen for having no control plane, daemon, webhook or deploy key: one command from anywhere; the accepted costs are that a release needs the operator until its switch and that syncs across servers work only through the operator's forwarded agent.
- On 2026-11-08 a sync across servers moved from the operator's forwarded agent to a key the operator makes for each sync: with project users, a door parent's login is the weak user, and any process of it could use the forwarded socket for every server the agent's keys open, root on the parent itself through the deploy user's key or back through a host of the attacker's with `-A`; blocking the parent's own sshd closed only the shortest path. The key's forced command does that sync's requests on the child while it is open there, the child building every script itself. Weighed and rejected: a dedicated agent holding only that key (forwarding stays, and CI keys keep it), ssh certificates (a standing key on every laptop that mints logins), a sync user of its own behind an sshd `Match` (a third identity and another reboot), the child pulling (the same key the other way), and relaying through the operator (the data would cross the operator's link twice). The accepted cost is that whoever runs as the parent's user during a sync can read that key.
- Names from project, instance and environment alone replaced a `path:` key, compose's `name:` (overridden through `COMPOSE_PROJECT_NAME` in `devopsy-target.env`), the checkout's folder and the local `COMPOSE_PROJECT_NAME`; the `-` join can collide (`a-b` + `c`, `a` + `b-c`), which `--check-names` refuses (internals/releases.md).
- A server-wide variable layer existed as `/etc/devopsy/devopsy.env` and went, and a file the proxy's release would write for other projects was rejected: nothing hidden on a host may change what a project sees, so what a server knows is its targets' variables or an export of the project that owns it; the cost is that CI and laptops name the server (`DEVOPSY_SERVER`, the address).
- "What is deployed decides on the server" costs that every server's devopsy must keep up (`devopsy @<server> --upgrade`).
- "Before the switch anything cancels; after it nothing interrupts" costs that a stuck run step can only be stopped on the server.
- "Check everything before changing anything" costs the marker files and the code that reads them; the alternative, a server needing someone to log in and guess after a cut-off session, was never acceptable.
- "The server never waits on the operator for long" costs that an operator frozen past the quiet time (a laptop asleep, Ctrl-Z) cancels, cleanly.
- "Words are never built-ins" costs that devopsy's features read as flags (`--release`, `--sync`), never as subcommands; `--` is the escape hatch.
- "Projects own policy; devopsy owns mechanics" costs that the templates carry the conventions and devopsy only reports facts to them (the `finish` word, exports).
- The Principles line on `devopsy-compose.yaml` was narrowed to what runs, and a build-mode fetch given a file of its own: a review found each release's own build running by the project's name, which every environment building under it moves (an `image:` beside `build:`, a branch's or a pull request's environment). Rewriting `devopsy-compose.yaml` before a fetch was set aside, since at a restart it is the live release's file, and a fetch cut there would leave it with no holds; the fetch's own file is removed once the fetch is adopted.
- A lock taken in Go waited its own way: the image lock's shared wait was said, its words of its own, and the sync keys' edit waited a minute in silence. Both moved onto one helper, `boundedWait`, worded as the scripts' `lockWait`, so both are said one way; the sync keys keep their minute, as the `--ssh-keys` scripts wait that long for the same lock.
- The Go helper was named for locks, `lockWaiting`, until Docker's restart after `--server-setup` waited through it too: a restart is no lock, and the words fit any wait that ends, so it became `boundedWait`, the principle naming every wait for a lock or another process.
- What a server knows for a project gained what devopsy computes for the target on 2026-11-12, with the uids an environment's containers run as (internals/uids.md): a probed uid is a host's own value, so the principle names computed values beside the targets' variables and the exports, each shown by `--env`. "No registry of environments" was kept as it was: a uid claim is found by its owner's name, like an environment's directory, and nothing finds environments through the claims.
- The Principle on a current Docker said, until 2026-11-12, that a feature needing one refuses an older Docker with words, through the door's helper: the containerd image store and buildx 0.33.0 were what project users needed, checked only by `--project-users add`, a claim and `--server-info` on a server with project users, and compose 2.33.0 only by a build with contexts. Every server is new, from a current Debian or Ubuntu with Docker installed fresh, so the floor became every server's, one table (`dockerFloors`) judged by one helper (`floorMissed`): `--server-setup`'s Docker item, a release's `--server-ready` (three short Docker calls, run at once, about 50 ms on a real daemon, made only until an apply of the same devopsy notes the floor met in `server.yaml`, so a release on a server set up pays nothing; a Docker put back below the floor since waits for the next devopsy to be seen, accepted, with no opt-out) and `--server-info` read it, and the door keeps its two reads under its own environment. The classic image store is refused with words that say devopsy supports a current Docker installed fresh, and moving a Docker to the containerd store is documented nowhere: a server on the classic store gets a new server.
- The Docker floor's Principle said "a current Docker installed fresh"; it names the containerd image store instead, the words a server's admin reads in the refusals.
