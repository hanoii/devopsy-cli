# Door

A project user has no Docker socket: what it finds as `docker` asks the deploy user through sudo. Code: `internal/door/` (the decisions, touching nothing), `cmd/devopsy/door_client.go` (the project user's side of sudo), `door.go` (the deploy user's), `utilscripts.go`, `internal/remote/door.go`. `e2e/door_test.go` runs what needs a real kernel, Docker and sudo, each with a control that the attack works where the rule is off.

- The door checks a rendered compose file and devopsy's own requests, never Docker's API: a policed socket's requests are read one way by it and another by the daemon, and compose acts as whoever runs it, past any socket.
- Projects on one daemon are kept apart by the door's checks, and more isolation than that is a server of its own, never a daemon per project here (for example rootless Docker or a VM): one Traefik must reach every project's containers.
- What runs is what the door checked: a name, a tag or a path is pinned or held from its check to its use (for example `imageLock`, `Paths.Real`, `cloneShape`), since a value resolved again after the check is a value nobody checked.
- The door's protection depends on no template or project: its rules are on compose keys and devopsy's requests, deny by default, so a file that does not meet them is refused, and only what a label means to a proxy is left to the admin's vet (`door: vets:`), as devopsy knows no URL.
- A server's `door:` is read only from the deploy user's own config: a project's could grant itself.
- A project user's entry is a file of its own, `door/users/<user>.yaml` beside the deploy user's config (`DoorDir`), merged into `door: users:`, and a user in both refuses: devopsy-server rewrites the config it marked at each run, and a round trip through YAML loses the admin's comments.
- Who asks comes from `SUDO_USER`, and every word of the request is treated as hostile.
- A project user's keys are the deploy user's to edit, in `DoorDir`'s `keys/<user>` (`--ssh-keys --for`), and sshd reads them only through `--authorized-keys`, dispatched before anything else, printing only lines that parse: a key a project user puts in its own home is never read, or a leaked key would add a second one that outlives rotation.
- A project user's sync keys (`DoorSyncKeysFile`) are the door's to write (`--door sync-key`, from `--sync-key` as that user), each line the door's own (`remote.SyncKeyLine`), for an environment in that user's tree, and `--authorized-keys` prints them after its keys; a leaked key could add one that does that user's syncs' requests until its sync ends or it expires, so removing any of the user's keys, or the user, drops them all (internals/syncs.md).
- Who the socket lets in has no door (`runDocker`): the deploy user, and a project an admin put in the docker group.
- `--door` and `--door-read` are dispatched first in `run`, before anything loads a project or reads the environment.
- The deploy user never reads a project's tree: what it needs comes from `--door-read`, run as that project's user, so no link or swap there can show it anything of the deploy user's.
- A project user's answer about a path is believed only for a path whose every part is the deploy user's (`Paths.Real`).
- Compose runs on a file the project user rendered, never on the project's own: compose reads `env_file` and `extends` and runs `provider` as whoever runs it.
- A whole project's `down` (`--destroy`, `--reset`) runs by its name alone, which `OwnName` checks, with no file: compose finds what it holds by its own label, an older release's included.
- A rendered file and each verb's flags are checked deny by default (`CheckFile`, `CheckVerb`), so a key compose adds later fails closed.
- A compose upgrade is tried against the rules before devopsy-server moves its pin: a key it starts writing by default refuses every `up`.
- A bind holds no path with a part the project user can change, since the daemon resolves a bind at each start: an entry by its real path under `<space>/mnt/<compose name>`, a read-only part of a release as a sealed copy under `<space>/sealed/<project>`.
- The project users' firewall is devopsy's, one for the server (`internal/remote/firewall.go`), never per user: a chain jumped to first from filter's OUTPUT by the group (`--suppl-groups`) rejecting loopback, Docker's bridges (`-o docker0`, `-o br-+`) and the metadata services, and a chain jumped to from raw's PREROUTING dropping containers' packets to the metadata services, in IPv4 and IPv6. A bridge the deploy user renames (`com.docker.network.bridge.name`) is not matched, which a project user cannot do (`driver_opts` refused).
- The firewall goes by interface and by the metadata services' addresses, never another range: a sync reaches another server at any address, one inside Docker's pools included. All of link-local is a metadata address (`169.254.0.0/16`), since it is never another server's, and the clouds' others are named.
- DNS at a metadata address goes through, for project users by `--ctorigdstport 53` and for containers by `--dport 53` (raw has no connection tracking yet): Google's resolver is its metadata server, AWS's 169.254.169.253.
- On loopback, which the host's own addresses go out through (its sshd included), the firewall lets through only a resolver, by the port first asked for (`--ctorigdstport 53`, as Docker's own at 127.0.0.11 is moved by a NAT), and the answers to a connection another made (a sync's forward is the project user's sshd).
- The firewall's rules are written as `iptables -S` prints them (`doorRules`), so the lines loaded (`DoorFirewallLoader`, `iptables-restore --noflush` of devopsy's chains alone) are the lines checked (`DoorFirewallWrong`): a chain differing, or a rule ahead of a jump that is neither a DROP nor a REJECT, is wrong.
- `add` loads and checks the firewall first, as root through the util image with the host's network, and refuses when it is wrong; `DoorFirewallUnit` loads it at boot, after what loads a whole ruleset and before the network's services, and `DoorFirewallTimer` every five minutes from the next boot (the install runs chrooted, where `systemctl` does nothing), since a reload of the server's own firewall drops it silently; `--server-info` reads it the same way: the deploy user can neither read nor change iptables.
- Docker's `userland-proxy` stays on: the loopback's REJECT stops a project user's packet before `docker-proxy` reaches a published port, and turning the proxy off drops IPv6 visitors to IPv4-only containers.
- `<space>` is on a mount of its own with `nosuid` and `nodev`, or the door refuses every request (`spaceGuarded`): a container's setuid file or a crafted tar there otherwise crosses projects, or reaches root.
- A project user's `shared/mnt` is a link into `<space>`, made at a release's start (`--mnt-ready`), and a compose name comes from where an environment is in that user's tree, never from a caller (`Policy.NameOf`).
- Entries are made by the door, so a project user can write inside one and never replace it: when devopsy's own mkdir is refused (`makeEntry`), and what a file binds, at `compose config`, since a step writes in an entry before anything starts (`entries`), and at `up` (`bindEntries`).
- What a root util container writes in an entry is given back to the project user as `rwX` when it exits, or when it is removed for one detached (`Regrant`, `Removes`, `regrant`): a tar's or an rsync's mode on a file with an ACL sets its mask, which narrows the project user's entry, and only an owner or root changes an ACL, so a root util container does it, touching only what lost its group class's write.
- An entry the door made a directory, not knowing it is a file, is replaced while empty: the two are told apart only by an import or a sync.
- A service is on its project's own networks, a joinable one or none, never Docker's default bridge (`network_mode: bridge`): every service with it shares docker0 and reaches the others' ports there.
- A project's network has no IPv6 (`enable_ipv6` refused), its address space Docker's: fewer paths across the server to keep shut.
- A service on a shared network is named `<project>-<name>` (`OwnName`), and holds no alias or fixed address there: compose makes each service's name an alias on its networks, which would answer for another's name (for example `traefik` on `tunnel`).
- A listing is cut by container id, never by trusting a caller's filter: filters of one key widen each other.
- The door acts only on containers it made for the asking user (`devopsy.door`, `door.DoorLabel`, on every service it runs and every util container), and runs no compose command while a container it did not make is under the project's names (`Policy.Foreign`): compose's and devopsy's labels are anyone's to set outside it, and such a container runs as root with any mount.
- Of another project's labels, only its role, compose project and exports are ever read (`exportedLabel`).
- A util container is one of the forms in `internal/door/forms.go`, its command, its arguments and its mounts checked together, never one a caller gives: it is root on the host's files, and a command paired with another's mounts writes where a bind goes by.
- A new util container gets a form and a line in `TestDoorTakesWhatDevopsyRuns`, which runs devopsy's own against a fake docker: else a project user's release fails on it at runtime.
- An rsync that names a whole mnt holds only the entry it writes (`narrow`): what it copies could otherwise leave a link where a bind's source goes by.
- A word in a util container's arguments never starts with a dash: `find "$@"` would take it as code.
- A Docker command devopsy calls has an answer here, or a reason in `doorVerbs` (`TestDoorKnowsDevopsysDockerCommands`, which sees `exec.Command`'s and scripts' lines, not a helper's).
- An image's own labels under `devopsy.` or a vet's prefix refuse it, what a service builds included, by compose's name for it: they land in its containers' labels, past any check of a file's, and an image not here yet is pulled first so they are read.
- A start runs the image the door read: compose never pulls or builds one then (no `pull_policy` but `missing`, `never` or `if_not_present`, `--pull` only `missing` or `never`, an image still missing refuses), and the project's image lock (`imageLock`), which a build, a pull and a tag take too, is held into compose's exec, so nothing changes the image between the check and the create.
- An image is a project's when only it writes one of its names (a build's, under its names; a hold of its own) or when it claimed it (`door.Policy.OwnsImage`); any other is claimed before a start runs it, an inspect reads it or a tag takes it as a source (`Action.Claims`, `doorSide.claim`): pulled with the project's own registry logins, then its id recorded in `<space>/images/<user>` (`Policy.ImagesFile`), so an image another project pulled with its own logins, or built, is never this one's by being on disk, and once claimed a start asks the registry nothing. A claim never writes another project's hold (`Claimable`): a registry's tag of that name would be one here. devopsy's util image is the server's own.
- A build writes only a tag of this project's, and holds no labels of its own.
- A build runs on the project's own BuildKit, `devopsy-<project>` (docker-container driver, made at its first build, `builder`), its settings in `<space>/buildx`: on one builder, cache mounts are shared across projects by their id, so one project's build would fill a cache another's trusts. Its `FROM` comes from a registry or its own stages, never the server's store, which that builder does not see.
- The deploy user is who owns the binary (`deployUser`): an install of it as root would point the door at root.
- A container runs as `<uid>:<gid>` in numbers, never 0, the deploy user's ids, the door's users' or the socket's group (`hostIDs`), for a service's `user:` and `exec -u` alike (`userRefused`): a name is the image's to map to 0, and a host id is that user's to reach through `/proc`.
- A server with project users needs `sudo`, `acl` and `<space>` on its own mount, the admin's; `--project-users add` puts the rest on the host, all of it devopsy's own interface (`DoorHostScript`): the `devopsy-projects` group, the two sudo rules (`%devopsy-projects` to the deploy user for `devopsy --door *`, the deploy user to them for `devopsy --door-read *`), sshd's drop-in and the root-owned script it runs, and the `docker` link to devopsy, refused over a real `docker`.
- Each host piece lands only when missing or different, and only after its check (`visudo -c`, `sh -n`, `sshd -t`, with the old drop-in put back on a refusal): a broken sudoers file breaks every sudo on the server, and a broken sshd config every login.
- `add` checks what sshd resolves for the project user (`doorSSHDTakes`, `sshd -T -C user=...`), devopsy's keys command as the deploy user and no file of keys, before its entry is written: a `sshd_config` with no Include of `sshd_config.d`, or with it below a Match, parses and leaves the user on its own `~/.ssh/authorized_keys`.
- A project user has no cron or at jobs (`/etc/cron.deny`, `/etc/at.deny`): they run with no session, so a leaked key's job would outlive the key's removal.
- `--server-info` lists a project user's environments as that user (`--door-read environments`, `treeEnvironments`): the deploy user never walks a project's tree.
- devopsy's path goes into sudoers, which has no quoting, so `add` refuses one sudo would read as more than a path (`DoorDevopsyPath`), and into the keys command quoted.
- sshd takes the drop-in at a reboot, never a reload by devopsy (`DoorRebootMarker`, `/run/reboot-required`): a reload is a privileged container in the host's pid namespace, and a service name per distribution.
- `add` refuses while the deploy user or root is in `devopsy-projects`: sshd would ignore their own keys for devopsy's, and once sshd has the door, that locks them out at once.
- `add` refuses while a container the door did not make is under the project's names, and a tree that is there and not the project user's (`doorTreeCheck`), before it makes anything: either would hand that user what another made.
- A release by the deploy user of a compose project under a project user's names is refused before its switch (`--check-names`, `doorNameOwner`, the door's own `OwnName` among the server's projects): the door would then refuse that user's every compose command.
- `add` refuses a project name that extends another's on the server, or another extends (`projectNameClash`, over the door's users and the release root): compose names are flat, so whichever came first would hold the other's networks, volumes and containers.
- What `add` writes in a project user's home is written as that user (`runuser`), and only when the user is new: root writing in a home its user owns follows the links that user put there.
- `remove` drops a project user's entry, keys and sync keys, never its Unix user: deleting a user that holds a tree and data is not one subcommand's.
- A door killed mid-way leaves its work directory for the next request's sweep, a day on (`sweepWork`).
- A root container holds no path a project user can change: input is copied in and output collected by that user's rights, and a restore streams through a container with no mounts.
- A project's registry login reaches compose as its `auth` values alone, in the door's own directory: Docker's CLI loads plugins and helpers from a `DOCKER_CONFIG`, which would run the project's program as the deploy user.
- A project user's `docker login` goes through the door (`doorLogin`, `doorSide.login`): the deploy user's `docker login` asks the daemon to check it, with a config directory of its own, gone after, since the project user's own client reaches no registry on its server under the firewall; then the project user's devopsy writes `auths` itself, as user and password (never an identity token, which the door's pulls do not read), under the key a pull looks up (`loginKey`, `door.HubLogin` for Docker Hub).
- A login's password never comes on a command line (`-p` refused): it comes on stdin or at a prompt (`readSecret`, the terminal put back on an interrupt), and on stdin to the door.
- A login's registry and user reach `docker login` only as values (`door.LoginRegistry`, `door.LoginUser`): a host and port, or Docker Hub's key, and one word.
- A rendered file holds only `$$`: compose interpolates what it reads, after these checks, so a `$` not doubled refuses it (`variableIn`).
- A util container's mounts sit only where devopsy's own commands look (`mountTarget`), and its sources hold nothing of `--mount`'s or `-v`'s syntax (`mountSource`).
- `<space>/mnt/<name>` and `clones/<project>` are closed to every other user, and `sealed/<project>` to all but the deploy user, whatever modes a container gives its files.
- Nothing stays in `<space>/work` after its container, and sealed copies go once no container holds them, an hour old (`pruneSealed`).
- A compose name is a project's only while no other project's name extends its own, on the server's list and in its release root (`Policy.OwnName`).
- A secret reaches the door and a container by name, its value on stdin: a command line shows to every user of the server.
- The door's environment is its own (`doorEnvironment`): a caller's PATH would choose its docker, and a HOME the config it obeys.
- The door rewrites the file compose runs (a build's block, sources pinned or sealed), which `devopsy -- config` does not show, and a server with project users needs more than Docker, devopsy and a few tools: both accepted, against their Principles, for a project user only.
- Of the image store, only a hold or a built name is a project user's to remove: a plain name may be others', and `image prune` is server-wide, so both do nothing for it.
- A reflink clone lives in `<space>/clones/<project>`, on the data's filesystem, reached through a link in the project's tree: it holds other uids' files, and the project user reads it and cannot change a part of a path to it (`cloneDirReady`).
- A sync's rsync daemon has no network, and the door takes only `exec -i` of `DaemonServe` on a container it made: the push relays to it from a socket of its user's, never a port on the host's loopback.
- The door sets its own umask: a caller's comes through sudo.
- A rendered file goes to compose as an unlinked file (`unlinkedFile`), so nothing of a project's environment stays on disk.
- What the door refuses goes to `<space>/refused.log`, a vet's refusal too: a real release asks for nothing refused, and `image prune`, the admin's, does nothing here.
- Labels under a `door: vets:` prefix go to the admin's program, the rendered file on stdin and the project in `DEVOPSY_DOOR_PROJECT`, and exit 0 allows: devopsy knows no URL (Principles).
