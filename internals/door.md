# Door

A project user has no Docker socket: what it finds as `docker` asks the deploy user through sudo. Code: `internal/door/` (the decisions, touching nothing), `cmd/devopsy/door_client.go` (the project user's side of sudo), `door.go` (the deploy user's), `door_login.go`, `utilscripts.go`, `projectusers.go` (`--project-users`), `sshkeys.go`, `authorizedkeys.go`, `synckeys.go`, `internal/remote/door.go`, `projectusers.go`, `keys.go`, `firewall.go`. `e2e/door_test.go` runs what needs a real kernel, Docker and sudo, each with a control that the attack works where the rule is off.

- The door checks a rendered compose file and devopsy's own requests, never Docker's API: a policed socket's requests are read one way by it and another by the daemon, and compose acts as whoever runs it, past any socket.
- Projects on one daemon are kept apart by the door's checks, and more isolation than that is a server of its own, never a daemon per project here (for example rootless Docker or a VM): one Traefik must reach every project's containers.
- What runs is what the door checked: a name, a tag or a path is pinned or held from its check to its use (for example an image's pin, `Paths.Real`, `cloneShape`), since a value resolved again after the check is a value nobody checked.
- The door's protection depends on no template or project: its rules are on compose keys and devopsy's requests, deny by default, so a file that does not meet them is refused, and only what a label means to a proxy is left to the admin's vet (`door: vets:`), as devopsy knows no URL.
- A server's `door:` is read only from the deploy user's own config: a project's could grant itself.
- A project user's entry is a file of its own, `door/users/<user>.yaml` beside the deploy user's config (`DoorDir`), merged into `door: users:`, and a user in both refuses: devopsy-server rewrites the config it marked at each run, and a round trip through YAML loses the admin's comments.
- Who asks comes from `SUDO_USER`, and every word of the request is treated as hostile.
- A project user's keys are the deploy user's to edit, in `DoorDir`'s `keys/<user>` (`--ssh-keys --for`), and sshd reads them only through `--authorized-keys`, dispatched before anything else, printing only lines that parse: a key a project user puts in its own home is never read, or a leaked key would add a second one that outlives rotation.
- Nothing of a project user's home runs at a login: its login shell is devopsy itself (`remote.DoorShell`, a link to the binary, `runDoorShell`), static, so nothing a login's environment names is loaded into it (`LD_PRELOAD` from a home's `~/.pam_environment`, which some distributions' sshd PAM reads, or from `~/.ssh/environment`), and it hands `/bin/sh` an environment of its own (`doorShellEnv`: the password database's home and names, a fixed PATH, a terminal's and locale's names), a command as `sh -c` and an interactive shell as no login shell, with no `ENV`, so no `~/.profile`; `add` refuses a devopsy that is not static (`staticSelf`); its systemd user manager is masked (`/etc/systemd/system/user@<uid>.service` to `/dev/null`), which pam_systemd starts at every login to run the units of the home; the home is the user's to write, and a leaked key's hook would run at a kept key's next login.
- sshd runs nothing of a project user's home at a login and forwards it no agent, X11 or tunnel (`doorDropIn`: `PermitUserRC no`, `AllowAgentForwarding no`, `X11Forwarding no`, `PermitTunnel no`): a leaked key's `~/.ssh/rc` would run at the next login of a key kept, and a process it left could use an operator's forwarded agent.
- Removing any of a project user's keys (`KeysRemoveScript`), or the user (`removeProjectUser`, after its entry, so the door answers nothing meanwhile), ends every process it runs and its linger, then drops its sync keys under their lock, in one helper for both (`endProjectUser`, the key's script calling it through `remote.EndProjectUserFlag`), and the door refuses a user with no key (`remote.KeysLeft`); a key's removal marks its end before the key goes (`remote.DoorEndingFile`) and clears the mark once the end completes, the next edit or listing of the user's keys finishing an end a failure or a cut session left (`keysSettle`), and the door refusing the user while the mark is there: a key removed is no longer trusted, and a process it left running (setsid, nohup) outlives its logins, since logind leaves a user's processes running on Debian, and keeps the door by its group.
- The end also removes the project's builder and its network (`endBuilder`), made anew at the next build: a removed key's build fills its caches (cache mounts, layers), which the owner's next build would trust.
- The end runs devopsy itself as root in the util image under the host's pids (`remote.EndUserArgs`, `runEndUID`): a child takes the user's uid as its effective one and one no process has as its real and saved one, and kills with `kill(-1)`, which no fork races, while the user's processes cannot signal it; the root parent then kills by pid what a scan of the processes' credentials in their status still finds, until none: a scan and a kill by pid alone miss a process that forks its next and exits. That uid is `door.EndUID`, which no container of the door's may take, and a process at it never holds up the end.
- A project user's sync keys (`DoorSyncKeysFile`) are the door's to write (`--door sync-key`, from `--sync-key` as that user), each line the door's own (`remote.SyncKeyLine`), for an environment in that user's tree, and `--authorized-keys` prints them after its keys; a leaked key could add one that does that user's syncs' requests until its sync ends or it expires, so removing any of the user's keys, or the user, ends the user under the sync keys' lock in one stretch (`endProjectUser`): the sync keys go first, sshd taking none for a login while the end runs, then the processes, then the keys file is made anew (`renewKeys`), and the door adds none for a request whose keys file is no longer the one it found (`doorSide.keysAt`): a door already past its sudo outlives the processes ended (internals/syncs.md).
- Who the socket lets in has no door (`runDocker`): the deploy user, and a project an admin put in the docker group.
- `--door` and `--door-read` are dispatched first in `run`, before anything loads a project or reads the environment.
- A read as a project user (`--door-read`) starts through `doorRead` alone, in a session of its own: its process is that user's to trace, and in the caller's session it would hold the caller's terminal (an admin's, under `--server-info`) to read and type into.
- The deploy user never reads a project's tree: what it needs comes from `--door-read`, run as that project's user, so no link or swap there can show it anything of the deploy user's.
- A project user's answer about a path is believed only for a path whose every part is the deploy user's (`Paths.Real`).
- Every answer the deploy user holds from a read as a project user goes through `doorAnswer`: a cap on its size and a deadline (`doorReadWait` in a door request, `doorTreeWait` for `--server-info`'s read of a tree), the read's sudo killed then: that user's files make the read as large and as slow as it likes (a FIFO), and a read held open holds a process of the deploy user's, whose process limit sshd's look at keys runs under. A sealed copy's tar streams to disk, past this cap, `<space>` being the project's to fill from its containers anyway.
- Compose runs on a file the project user rendered, never on the project's own: compose reads `env_file` and `extends` and runs `provider` as whoever runs it.
- A whole project's `down` (`--destroy`, `--reset`) runs by its name alone, which `OwnName` checks, with no file: compose finds what it holds by its own label, an older release's included.
- A rendered file and each verb's flags are checked deny by default (`CheckFile`, `CheckVerb`), so a key compose adds later fails closed.
- A project user's compose global flags go to the render, and only those that change what renders (`composeGlobals`, `composeLone`); any other (for example `--dry-run`) refuses in its client (`dockerCompose`): the door gets the verb and what follows it, and would run the command without the flag.
- A compose upgrade is tried against the rules before devopsy-server moves its pin: a key it starts writing by default refuses every `up`.
- A bind holds no path with a part the project user can change, since the daemon resolves a bind at each start: an entry by its real path under `<space>/mnt/<compose name>`, a read-only part of a release as a sealed copy under `<space>/sealed/<project>`, made only when the verb starts containers (`up`, `create`, `run`, `door.StartsContainers`), any other binding nothing.
- `restart` and `start` first warn of each service whose containers hold another sealed copy than the release would seal now (`warnSealed`, `door.KeepsSealed`), the release read and hashed as a seal does (`sealRead`), keeping no copy, and a failure loses only the warning: a container keeps the copy it was made with, so a restart would run a file changed in place in the release as it was, saying nothing.
- The warning offers a release by the session's address (`sealedFix`), in words without one, never a compose command: shown locally in a session, compose's would run on the local project.
- The project users' firewall is devopsy's, one for the server (`internal/remote/firewall.go`), never per user: a chain jumped to first from filter's OUTPUT by the group (`--suppl-groups`) rejecting loopback, Docker's bridges (`-o docker0`, `-o br-+`) and the metadata services, and the containers' chain jumped to from raw's PREROUTING dropping containers' packets to the metadata services (`FirewallContainerChain`, every server's, internals/server-setup.md), in IPv4 and IPv6. A bridge the deploy user renames (`com.docker.network.bridge.name`) is not matched, which a project user cannot do (`driver_opts` refused).
- The firewall goes by interface and by the metadata services' addresses, never another range: a sync reaches another server at any address, one inside Docker's pools included. All of link-local is a metadata address (`169.254.0.0/16`), since it is never another server's, and the clouds' others are named.
- DNS at a metadata address goes through, for project users by `--ctorigdstport 53` and for containers by `--dport 53` (raw has no connection tracking yet): Google's resolver is its metadata server, AWS's 169.254.169.253.
- The firewall keeps a project user's processes off the host's own addresses, never its containers: a container reaches what the host listens on beyond loopback, as on any Docker host, since an INPUT rule refusing bridges would refuse a site's call to another on its server (a container on Traefik's network is not DNATed, and on older Docker none is); `--server-info` names those listeners (`DoorListeners`), sshd's and `docker-proxy`'s aside, and a host service containers must not reach listens on 127.0.0.1.
- On loopback, which the host's own addresses go out through (its sshd included), the firewall lets through only a resolver, by the port first asked for (`--ctorigdstport 53`, as Docker's own at 127.0.0.11 is moved by a NAT), and the answers to a connection another made (a sync's forward is the project user's sshd).
- One loader, its unit and install serve the door and a server with no door (`FirewallLoader`, `FirewallInstall`, by whether a door is there), so the two never disagree: the door's chains, groups and Docker drop-in are the door's alone, `--server-setup` loading them too where `door:` is set or the door's is loaded.
- The firewall's rules are written as `iptables -S` prints them (`firewallRules`), so the lines loaded (`FirewallLoader`, `iptables-restore --noflush` of devopsy's chains alone) are the lines checked (`FirewallWrong`): a chain differing, or a rule ahead of a jump that is neither a DROP nor a REJECT, is wrong.
- Docker's daemon has a chain of its own (`DoorDaemonChain`), jumped to by its cgroup (`daemonCgroup`: `docker.service`'s under systemd, before it starts too, else the running `dockerd`'s; none for the root cgroup, every process's): no new connection of its to the host's loopback or a metadata address, DNS aside: it contacts no registry a project names, and the chain still holds what it does reach (the util image's build, a builder's first boot, the deploy user's own pulls, which reach no registry on the host's loopback). Never the host's other addresses: traffic to them goes out on loopback too, and a registry on this server is reached by its name or Docker's bridge.
- `add` loads and checks the firewall first, as root through the util image with the host's network, processes and cgroups and `SYS_PTRACE` (`doorFirewall`), without which a host hiding other users' processes (`/proc`'s `hidepid`) shows it no `dockerd`, and refuses when it is wrong; `FirewallUnit` loads it at boot, after what loads a whole ruleset and before the network's services, the daemon's jump waiting for Docker's cgroup, `FirewallDockerDropIn` at every start of Docker, in its new cgroup, since a cgroup's rule binds the cgroup there when it goes in and `--server-info` tells one made since (`DoorFirewallDaemonMark`); the install loads it through `FirewallUnit` where `systemctl` reaches systemd from the chroot (`SYSTEMD_IGNORE_CHROOT=1` and the host's pids), else runs the loader itself (internals/server-setup.md); nothing loads it again in between; `--server-info` reads it the same way, the groups' ids with it, as the loader reads them: the deploy user can neither read nor change iptables.
- The `firewall` request takes no argument and answers only right, wrong or unknown (`doorSide.firewall`, `firewallAnswer`): the deploy user's read of the chains as root, devopsy's fixed script on a read-only root (`firewallReadRun`), nothing of the caller's in it, for a project user's release and `--server-info` to pass W0001 on to the admin (internals/server-setup.md).
- Docker's `userland-proxy` stays on: the loopback's REJECT stops a project user's packet before `docker-proxy` reaches a published port, and turning the proxy off drops IPv6 visitors to IPv4-only containers.
- `<space>` is on a mount of its own with `nosuid` and `nodev`, or the door refuses every request (`spaceGuarded`): a container's setuid file or a crafted tar there otherwise crosses projects, or reaches root.
- A project user's `shared/mnt` is a link into `<space>`, made at a release's start (`--mnt-ready`), and a compose name comes from where an environment is in that user's tree, never from a caller (`Policy.NameOf`).
- Entries are made by the door, so a project user can write inside one and never replace it: when devopsy's own mkdir is refused (`makeEntry`), and what a file binds, at `compose config`, since a step writes in an entry before anything starts (`entries`), and at `up` (`bindEntries`).
- What a root util container writes in an entry is given back to the project user as `rwX` when it exits, or when it is removed for one detached (`Regrant`, `Removes`, `regrant`): a tar's or an rsync's mode on a file with an ACL sets its mask, which narrows the project user's entry, and only an owner or root changes an ACL, so a root util container does it, touching only what lost its group class's write.
- An entry the door made a directory, not knowing it is a file, is replaced while empty: the two are told apart only by an import or a sync.
- A service is on its project's own networks, a joinable one or none, never Docker's default bridge (`network_mode: bridge`): every service with it shares docker0 and reaches the others' ports there.
- A project's network has no IPv6 (`enable_ipv6` refused), its address space Docker's: fewer paths across the server to keep shut.
- A network's boolean keys are JSON booleans (`notBool`), never a word compose also reads as one (for example `"yes"`): the rules would read the word as false.
- A service on a shared network is named `<project>-<name>` (`OwnName`), and holds no alias or fixed address there: compose makes each service's name an alias on its networks, which would answer for another's name (for example `traefik` on `tunnel`).
- A listing is cut by container id, never by trusting a caller's filter: filters of one key widen each other.
- The door acts only on containers it made for the asking user (`devopsy.door`, `door.DoorLabel`, on every service it runs and every util container), and runs no compose command while a container it did not make is under the project's names (`Policy.Foreign`): compose's and devopsy's labels are anyone's to set outside it, and such a container runs as root with any mount.
- Of another project's labels, only its role, compose project and exports are ever read (`exportedLabel`).
- A container's name is the project's own (`Policy.OwnContainerName`): a compose name of its own, or devopsy's `devopsy-<word>-<compose name>-<part>` of one of its environments, since a name of another's, or of none, could take the name another project's next container needs.
- A util container is one of the forms in `internal/door/forms.go`, its command, its arguments and its mounts checked together (a script with arguments with `sh` for its $0, so each is checked where the script reads it), never one a caller gives: it is root on the host's files, and a command paired with another's mounts writes where a bind goes by.
- A new util container gets a form and a line in `TestDoorTakesWhatDevopsyRuns`, which runs devopsy's own against a fake docker: else a project user's release fails on it at runtime.
- An rsync that names a whole mnt holds only the entry it writes (`narrow`): what it copies could otherwise leave a link where a bind's source goes by.
- A word in a util container's arguments never starts with a dash: `find "$@"` would take it as code.
- A Docker command devopsy calls has an answer here, or a reason in `doorVerbs` (`TestDoorKnowsDevopsysDockerCommands`, which sees `exec.Command`'s and scripts' lines, not a helper's).
- An image's own labels under `devopsy.` or a vet's prefix refuse it, what a service builds included, by devopsy's name for it: they land in its containers' labels, past any check of a file's, and an image not here yet is claimed first so they are read.
- A start runs the image the door read: compose never pulls or builds one then (every service of the file it runs holds `pull_policy: never`, written before the vet reads the file; a project's own `pull_policy` only `missing`, `never` or `if_not_present`; `--pull` only `never`, since `missing` overrides the file's), and an image gone since its claim fails the start.
- Compose runs with `DOCKER_CONFIG` an empty directory of the door's, `<space>/docker-empty` (the deploy user's, mode 555), for every verb but a build: unset, it reads the deploy user's own `~/.docker` (`doorEnvironment` sets HOME there), its logins, credential helpers and plugins.
- A start names an image only the project writes (its build's, a hold of its own) or devopsy's util image by the id the door read (`image: sha256:<id>`), never by its name: the project's build or tag in another environment moves it before compose's create, and no lock is held, so a one-off container's `run` holds up nothing for as long as it runs.
- A start names any other image by its digest, `<image>@<digest>` in the file compose runs (`startImage`, `images.Pin`): a name not only the project's is anyone's on the server to move (a registry moving a tag another project pulls, the deploy user's build of a registry's name), and only a digest withstands that. An image it claimed by its id, or that carries a name only it writes (a build's or a hold of its own), goes by its digest in the repository of the name asked, read in one inspect, as the `devopsy.digest` label chooses it; any other by the digest its claim loaded; one with no digest is claimed, else refused, never run by its plain name.
- An image is a project's when only it writes one of its names (its build's; a hold of its own) or when it claimed it (`door.Policy.OwnsImage`); any other is claimed before a start runs it, an inspect reads it or a tag takes it as a source (`Action.Claims`, `doorSide.claim`), so an image another project pulled with its own logins, or built, is never this one's by being on disk, and once claimed a start asks the registry nothing. A claim reads one image manifest's digest with the project's logins (`platformManifest`, the ref's own manifest or its index's entry for the daemon's platform, itself a manifest, a ref by digest, an index's too, only as those bytes, each read bounded in size and time); takes the image as it is when that digest, in the repository asked, inspects to an id the project recorded; else copies the registry's bytes of it with the door's client into an OCI layout in a work directory (`copyImage`, `buildx imagetools create --prefer-index=false`), checks that every blob the manifest names is there, a regular file, its hash and its size (none below 0), and that each layer is of a kind containerd pairs with a diff_id (`layerKinds`) and its content, decompressed as containerd unpacks it, the one the config names by position, a blob named twice read as each kind it is named (`checkLayout`, `layerContent`, streaming each: a layer may be larger than the door's memory), and loads a tar the door writes of those blobs alone, its own index naming the manifest by its canonical name (`loadImage`, `images.Canonical`), so Docker's daemon contacts no registry a project names, and on the containerd store the load leaves what a pull by digest does; Docker skips a blob its store holds without a word, so a copy missing one would load an image of another's blobs, and a load lands on the layers the server holds for the config's diff_ids without unpacking them, so a config naming another's over junk would run another's files. A load succeeded only when it exits 0 and says exactly `Loaded image: ` and the familiar name (Docker says an unpacking error on stdout and exits 0); a failed one records nothing, removes nothing and drops the digest from the record, and an image that loads under another id than that digest is refused; a copy that fails touched no store, so leaves the record as it was. The id is then recorded in `<space>/images/<user>` (`Policy.ImagesFile`, under a lock, by rename), and what the request runs takes it by that digest (a tag's source, an inspect's target; an own one by the id the door read, unless it is a name only this project writes). The builders' registries, CAs and mirrors are the admin's, `<space>/buildx/buildkitd.default.toml`; the door's client, the read and the copy, takes a builder's mirrors and plain http from it (the builder made, never started), and trusts the host's CA store, never a CA file a builder's config names. A claim, and the pull verb, never writes a name a project alone writes (`Claimable`), its own included, a hold or a build's name, which the door then takes as the project's with no claim. Any other name is a registry's, a name under another project's included. devopsy's util image is the server's own.
- Compose's pull verb is the door's own claims for a project user (`doorSide.pull`, `door.PlanPull`), never compose's pull: the services named, else those compose's own config takes as active under the profiles, dependencies only with `--include-deps`, skipping a service with no image, with an image of the project's own (`OwnRef`), with its `pull_policy: never`, with `missing` or `if_not_present` one whose image the project has (`OwnsImage`), as compose skips one it has, and with `--ignore-buildable` one that builds; every refusal of the file comes before the first claim, a claim its registry fails (`registryFailure`: a tag, a platform or logins it does not serve) is said and unlogged, ending the pull with 1, or with `--ignore-pull-failures` every one said as a warning and 0, and a claim the door refuses for what was served ends it as a refusal, logged.
- A door project's build is named `devopsy.internal/<compose name>/<service>` (`images.DoorBuild`), whatever `image:` says, by the render and by the listing (`ParseComposeConfig`, since a project user's `compose config` runs unrendered), and holds no labels of its own: a name without a host is a registry's, which another project may pull and run, and `.internal` is reserved for private networks, never a public registry's.
- The door runs under a group of its own (`remote.DoorRunGroup`, `devopsy-door`, no user in it), its effective one through sudo's `-g` (`sudoArgs`), and refuses to run under any other (`doorGroupHeld`); the firewall jumps from that group to a chain of its own (`DoorRunChain`, `DEVOPSY-DOOR`: the host's loopback, the metadata services and Docker's bridges refused, DNS aside, the host's other addresses its to reach as the daemon's) (`firewallJumps`): every registry client the door starts on the host (a claim's read of a manifest and its copy, compose's and buildx's for a build, whose token BuildKit asks its client for) answers a registry the project user names, which can send it to the host's loopback or a metadata service, so all of them are held by one rule, never each moved into a container.
- A build holds only `args`, `context`, `dockerfile`, `no_cache`, `pull`, `target` (`buildKeys`), and `additional_contexts` only as another service of the same file that builds (`checkContexts`, `service:<name>`): that build runs on the project's own builder from its own release, while a path is read by the client with the deploy user's rights outside the sealed context, and an image (`docker-image://`) is fetched by the project's builder past a claim.
- A build with contexts runs only on a compose that reads `service:<name>` as another service's build (2.33.0 on, `composeKnowsServiceContexts`), read under the build's own environment (Docker finds compose in `$DOCKER_CONFIG/cli-plugins` first) and refused when its version cannot be read: an older one reads it as a path in the project's directory, the project user's to make, and its client reads it with the deploy user's rights.
- What compose's client opens in a sealed context as the deploy user, the Dockerfile and its ignore files, crosses no link on its way (`Within`, after `Seal`): a copy keeps the links it holds, and a directory the project user turned into a link between the check and its tar would read any file that user reads, its lines coming back in BuildKit's parse error.
- Every build the door runs has no git of the deploy user's (`BUILDX_GIT_INFO=false`, `BUILDX_GIT_LABELS=false`, in `builder`'s environment): buildx's client asks git about the context, a sealed copy is the deploy user's own, so git trusts the repository config the project user put in it, which can name a program it runs.
- A build lands where a start then reads: on devopsy's name for it, or on its release's bookmark of that name when devopsy's own file names one (`ownHold`); a pull leaves out a name of the project's own (`OwnRef`: a bookmark, a hold, a build's name), never refusing the whole pull; a tag goes onto a hold of its own only, the one name devopsy tags.
- A door project's record fails on a build it cannot read by devopsy's name for it (`entries`, strict), as any project's does without its fetch tag: its start would otherwise run whatever that name holds.
- A service sharing a build's image behind the door (an `image:` with no `build:`) is not one of the project's own: the door renames the build, never the sharer, so it builds with the same context instead.
- Every name a container answers for on a shared network is the project's (`checkAliases`): its service's, no alias, and its hostname, which Docker's DNS answers for there too; no domainname.
- A container request goes to Docker by the full id the check read (`ownContainerID`: inspect, rm, a sync daemon's exec), never the caller's word, a name or an id's prefix Docker would resolve again.
- The door catches its caller's terminal stop signals until it execs (`doorStops`, `holdStops`), never ignoring them: one held between a check and its use would stretch every window between them, and an exec resets a caught signal to its default, keeping an ignored one ignored.
- An entry's owner (the owners form) is held as a container's user is (`userRefused`): never root's or an id of the host's.
- A network's labels, as a volume's, are never compose's or devopsy's.
- devopsy refuses a first word that only starts like a door flag, and any call through sudo from a member of the project users' group that is not the door (`inDoorGroup`), before it reads a project: sudo matches `--door *` against one string, a wildcard across words, so one argument "--door x" passes it.
- On a shared network a hostname, as a service's name, is a lowercase name of the project's: Docker's DNS reads any case alike.
- `add` clears a project user's linger (`/var/lib/systemd/linger/<user>`), as it denies cron and at, and so does every end of its processes (`remote.EndUserArgs`): a user manager running with no session, and its units at each boot, would outlive a key's removal.
- A build runs on the project's own BuildKit, `devopsy-<project>` (docker-container driver, made at its first build, `builder`), on a network of its own, `devopsy-<project>-build` (one made otherwise is made again), its settings in `<space>/buildx`: on one builder, cache mounts are shared across projects by their id, so one project's build would fill a cache another's trusts, and on Docker's default bridge a build step reaches another project's builder and what its build listens on. Its `FROM` comes from a registry or its own stages, never the server's store, which that builder does not see.
- The deploy user is who owns the binary (`deployUser`): an install of it as root would point the door at root.
- A container runs as `<uid>:<gid>` in numbers, never 0, the deploy user's ids, the door's users' or the socket's group (`hostIDs`), nor an id of the project users' range (`door.ProjectIDMin` to `ProjectIDMax`, 50000 to 59999), which `add` gives a project user and its group (`projectIDRange`), for a service's `user:` and `exec -u` alike (`userRefused`): a name is the image's to map to 0, and a host id is that user's to reach through `/proc`.
- The door's `uids` and `free` requests are a release's uid lookup and a `--destroy`'s last step (internals/uids.md); a start's locks are taken in the compose request, before its checks, and handed to compose at the exec.
- A container runs only as the claimed uid of the environment the request's directory is of, or its project's, uid and gid the same number (`Policy.UIDs`, `dirOwners`, from the claims read once a request, `doorSide.claims`), never one the file's name picks: a compose file is its branch's code, so it never takes another environment's uid, nor another tenant's (internals/uids.md).
- An owner devopsy gives a project's data (the owners form, the volume owner form, an rsync's `--chown`) is one of the project's claimed uids (`Policy.ProjectUIDs`), uid and gid the same.
- `add` closes the deploy user's projects in the release root (`closeDeployProjects`), as every release keeps its own (internals/releases.md): a project user enters a root of its own to reach its tree there, and reads nothing of the deploy user's.
- A volume's labels are never compose's or devopsy's (`reservedVolumeLabel`), in a file's volumes and the door's volume create alike: they say whose a volume is and what holds data.
- A project user is named for its project, and every name of what is the user's comes from the project in one place (`internal/door/names.go`: `UserOf`, `BuilderOf`, `BuilderNetworkOf`, `LoginsDirOf`, `ImagesFileOf`), an entry named otherwise refused where it is read (`decodeDoorUser`): a name computed from the user in one place and the project in another drifts apart, and a key's removal then misses the builder whose caches it drops.
- The project user's answer of where a path ends (`Real`, its read being its own process) is taken only absolute and clean: a `..` read lexically means another place to the kernel through a link the user made.
- A request acts on the user's behalf only while the user is as it found it (`stillAsked`: the same keys file, a key left, no end pending), asked at the request's start, before compose or a request's Docker runs, before a sync key goes in and before what the door keeps for the user is written: a user's end renews its keys file and reaches none of the door's processes, so a request past its sudo (one held on a registry's copy for days) acts no further.
- A name a project gives an image reaches the door's clients only as one of Docker's (`images.IsReference`, first in `Claimable`, which every claim runs): buildx's imagetools reads more (`oci-layout://<path>:<tag>`, a local layout it makes when it is not there, and `docker-image://`), and would read, copy or make any path the deploy user may.
- Every bind the door passes has `create_host_path: false`, and a util container's host binds go as `--mount`, never `-v`: the door makes what it binds before compose runs, so a source gone since fails the start, never binds an empty directory Docker made.
- A whole project's `down` by name runs from `/`, compose finding no compose file there or in a parent.
- A project user's compose reads `-h` and `--help` as compose's only among compose's own flags, the global ones before the verb and the verb's (`composeHelp`): past exec's or run's service they are its command's, which goes to the door.
- No pull or login of a project user's names a registry at the server's loopback (an address, `localhost`, `.localhost`), link-local, unspecified or a metadata address, in any case and in any spelling a C resolver reads as an address (for example `Localhost`, `127.1`, `0x7f000001`), a first part with a capital read as a host as Docker does (`ownHost`, `registryHost`, in `Claimable` and `LoginRegistry`): a claim's clients contact it for the project, the project's builder among them, which no chain of the door's group holds. The metadata addresses are one list (`door.Metadata4`, `Metadata6`), the firewall's too.
- A project user has no subordinate ids (`useradd -K SUB_UID_COUNT=0`, any listed for it removed at `add`): with newuidmap on the host, a user namespace mapping them takes its process out of its groups, and so past the firewall, which goes by its group.
- A server with project users needs `sudo`, `acl`, `<space>` on its own mount and a current Docker (its containerd image store and buildx 0.33.0 or later, `doorHostReady`, which `add` and a claim refuse without and `--server-info` warns of), the admin's; `--project-users add` puts the rest on the host, all of it devopsy's own interface (`DoorHostScript`): the `devopsy-projects` and `devopsy-door` groups, the two sudo rules (`%devopsy-projects` to the deploy user and `devopsy-door` for `devopsy --door *`, the deploy user to them for `devopsy --door-read *`), sshd's drop-in and the root-owned script it runs, and the `docker` link to devopsy, refused over a real `docker`.
- devopsy never mounts `/proc` with `hidepid`, the host's hardening being devopsy-server's setup's; it reads it from `/proc/mounts` as the deploy user (`procHidePID`, `invisible`, `ptraceable` and `noaccess` hiding, by name or number, `processesHidden`) and warns in one wording (`processesShownWarning`), in `--server-info` where the door has users and in `add`, never refusing: a project user otherwise reads every other user's command lines.
- Each host piece lands only when missing or different, and only after its check (`visudo -c`, `sh -n`, `sshd -t`, with the old drop-in put back on a refusal): a broken sudoers file breaks every sudo on the server, and a broken sshd config every login.
- `add` checks what sshd resolves for the project user (`doorSSHDTakes`, `sshd -T -C user=...`), devopsy's keys command as the deploy user and no file of keys, and the drop-in's login settings (no `~/.ssh/rc`, no forwarding), which an earlier Match would set first, before its entry is written: a `sshd_config` with no Include of `sshd_config.d`, or with it below a Match, parses and leaves the user on its own `~/.ssh/authorized_keys`.
- A project user has no cron or at jobs (`/etc/cron.deny`, `/etc/at.deny`): they run with no session, so a leaked key's job would outlive the key's removal.
- `--server-info` lists a project user's environments as that user (`--door-read environments`, `treeEnvironments`), its tree wherever it is (`doorTrees`), walks itself no project directory it does not own (`ownedByMe`: a removed user's tree, one named by another spelling of the root), and only those its project and devopsy's names allow (`envPathIn`): the deploy user never walks a project's tree, and that user writes what the read answers, which a hint offers as a command.
- devopsy's path goes into sudoers, which has no quoting, so `add` refuses one sudo would read as more than a path (`DoorDevopsyPath`), and into the keys command quoted.
- That path is the running binary's own, links resolved (`devopsyPath`), in `add` and in every call through sudo: a deploy user and its project users run one file, and a devopsy a PATH finds first would name a path sudo's rules do not.
- sshd takes the drop-in at a reboot, never a reload by devopsy (`DoorRebootMarker`, `/run/reboot-required`): a reload names sshd's service, which differs per distribution (`ssh`, `sshd`).
- `add` refuses while the deploy user or root is in `devopsy-projects`: sshd would ignore their own keys for devopsy's, and once sshd has the door, that locks them out at once.
- `add` takes a Unix user only when it made it (`doorUserCheck`): one there already and not in the group is someone's account, the deploy user's if it is named `devopsy-<project>`, which the group would take from sshd's own keys and put behind the firewall.
- `add` refuses while a container the door did not make is under the project's names, and a tree that is there and not the project user's (`doorTreeCheck`), before it makes anything: either would hand that user what another made.
- Every script of the deploy user's on an environment whose compose name is under a project user's names stops before it changes anything (`--release-settings <project> <compose name>`, `basePrelude`'s first call, `doorNameOwner`, the door's own `OwnName` among the server's projects and the target's): compose acts on a project by its name alone, so the deploy user's `--destroy` takes that user's containers and volumes down, and a release of it would make the door refuse that user's every compose command.
- `add` refuses a project name that extends another's on the server, or another extends (`projectNameClash`, over the door's users and the release root): compose names are flat, so whichever came first would hold the other's networks, volumes and containers.
- What `add` writes in a project user's home is written as that user (`runuser`), and only when the user is new: root writing in a home its user owns follows the links that user put there.
- `remove` marks itself and its end (`remote.DoorRemovingFile`, with the project, and `remote.DoorEndingFile`) together with the entry's and the keys' removal under the keys' lock, a key's removal clearing only its own mark; a removal asked again, or a listing or an edit of the user's keys (`keysSettle`, the end flag's `finishPendingRemoval`, its entry included), finishes what the marks say, and the project users' listing warns of one; sshd takes no key of a user whose removal is pending and no sync key of one whose key's end is (`authorizedKeysOf`), `add` refuses while either mark is there, and a user under `door: users:` is removed the same, its config line named for the admin to drop; a new write of a removal or a new way to settle one gets its step in `TestRemovalCuts`, which builds every state a cut leaves and settles it every way; it drops a project user's entry, keys and sync keys, and what the door kept for it (its registry logins, its claimed images' record), under the record's lock (`removeKept`), which the door writes them under only while the user has a key (`whileAUser`), so a request past its sudo before the removal brings neither back; never its Unix user: deleting a user that holds a tree and data is not one subcommand's.
- The door lifts the file size limit its caller hands it through sudo, and refuses to run under one it cannot lift (`doorLimits`): its append to the refusals' log would fail without a word.
- A door killed mid-way leaves its work directory for the next request's sweep, a compose request's included, a day on (`sweepWork`); a claim cut by SIGINT, SIGTERM or SIGHUP, in its read, copy or load, kills its child's process group (the docker CLI and its buildx plugin), starts no other and removes the request's work directories, its own among them (`claimCut`), since a release cancelled mid-fetch would leave a whole image there.
- A root container holds no path a project user can change: input is copied in and output collected by that user's rights, and a restore streams through a container with no mounts.
- Every util container the door runs holds `--pull never` (`door.UtilNoPull`, in `RootUtil` and the restore's stream): its image is the deploy user's build, and one gone would be the daemon's to pull from a name the network's DNS answers.
- A root util container writes nothing of its own (`door.RootUtil`: a read-only root, a small `/tmp` that runs nothing, the sync daemon's settings there): a link a project user swaps mid-copy would lead a write into the container's files, which a later step of the same container then runs.
- A project's registry login reaches compose only for a build, and the door's claims, as its `auth` values alone, in the door's own directory, written once per request (`logins`): Docker's CLI loads plugins and helpers from a `DOCKER_CONFIG`, which would run the project's program as the deploy user.
- A project user's `docker login` is saved by its own devopsy and checked by nothing (`doorLogin`): it writes `auths` as user and password (never an identity token, which the door's claims do not read), under the key a claim looks up (`loginKey`, `door.HubLogin` for Docker Hub), and says it is not checked, with no `Login Succeeded`; the first claim checks it, in the registry's words, since a check by Docker's daemon would contact the registry the project names.
- A login's password never comes on a command line (`-p` refused): it comes on stdin or at a prompt (`readSecret`, the terminal put back on an interrupt).
- A login's registry and user are written only as values (`door.LoginRegistry`, `door.LoginUser`): a host and port, or Docker Hub's key, and one word.
- A rendered file holds only `$$`: compose interpolates what it reads, after these checks, so a `$` not doubled refuses it (`variableIn`).
- A util container's mounts sit only where devopsy's own commands look (`mountTarget`), and its sources hold nothing of `--mount`'s or `-v`'s syntax (`mountSource`).
- `<space>/mnt/<name>` and `clones/<project>` are closed to every other user, and `sealed/<project>` to all but the deploy user, whatever modes a container gives its files.
- Nothing stays in `<space>/work` after its container or its claim, and sealed copies go once no container holds them, an hour old (`pruneSealed`).
- A compose name is a project's only while no other project's name extends its own, on the server's list and in its release root (`Policy.OwnName`).
- A secret reaches the door and a container by name, its value on stdin: a command line shows to every user of the server.
- The door's environment is its own (`doorEnvironment`): a caller's PATH would choose its docker, and a HOME the config it obeys.
- The address the caller's session carries for its hints is read before the door clears its environment (`doorEnvironment`, `remote.SessionFrom`, which drops one over its cap or that parses as no address) and used only as a remedy's command (`doorSide.asked`), never in a decision or the refusals' log: its caller sets it, so a forged one reaches only that caller's own messages.
- The door's sudo rule keeps only the address a session carries for its hints, in its two forms, by name (`Defaults!DEVOPSY_DOOR env_reset, !env_keep, env_keep = "...", !setenv`, `doorKept`), never the operator's command, which no hint of the door's gives, and the read's as a project user none of its caller's variables (`Defaults!DEVOPSY_DOOR_READ env_reset, !env_keep, !setenv`; a read runs as the project user, who reads its environment through /proc), whatever the server's sudoers keeps for others (`doorSudoers`), a command's Defaults, which sudo applies after every user's, group's and run-as user's: Go's runtime reads some (for example `GODEBUG`) before `doorEnvironment` clears them.
- The door rewrites the file compose runs (a build's block and name, sources pinned or sealed, images pinned to a digest), which `devopsy -- config` does not show, a server with project users needs more than Docker, devopsy and a few tools (its containerd image store and buildx 0.33.0 among them), and compose's pull verb is the door's own, its flags and its words: all accepted, against their Principles, for a project user only.
- Of the image store, only a hold or a build's name of its own (`OwnRef`) is a project user's to remove or to tag onto (a record bookmarks its builds), never another project's hold under a repository it names: a plain name may be others', a hold is its project's reference to the image it runs, and `image prune` is server-wide, so a removal of any other does nothing for it and a tag onto one is refused.
- `devopsy` and any name under `devopsy-` are no project's (`projectNameClash`): devopsy's own names are under them (its util image, the project users, their group, the builders).
- Nor is a project whose user would bear the name of a group of devopsy's (`projects`, `door`): `useradd` gives a user a group of its own name, which would put the door's files, or sshd's and the firewall's match, on that user's group.
- A reflink clone lives in `<space>/clones/<project>`, on the data's filesystem, reached through a link in the project's tree: it holds other uids' files, and the project user reads it and cannot change a part of a path to it (`cloneDirReady`). The door's clone, mark and removal take only a clone's directory or a take's in it (`CloneDir`), never a path inside a copy, whose directories keep the project user as their owner.
- A sync's rsync daemon has no network, and the door takes only `exec -i` of `DaemonServe` on a container it made; a sync's receive has none either, its rsync over its session (`known.Receive`) into the one entry or volume mounted: no form takes the host's network, so no util container reaches a port of the host's.
- The door sets its own umask: a caller's comes through sudo.
- A rendered file goes to compose as an unlinked file (`unlinkedFile`), so nothing of a project's environment stays on disk.
- What the door refuses goes to `<space>/refused.log`, a vet's refusal too: a real release asks for nothing refused, and `image prune`, the admin's, does nothing here.
- Labels under a `door: vets:` prefix go to the admin's program, the rendered file on stdin and the project in `DEVOPSY_DOOR_PROJECT`, and exit 0 allows: devopsy knows no URL (Principles).
