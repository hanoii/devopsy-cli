# The door's history

History, not rules: `internals/door.md` wins where they differ.

- Docker's socket is root, so a leaked deploy key was the whole server. A policed socket came first, tried and reviewed: one round found about 33 ways through, most from forwarding JSON the daemon read differently. Compose also acts as whoever runs it (`env_file`, `extends`, `provider`), which no socket sees. So the file is rendered by the project's own user, with its own rights, and checked before compose runs it.
- Moving the scripts to the server first was weighed and put after: the door works with them as they are, and a key that may release runs a project's steps on the host either way.
- The first version kept the project's tree the deploy user's, which makes every write a request. The project user owns it instead, and nothing the door does trusts it. Daemons resolve a bind at each start, so pinning came from a swapped link reaching another project at a restart, in a test with its control.
- `nosuid,nodev` came from reading the door as an attacker, then testing: a container's setuid file reached another project through `/proc`, and a crafted tar gave root on the host.
- Two review rounds, on Opus and Fable, found what the door's own attack rows had missed. The first: mounts over a util image's binaries, a second `--mount` source, variables compose expands after a check, keys in other forms, a world-readable space. The second: still more routes to root, from checking a util container's command and mounts apart, after named requests had been put off as adding nothing. So a util container became one form of a table, its command, arguments and mounts together.
- A password written to ssh's stdin raised SIGPIPE when ssh exited first, which `interruptible` takes for the session's end: first blamed on load, until the same test on `main` passed every time. Hence a pipe filled before ssh starts.
- Firewalling all private ranges broke a sync over a private network, found by the first end-to-end run of it: only Docker's pools were blocked. That still refused a peer inside them, as on GitHub's runners, whose test server sat in the daemon's `172.16.0.0/12` (and AWS's default network is inside Docker's default pools): the rule now goes by the interface traffic leaves through, Docker's bridges, not by address.
- A third review, an attack round on Opus and Fable, found that what the door checked was not always what ran: compose took an image's tag again after its labels were read (a pull policy, `--pull`, a build of the same tag), and compose's own alias for a service's name answered on a shared network past the alias check. It also found `exec -u` held apart from `user:`, an id filter in another spelling, and a take named `mnt` in a clone, which let a root container follow a project's link to a root-only file. Hence starts that neither pull nor build, the image lock held into compose, one check of who a container runs as, and service names on shared networks that are the project's. The shared BuildKit's cache mounts crossed projects too. A builder per project was chosen over requiring prefixed cache ids, which would make the door parse Dockerfiles exactly as BuildKit does, the same shape as the policed socket that fell to about 33 attacks. It was kept without a setting, since sharing it undoes the door's promise.
- Why a door at all, as argued after the third review. On a deploy user in the docker group, a leaked project key is root on the server for nothing; through the door, an attacker needs a bug in it. Whoever can talk to one shared, rootful daemon is root, so as long as projects share a daemon, something has to decide what each may ask: a policy cannot be avoided there, only kept small. Isolation by construction means a daemon per project, and that was weighed and set aside: rootless Docker breaks one Traefik across projects and costs about 120 to 140 MB per idle daemon, and a VM per project is a separate server, which is already the answer when a project needs more.
- Why the door and not the policed socket. The socket's policy read Docker's API, JSON the daemon read another way (most of its 33 routes), and could not see what compose does as whoever runs it (`env_file`, `extends`, `provider`). Its surface was the whole API, exec, attach and builds' streams included. The door checks one rendered file, deny by default, runs compose on that very file, and answers only devopsy's own requests, its util containers a fixed table of forms. Its rounds' findings were mostly what was checked not being what ran (a tag pulled again, a name resolved twice, a path one level deeper), a class that closes by pinning what was checked; the socket's were parsing differences, which have no end.
- What the door costs, accepted. Every Docker call or compose key devopsy adds needs a form, a rule and a review, and some of what the door relies on is the host's (ACL masks, a firewall's ranges against Docker's pools, mount options, sudo), so a host unlike the tests' can break it where no local run shows it: two such failures showed only on GitHub's runners, one hidden by OrbStack's `docker exec` umask of 000. The maintainer chose to keep it, extend it and secure it as far as it goes, unless a way without a policy turns up that is neither rootless Docker nor a VM per project.
- A root copy's modes narrowing a project user's ACL was first fixed by a grant at each start, after the cause, walking every entry on every start; it moved to the copy itself, a form saying what it writes. Dropping instead the project user's writes in its entries from the host was weighed and kept: drupal11's maintenance flag and registry's htpasswd are written that way.
- The firewall was first three lines an admin added and `--server-info` looked for. An attack round found them counted behind an ACCEPT that let everything past, IPv4 only, holding a project user's processes but not containers off the metadata service, and blind to a port published on loopback, which `docker-proxy`, root's, reaches. It became devopsy's own chains, loaded by `add` and compared whole. Turning Docker's `userland-proxy` off, so that such a port goes by NAT through a bridge, was weighed and set aside: it drops IPv6 visitors to IPv4-only containers (Traefik's), is the whole daemon's, taken only when Docker restarts, and has Docker set `route_localnet`. Rejecting the project user's own packet on loopback stops it before the proxy, and covers the host's own services there too. That cut off a sync's daemon on loopback, which now has no network and serves over `docker exec`, relayed from the push's own socket. A block on project users reaching the host's sshd was dropped: it was for the agent, which syncs no longer forward.
- A review found a project's own names overlapping a registry's: anything under `<project>-` is a project's to build, and Docker Hub's official images share that space (project `mongo` builds `mongo-express:1`). Another project claimed and checked the name under its own image lock, then compose resolved it again at the create, so a build timed in between ran the builder's image with the other project's secrets and data; the deploy user's releases, which pull and then `up` by name, were open the same way. Starts were pinned to a digest, in the door and in every release's `devopsy-compose.yaml`, and the claim takes the digest from its pull: an inspect of the name after the pull, the first design, is itself the window, and on Docker's containerd store a built image has a digest in that repository too. A server-wide image lock was set aside (an attached `up` would block every project), as was a pin by id (an image removed in the window cannot be pulled back). Narrowing the names a project may build was measured and set aside at first: compose names prefixed by the project user's uid break the rule that a target's compose name comes from nothing else, and builds under a reserved `.invalid` domain were read as the door translating one name across every request. The pins left each reader of a pulled name to fix one by one (the release's record read the name seconds after its pull; a rollback's restore read what the name held at any time, a build placed hours before running there), and a person running by name stayed open. That reading was wrong: the door renders every compose call already, and the only other place a build is named is the listing, a project user's `compose config` running unrendered, so one function (`images.DoorBuild`) in the render and the listing names every door build under `devopsy.invalid`, and no project user writes a name a registry serves. That closed the cause, and took with it the refusal of a pull under another project's names (with a project `mongo`, no other ran `mongo-express`) and the build check on `image:`; the pins stayed, as cheap guards against a registry or the deploy user moving a name. The same change found a door project's rollback in build mode refused, its retag onto the build's name not a hold, untested since the door's end-to-end life ran in image mode.
- A review found a project user's detached process outliving its last key's removal and keeping the door by its group: logind leaves a user's processes running on Debian (KillUserProcesses off), and removing a key ended no session. Removing the last key, or the user, now ends its processes, and the door refuses a user with no key. The plan first matched them by the owner of `/proc/<pid>`; a process that makes itself undumpable shows root's there, so the kill runs as the user and sends `kill -9 -1`, which reaches every process the user may signal. busybox's `pkill` has no `-u`, which the first plan relied on.
- devopsy's container names were one namespace across projects (`devopsy-sync-<id>-daemon`, `devopsy-export-<pid>`), the door taking any `devopsy-` name with an environment's label: another project user could take a name first and fail that sync's `docker run`, availability only, since everything acts by the id run printed or by labels. Each name now carries its environment's compose name, from one constructor, and the door takes only its own; the label check that stood in for it went.
