# The door's history

History, not rules: `internals/door.md` wins where they differ.

- Docker's socket is root, so a leaked deploy key was the whole server. A policed socket came first, tried and reviewed: one round found about 33 ways through, most from forwarding JSON the daemon read differently. Compose also acts as whoever runs it (`env_file`, `extends`, `provider`), which no socket sees. So the file is rendered by the project's own user, with its own rights, and checked before compose runs it.
- Moving the scripts to the server first was weighed and put after: the door works with them as they are, and a key that may release runs a project's steps on the host either way.
- The first version kept the project's tree the deploy user's, which makes every write a request. The project user owns it instead, and nothing the door does trusts it. Daemons resolve a bind at each start, so pinning came from a swapped link reaching another project at a restart, in a test with its control.
- `nosuid,nodev` came from reading the door as an attacker, then testing: a container's setuid file reached another project through `/proc`, and a crafted tar gave root on the host.
- Two review rounds, on Opus and Fable, found what the door's own attack rows had missed. The first: mounts over a util image's binaries, a second `--mount` source, variables compose expands after a check, keys in other forms, a world-readable space. The second: still more routes to root, from checking a util container's command and mounts apart, after named requests had been put off as adding nothing. So a util container became one form of a table, its command, arguments and mounts together.
- A password written to ssh's stdin raised SIGPIPE when ssh exited first, which `interruptible` takes for the session's end: first blamed on load, until the same test on `main` passed every time. Hence a pipe filled before ssh starts.
- Firewalling all private ranges broke a sync over a private network, found by the first end-to-end run of it: only Docker's pools were blocked. That still refused a peer inside them, as on GitHub's runners, whose test server sat in the daemon's `172.16.0.0/12` (and AWS's default network is inside Docker's default pools): the rule now goes by the interface traffic leaves through, Docker's bridges, not by address.
- A third review, an attack round on Opus and Fable, found that what the door checked was not always what ran: compose took an image's tag again after its labels were read (a pull policy, `--pull`, a build of the same tag), and compose's own alias for a service's name answered on a shared network past the alias check. It also found `exec -u` held apart from `user:`, an id filter in another spelling, and a take named `mnt` in a clone, which let a root container follow a project's link to a root-only file. Hence starts that neither pull nor build, the image lock held into compose, one check of who a container runs as, and service names on shared networks that are the project's. The shared BuildKit's cache mounts crossed projects too. A builder per project was chosen over requiring prefixed cache ids, which would make the door parse Dockerfiles exactly as BuildKit does, the same shape as the policed socket that fell to about 33 attacks. It was kept without a setting, since sharing it undoes the door's promise.
- Why a door at all, as argued after the third review. On a deploy user in the docker group, a leaked project key is root on the server for nothing; through the door, an attacker needs a bug in it. Whoever can talk to one shared, rootful daemon is root, so as long as projects share a daemon, something has to decide what each may ask: a policy cannot be avoided there, only kept small. Isolation by construction means a daemon per project, and that was weighed and set aside: rootless Docker breaks one Traefik across projects and costs about 120 to 140 MB per idle daemon, and a VM per project is a separate server, which is already the answer when a project needs more.
- Why the door and not the policed socket. The socket's policy read Docker's API, JSON the daemon read another way (most of its 33 routes), and could not see what compose does as whoever runs it (`env_file`, `extends`, `provider`). Its surface was the whole API, exec, attach and builds' streams included. The door checks one rendered file, deny by default, runs compose on that very file, and answers only devopsy's own requests, its util containers a fixed table of forms. Its rounds' findings were mostly what was checked not being what ran (a tag pulled again, a name resolved twice, a path one level deeper), a class that closes by pinning what was checked; the socket's were parsing differences, which have no end.
- What the door costs, accepted. Every Docker call or compose key devopsy adds needs a form, a rule and a review, and some of what the door relies on is the host's (ACL masks, a firewall's ranges against Docker's pools, mount options, sudo), so a host unlike the tests' can break it where no local run shows it: two such failures showed only on GitHub's runners, one hidden by OrbStack's `docker exec` umask of 000. The maintainer chose to keep it, extend it and secure it as far as it goes, unless a way without a policy turns up that is neither rootless Docker nor a VM per project.
- A root copy's modes narrowing a project user's ACL was first fixed by a grant at each start, after the cause, walking every entry on every start; it moved to the copy itself, a form saying what it writes. Dropping instead the project user's writes in its entries from the host was weighed and kept: drupal11's maintenance flag and registry's htpasswd are written that way.
- The firewall was first three lines an admin added and `--server-info` looked for. An attack round found them counted behind an ACCEPT that let everything past, IPv4 only, holding a project user's processes but not containers off the metadata service, and blind to a port published on loopback, which `docker-proxy`, root's, reaches. It became devopsy's own chains, loaded by `add` and compared whole. Turning Docker's `userland-proxy` off, so that such a port goes by NAT through a bridge, was weighed and set aside: it drops IPv6 visitors to IPv4-only containers (Traefik's), is the whole daemon's, taken only when Docker restarts, and has Docker set `route_localnet`. Rejecting the project user's own packet on loopback stops it before the proxy, and covers the host's own services there too. That cut off a sync's daemon on loopback, which now has no network and serves over `docker exec`, relayed from the push's own socket. A block on project users reaching the host's sshd was dropped: it was for the agent, which syncs no longer forward.
- A review found a project's own names overlapping a registry's: anything under `<project>-` is a project's to build, and Docker Hub's official images share that space (project `mongo` builds `mongo-express:1`). Another project claimed and checked the name under its own image lock, then compose resolved it again at the create, so a build timed in between ran the builder's image with the other project's secrets and data; the deploy user's releases, which pull and then `up` by name, were open the same way. Starts were pinned to a digest, in the door and in every release's `devopsy-compose.yaml`, and the claim takes the digest from its pull: an inspect of the name after the pull, the first design, is itself the window, and on Docker's containerd store a built image has a digest in that repository too. A server-wide image lock was set aside (an attached `up` would block every project), as was a pin by id (an image removed in the window cannot be pulled back). Narrowing the names a project may build was measured and set aside at first: compose names prefixed by the project user's uid break the rule that a target's compose name comes from nothing else, and builds under a reserved `.invalid` domain were read as the door translating one name across every request. The pins left each reader of a pulled name to fix one by one (the release's record read the name seconds after its pull; a rollback's restore read what the name held at any time, a build placed hours before running there), and a person running by name stayed open. That reading was wrong: the door renders every compose call already, and the only other place a build is named is the listing, a project user's `compose config` running unrendered, so one function (`images.DoorBuild`) in the render and the listing names every door build under a host of devopsy's (first `devopsy.invalid`, then `devopsy.internal`, since an image name saying "invalid" reads as broken; `.internal` is reserved for private networks just as surely), and no project user writes a name a registry serves. That closed the cause, and took with it the refusal of a pull under another project's names (with a project `mongo`, no other ran `mongo-express`) and the build check on `image:`; the pins stayed, as cheap guards against a registry or the deploy user moving a name. The same change found a door project's rollback in build mode refused, its retag onto the build's name not a hold, untested since the door's end-to-end life ran in image mode.
- A review found a project user's detached process outliving its last key's removal and keeping the door by its group: logind leaves a user's processes running on Debian (KillUserProcesses off), and removing a key ended no session. Removing the last key, or the user, now ends its processes, and the door refuses a user with no key. The plan first matched them by the owner of `/proc/<pid>`; a process that makes itself undumpable shows root's there, so the kill runs as the user and sends `kill -9 -1`, which reaches every process the user may signal. busybox's `pkill` has no `-u`, which the first plan relied on.
- devopsy's container names were one namespace across projects (`devopsy-sync-<id>-daemon`, `devopsy-export-<pid>`), the door taking any `devopsy-` name with an environment's label: another project user could take a name first and fail that sync's `docker run`, availability only, since everything acts by the id run printed or by labels. Each name now carries its environment's compose name, from one constructor, and the door takes only its own; the label check that stood in for it went.
- A review found a claim proving only that a registry answered: Docker's pull fetches no blob it has, so a registry serving a manifest that named another project's private image, by digests from a CI log, landed the claim on it, its Env readable and its files runnable. A proof only when the image was on the server before the pull was weighed, then widened to the image carrying another name after it, and both dropped: Docker deduplicates per layer, so a config of the attacker's over the victim's layers pulls a fresh id with none of their bytes served, and no signal of the pull's (its progress words, shared sizes) tells reliably what came from the registry. So every first claim is proven on the project's own builder, whose store only the project fills, at the cost of a second download of what it lacks. A registry client in the door was the fallback, not needed: a fetch on the builder with a blob gone fails on it.
- A third review found a pull writing a name the door takes as a project's own: its own hold or build name, which an earlier change let a project pull, reasoning that it moved only its own image. It moved a name the door then trusts with no claim, so a registry's manifest naming another project's layers landed there unproven. No pull now writes a hold or a build's name, a project's own included; devopsy itself pulls neither (holds by digest, builds skipped).
- A third review found the kill run as the user stopped by the user: a process sending kill -9 -1 in a loop ends runc's init, which takes the uid before the container starts, and the key was gone with no retry. The kill now runs as root and matches each process by the credentials in its status, which a process that makes itself undumpable cannot hide (only its /proc directory's owner changes). The review also found that removing a key other than the last ended nothing, so a rotation never evicted what a leaked key left running: any removal of a project user's key now ends its processes, accepted though it cuts a session of another key's, which the next lock-taker settles.
- A third review found subordinate ids taking a project user past the firewall: `useradd` gives every user a range, and with the uidmap package on the host (rootless tools install it) a user namespace drops the process's groups, which the firewall matches. Project users get none. A firewall matching a cgroup instead of the group was the structural alternative, set aside while the ids are the only way out of the group.
- A third review found a project user reading the deploy user's projects under a release root of its own (a block volume): a release made its directories with the session's umask, and the root is every project user's to enter, their trees being there. Door trees moved to the project users' homes was weighed, leaving the root the deploy user's alone, and set aside for the cheaper fix with the same effect: a release keeps its project's directory at 700, and `add` closes those already there. A umask over the whole release was set aside: the upload unpacks as the deploy user, so a container's own user could no longer read a bind-mounted config.
- A third review found `add` adopting a Unix user it did not make, the deploy user included when named `devopsy-<project>`: its group check ran before the user joined the group. `add` now refuses a user outside the group; one it made, which `remove` keeps there, is taken again.
- A third review found the util image named `devopsy-util:4`, a name without a host, which any project user's pull could have written, while root containers run it by name: only Docker Hub's official namespace, which nobody can squat, kept it. It became `devopsy.internal/util:5`, under the door's build host, which no pull writes.
- An assessment after the third review found `--server-info`'s read as each project user running in the admin's session, its terminal still the controlling one: only sudo's `use_pty`, a host default devopsy neither sets nor checks, kept a process of that user's, which can trace the read, off the admin's terminal. Every `--door-read` now starts in a session of its own (`doorRead`). The same assessment found the names that read returns (an environment's directory, its `current` link) printed as they were, control characters and all, and pasted unquoted into an offered `cd`: devopsy now escapes control characters in every line it says or prints, and quotes such a path.
- An assessment after the third review found every project's builder on Docker's default bridge, a build step a member of it: one project's Dockerfile reached another's builder and any port its build opened. Each builder is now on a network of its own. OrbStack does not separate bridges, so only a Linux Docker shows it, as the end-to-end servers do.
- An assessment after the third review found the proof and the claim free to land on different images: given a multi-platform index, Docker's pull (the classic store prefers the CPU's amd64 level, keeps an entry with an empty platform, falls back to the next match) and BuildKit's fetch (plain amd64, the top match only) choose by rules of their own. The door now reads the manifest itself and picks the entry for the daemon's platform, checking it is a manifest by its bytes, and both pull and prove that digest, which the start pins. The proof exports the image's files rather than its blobs, so each layer is unpacked against the image's config: a lead the assessment raised, a second claim reusing the config a failed one left, pulling nothing and proving junk layers, needs that, and a failed proof now removes the reference its pull made. `RUN true` was set aside for the unpack: it needs a shell in the image.
- An assessment after the third review found the daemon a project user's deputy: a pull or a login made Docker's daemon, root and outside the project users' firewall, contact any host the project named, its loopback and the metadata address included, and pass back what it got (a port open or not, an error page, a request to any path through a registry's token realm). The door now refuses such hosts, which alone treats the symptom: a registry the project runs can still send the daemon there by a redirect, a realm or a DNS name, so the firewall covers the daemon's own traffic too (its loopback and metadata), at the cost, accepted, of a deploy user's registry or mirror on loopback.
- A fourth review found the image lock held into compose's `run`, for as long as the one-off container ran: a task or a shell left in one refused every start, build, pull and tag of the project's, in every environment, after ten minutes. The lock was there only so a build of the project's own could not move one of its names between the check and the create. Pinning those by the id the door read closes the same window with no lock, so the lock went; a pin by id was set aside before for a pulled image, which a removal in the window leaves nothing to pull back, and an own build is never pulled. A vet reads such a service's image as that id.
- The same review found the rule on the server's own hosts reading a host as written while Docker and a C resolver read more (a capital makes a first part a host, case does not matter, and a hexadecimal last label is an address), and a network's `enable_ipv6` taken as a word, which compose reads as a boolean: hosts are read in those forms, and a network's boolean keys only as booleans.
- The fourth review found a key's removal dropping the user's sync keys before ending its processes, the two files under locks of their own: what the removed key left running, or a door request already past its sudo, which the end of the user's processes does not reach, added a sync key after, alive for its two days. The removal now drops them after the end, under the sync keys' lock, and the door refuses an add once the user's keys file is not the one its request found.
- Once a release's builds landed under its own names (the build pins, merged from main), a service built on another's by its `image:` name stopped working, and compose's own way, the other service as a build context (`additional_contexts: service:<name>`), was refused behind the door with every other context. It is taken in that one form: the other service's build runs on the project's builder from its release, while a path is read with the deploy user's rights and an image fetched past a claim.
- The second pass of a hunt for holes found a claim's manifest read (`buildx imagetools`) a registry client on the host as the deploy user, outside every chain of the firewall: end to end, a registry's token realm on the server's loopback was fetched. The read moved into a container on the project's build network. buildx's client there took a builder's mirrors from its instance file but none of its CAs, only the system's trust store, which on the host had let the tests' private-CA registries through, so the host's CA bundle is mounted with it. A copy of the whole builder store was narrowed to the one instance file, under a tmpfs owned by the read's user, since the runtime makes a mount's parent directories as root.
- The same hunt proposed three hardenings, none shown as a hole, built after the claim's fix. Root util containers got a read-only root: a write a swapped link led into the container could be what its next step runs (an import's zstd branch runs `cat` after `tar`).
- The door's sudo rule got Defaults of its own: Go's runtime reads `GODEBUG` before `doorEnvironment` clears it, and an admin's wider `env_keep` reached the door, shown end to end with `inittrace`. The group's Defaults were tried first and lost to an admin's line in a later file, sudo 1.9 applying Defaults of one kind in file order, so they are the command's, which it applies after all others.
- A project user's linger, cleared at `add`, is cleared wherever its processes are ended too: set later, by an admin or a polkit that lets the user, it would start its units at the next boot after its key's removal.
- A review round after the hunt found the end of a user's processes, a scan of /proc killing each by pid, missing a chain that forks its next and exits at once: every member was gone when its status was read, the round killed nothing, and the removal said the processes were ended. The kill became one `kill(-1)` at the user's uid, from a process of devopsy's whose real uid is no one's, so the user's processes cannot signal it; busybox and dash drop privileges when the real and effective uid differ, so devopsy, a static binary, runs in the util image to do it. A cgroup kill of the user's slice was set aside: it misses a process in a `--door-read`, in the deploy user's session. The same round found `--project-users remove` dropping sync keys before the end and outside their lock, the key's script doing it after and under it: the two sequences, one in Go and one in shell, became one helper.
- The same round found `--debug imports` reading each running project's release where its containers' `working_dir` label pointed, a project user's word on a container the door made, through the links in its tree: it now leaves a project user's release unread and says so. Reading it through `--door-read` was weighed and left for a need: the listing is the admin's view of imports, and a project user's are its own.
- The same round found sshd running a project user's `~/.ssh/rc` at every login: a leaked key wrote one, its removal left it, and a kept key's next login ran it. `no-user-rc` on each key line was weighed against `PermitUserRC no` in the drop-in, which covers every key whatever prints it; agent, X11 and tunnel forwarding went off with it, devopsy forwarding none.
- The same round found a build's registry client on the host as the deploy user, outside the firewall: BuildKit asks its client for a registry's token, and compose or buildx fetched the realm a project's `FROM` named, the server's loopback included, as the claim's read had before it moved into a container. Moving each client into a container treated a symptom, one client at a time, so the door got a group of its own, its processes' primary one through sudo, which the firewall holds as it holds the daemon, and the claim's read came back to the host, the container's plugin lookup, CA bundle and builder's file with it.
- The same round found the ids a container may not take read at each check, the users there then: a project user made later took the next free uid, which a container already running could have (another project's, or one a project chose ahead), and read its environment and root through /proc. Project users now take their ids from a range of their own, 50000 to 59999, which no container of the door's runs as; `add` refusing a uid some container runs as was set aside, since a container started after it would take the same uid again. A per-project range of container uids, for the kernel's limits counted per uid (inotify instances, processes), was proposed and left for the maintainer.
- A second round found the end refusing to kill while any process ran at its own real uid, a check added with it: a project's service at that uid switched off every project user's end. The check went, since a process there is root's making or a build's step, the project's own, and the door refuses the uid for its containers.
- The same round found the end's container under Docker's AppArmor profile, which lets a container signal only its own peers: on a host with AppArmor on, its kills reached none of the user's processes, and the end-to-end servers, with none, never showed it. It runs unconfined, already root on the host's pids. Checked on a throwaway Ubuntu 24.04 server with AppArmor on and Docker 29.1.3: unconfined, the end ended a user's processes, one of them sending kill -9 -1 in a loop; under docker-default it failed after its fifty rounds with them running, and the kernel logged its signals denied. So before the fix, on such a server, no key's removal had ended anything.
- The same round found the door's group sharing the daemon's chain, which leaves Docker's bridges open: a registry's realm sent the door's clients to any project's container, a blind request and a port's state back. The door got a chain of its own that refuses the bridges too. The daemon itself still reaches them, by design: its cgroup holds `docker-proxy`, which connects to containers through the bridges, so a pull's realm can send the daemon there; refusing pull hosts inside Docker's pools would treat a symptom, and this is open for the maintainer.
- The same round found `--server-info` waiting with no bound on each project user's read of its tree, which that user's files can stall: one user kept the admin's view of the whole server from answering. Capping that one call would have treated a symptom, a path's resolution being as unbounded, so every answer from such a read goes through one helper, with a deadline where the deploy user waits outside the user's own request. The same round found `--server-info` offering `cd <tree> && devopsy --status` for a project user's environment, devopsy then running that user's programs as the deploy user: an environment read from a tree carries its user, set after the read, and its hint is the address of that user.
- A third round found two gaps in the end's sync keys: they were dropped after the end, so sshd took one for a login while it ran, and a door request begun after a key's removal but before the end found the keys file it checks unchanged by the end, adding a key past it. The end became one stretch under the sync keys' lock: drop, end, then the keys file written anew under a new inode, which no request's check takes for the one it found. A touch of its time was weighed and set aside, since a coarse clock could give the removal's and the end's writes the same time.
- The same round found a project's builder outliving a key's removal: a leaked key's build wrote into a cache mount, and the owner's next build, the release the doc says to run after a leak, read it. The end now removes the builder and its network, at the cost of the next build's cache.
- The same round found `PermitUserRC no` closing one hook of the home only: `~/.profile` ran at a login shell of a kept key (sshd's own, `--shell-host`'s `-l`), and the units of `~/.config/systemd/user` started at any login through pam_systemd, devopsy's own sessions included, checked on a throwaway Ubuntu 24.04 server. A `ForceCommand` was weighed and set aside, since it takes the subsystems (sftp) with it; the user's login shell became one of devopsy's that reads nothing of the home, and its user manager is masked, a link that works chrooted, logins going on without it.
- The same round found the daemon's jump holding nothing after a restart of Docker: a cgroup's rule binds the cgroup there when it goes in, systemd makes docker.service's anew at each start, and iptables prints the old rule the same, so the check saw nothing wrong; and at boot the loader, run before Docker, stopped at that rule, the kernel refusing a cgroup not there yet, leaving IPv6 unloaded. The loader now skips the daemon's jump until its cgroup is there, a drop-in runs it at every start of Docker, and it records the cgroup's inode, which `--server-info` compares. The timer alone would have treated the symptom. Checked on a throwaway Ubuntu 24.04 server: with the drop-in, a restart of Docker left the daemon's loopback traffic rejected under the new cgroup; without it, not.
- The same round found `--server-info` walking a project user's tree once `--project-users remove` took its entry, the tree and Unix user kept: whose a tree is went by the door's list alone. It now goes by owner as well, the deploy user walking no project directory it does not own; a mark left by the removal was weighed, but the owner also covers a tree the list names by another spelling of the root.
- The same round found a service with `networks: {}` skipping the names a shared network takes: the door read "no networks of its own" by the key being absent, compose by its content, and compose put such a service on a shared default under its plain name. The door now reads the content, as `notBool` reads a boolean.
- Every review round kept finding Docker's daemon to be the one network client of the door's that the firewall could not keep off other projects' networks: held by its cgroup, it was refused only the host's loopback and the metadata services, since `docker-proxy` shares that cgroup and reaches containers through the bridges, and a registry a project named answered it with a token realm or a redirect to another project's container, a GET whose status, port state and timing came back in the error. The daemon now contacts no registry a project names. A claim copies the registry's bytes with the door's client (`buildx imagetools create` into an OCI layout), checks every blob, and loads a tar the door writes itself, which on the containerd store leaves what a pull by digest does, so pins, holds and `internal/images` stayed as they were; compose's pull verb became the door's own claims, a start's file holds `pull_policy: never`, util runs `--pull never`, and a login is saved unchecked, its first claim checking it. Shown on Docker 27.5, 28.5 and 29.9: the shapes through the copy (an index of several platforms with attestation manifests, zstd layers, schema2), the load's words and exit, the canonical name's need, two loads at once. Set aside: loading the builder's export (not the registry's image: a rewritten config, a new id where a config has no `created`, false digests through bookmarks, no way to remove a claimed image); a verbatim copy on the classic store (the true id but no digest, so the record and `internal/images` would read digests from the door, for one store only); a forward proxy for the daemon (`proxies` in `daemon.json`: a standing daemon of devopsy's, server-wide, a Docker restart, the deploy user's pulls through it); a login checked in the door's process (a fourth registry client following a token realm, blind to the builders' CAs and mirrors); the door checking `diff_ids` itself from the layout (it would drop the proof and its second download, but needs zstd), left for later. The containerd store and buildx 0.33.0 became requirements, with a Principle that a feature needing a current Docker refuses an older one with words.
- The claims' first review round (two reviewers) found the layout's check and tar reading each blob whole into the door's memory, which an image of a large layer would push towards the OOM killer, now streamed; a failed copy taking a claimed digest out of the record, which only a load that ran may do; `registry-1.docker.io` folded into Docker Hub's short names, which Docker folds only for a login; the pull verb claiming an image it has under `pull_policy: missing`, which compose's pull skips; the host check reading the deploy user's own buildx while the copy runs the system's; `down` by name reading the deploy user's `~/.docker`, now through one helper for compose's environment; a signal racing the claim's child, reaching the docker CLI and not its buildx plugin, and missing the proof, now one guard for the whole claim, by process group; and the pull verb leaving a failed proof unlogged, now a refusal, only the registry's own failures a release's event. Also a manifest read without a bound, a ref by digest whose bytes were not checked, the loaded id not checked against the digest, and the record's lock outliving its user.
- The same round found the claim's proof checking a config's `diff_ids` only on BuildKit 0.33.1 or later (GHSA-f2v9-hprr-32q3, a fix of BuildKit's own), while a project's builder keeps whatever BuildKit it was made from, so an older one let the second forgery through. A BuildKit floor on the builders (refusing, or making them again from a fresh image) and a pinned builder image were weighed against the door checking each layer's content against the config itself. The door's own check was taken: the copy already showed every blob served, so the proof had nothing left to guard, and its going takes one download and one build out of every claim and the builder's BuildKit out of the claim's safety. zstd layers are read with klauspost/compress, containerd's own decoder, in process: the util image's zstd would have streamed through Docker's stdout, which the snapshot restore found too slow (8 MB/s on a small Droplet). A cap on a layer's decompressed size was left out: a layer that expands enormously costs a core for a while, as Docker's load of it would, and reaches nothing.
- The claims' second review round found a ref pinned by an index's digest taking an index whose bytes were never checked against the pin, so its registry chose the entry the door copied and a tag or an inspect acted on; and such a start handed compose the index's digest, which no image here goes by once the claim loads the platform's entry, so the start failed under `pull_policy: never` (a pull by that digest had left the index before).
