# Inherited variables

`cmd/devopsy/sync.go` (`inheritVars`, `runInherit`), `cmd/devopsy/parentenv.go` (the parent's copy), `internal/remote/vars.go` (the read and write scripts); a child's variables from its parent, written by a sync (`internals/syncs.md`) and by `--inherit`.

## inherit.env

- A parent's `inherit:` keys become the child's `shared/inherit.env`, whole: `inheritVars` reads the parent's files in one session (`ParentReadScript`, `readParent`, through the parent's own `--env-trace` over its `shared/.env`, its own `inherit.env`, so a chain passes on what the middle inherited, its instance's and project's `.env` and its `parent.env`), takes each key from the nearest level and writes them all under the child's lock (`InheritWriteScript`, the values on stdin), so a resync replaces the file; every release links it and the loader reads it below `.env`.
- A notice names the keys the child's own `shared/.env` shadows, never their values.
- The keys come from the parent's current release, never the checkout, through the preflight's session on the parent (`ParentCheckScript`; `--inherit`'s `ParentInheritScript`), which runs the hidden `--release-inherit` in its `current` to print what the release's own config names for the environment it was made for (`ReleaseEnvironment`) into `job.inherit` (`TestSyncInherit`): a checkout naming any key would copy that value of the parent's into the child whatever the parent's release says, and the parent's release decides what leaves it, as the child's decides its own `parent:` and run step.
- An `inherit:` naming nothing empties the child's `inherit.env` (a sync's child side writes an empty pending file, `SyncOptions.NoInherit`; `--inherit` an empty file): otherwise a key dropped from `inherit:` stays inherited for good.
- A first release inherits into `shared/inherit.env` before the upload, so `--missing-vars` sees the values; the file is kept on failure, since the next release is first again.
- A re-sync inherits into a pending file the sync reads in place of the release's, `$base/.devopsy-sync.inherit.<sync id>.env` (`remote.SyncInheritPending`, the id chosen by the operator's devopsy, `newSyncID`, since the file is written before the holder runs), named by `DEVOPSY_INTERNAL_INHERIT_FILE` (exported by the holder, set by `--sync-exec`) for everything the sync runs on the child, and in a release that syncs exported by the activation from before its prepare steps, so the owners' step after the switch reads the labels with it too (`TestMntOwnersInherited`, an owner inherited being the new one in that release, the entries the sync does not copy included): the child's labels follow an inherited variable in the same sync, never one sync late.
- `finish go` moves the pending file into place (`mv -Tf`) before restoring services, the hook and the run step; anything else removes it.
- One pending file per sync: two syncs of a child at once never read or remove each other's, and finish removes another's only past `staleInherit`, longer than any wait for the lock.
- `--inherit` (`runInherit`) writes the inherited variables and the parent's copy alone, with the same follow-up as `--vars set` (`internals/reload.md`).

## parent.env

- A parent on another server is copied whole, per child, into `shared/parent.env` (`remote.ParentEnvFile`, `writeParentEnv`): the parent's instance and project levels as written (`copyText`, each key's lines from the nearest level, merged per key, `dotenvChunks`, the files nearest first, so compose resolves a reference as it would across the files; within one file every line in order, a key defined twice reading as compose reads it; keys as compose's parser takes them), read below the child's own server's levels, so what the child's server says wins.
- The copy is written as the parent's files are, never interpolated on the parent's side: a `${...}` resolves on the child against its own variables, as it would were those files on its server; interpolated, a reference would carry the parent's `shared/.env` secret out and the parent's `COMPOSE_PROJECT_NAME` in.
- Every key is copied, with no exclude list: what must not leave a server belongs in an environment's `shared/.env`; a secret (`secrets:`, the checkout's) new in the copy is named, never its value.
- The read needs the parent's current release: a destroyed parent is no source, and the copy stays.
- The copy's first line names its source (`ParentEnvHeader`): every sync writes it from its own, and a release that does not sync, `--reload` and `--inherit` copy again (`refreshParentEnv`) from the child's parent resolved anew, or from the address a `--from` named, kept as named; a parent out of reach is a warning that keeps the copy.
- In a re-sync the copy is pending beside the pending inherit file (`ParentPendingOf`, read by everything passing `InheritPendingEnv`, swept with the leftovers) and moved into place on go.
- On the same server the child's side copies the parent's own `parent.env` under its lock, before its checks (`sameServerCopy`), else writes none, always under the child's own header (`sameServerParentEnv`, never the parent's), alone for a `--from` with nothing to copy, so its later copies follow it.
- A release or a reload rewrites the copy before its checks, as `--vars set` writes a file; the next activation applies it (accepted).
- Snapshots do not carry the copy: the next refresh writes it.
- A sync writes the inherited variables and the copy in one session (`ParentVarsWriteScript`), and a child's release reads the copy's header in its check of `current` (`CurrentExistsScript`'s `parentenv` line), so a release that does not sync costs the parent's trace and the write and no more: the values are on the parent's server, and carried in the upload the copy would be the release's, brought back by a rollback.
