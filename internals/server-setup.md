# Server setup

`--server-setup` keeps what devopsy needs of a server as devopsy wants it. Code: `internal/setup/` (the item model, touching nothing; parts, states, the steps and what stops them, the merge, the record, the daemon's flags, the volume candidates, the files' texts), `cmd/devopsy/serversetup.go` (the operator's side), `serversetup_step.go` (the server's, `--server-setup-step`), `firewallcheck.go` (the firewall's root read and its judgment, for the setup, `--server-info`, a release and the door), `hostroot.go` (`hostRun`), `internal/remote/serversetup.go` (`SetupRootScript`), `cmd/devopsy/projectusers_setup.go` and `internal/remote/projectusers_setup.go` (`--project-users setup`, `ProjectUsersSetupScript`), `internal/howto/` (`--server-setup-howto`'s topics) and `cmd/devopsy/howto.go`. User docs: `docs/servers.md`, `docs/server-setup-howto.md`, `docs/codes.md`, `docs/releases.md` (what an upload says).

## Items

- An item is a want, a check and, for what devopsy sets, an apply: the required ones (the release root, `tar` and `flock`, Docker) refuse what depends on them before anything changes, and the tunables (`daemon.json`'s parts, the socket buffers, the mounts drop-in, the metadata firewall) are applied.
- A refusal stops only the steps that need what it refuses (`setup.Facts.Goes`, a step naming its needs in `stepNeeds`, a refusal what it stops by `Refusal.Stops`), the others applied, and the run fails (a warning under `--upgrade`): a setup's items are independent settings.
- A refusal is said once per run with its fix (`sayRefusals`): by the first session, whose apply takes the identities of those it said (`--said`, `setup.Refusal.ID`) and says every other one it finds; by an apply run alone (`--upgrade`), all of them.
- Docker refused as not answering, not this host's, without systemd or its unit inactive stops every step; a Docker not answering or not this host's takes no chains' read or build of the util image either, its root container's host being another machine (`dockerHere`, `readsChains`), judged with or without systemd; its unit's `--config-file` stops `daemon.json`'s parts and a restart; its plugins and its floor stop nothing.
- What Docker answers of itself (`dockerFacts`, its `docker info` and compose's and buildx's versions, asked at once) is judged once (`dockerAnswers`): no daemon answering, a plugin missing, then one refusal per floor missed (`floorMissed`, `dockerFloors`), a plugin's only where it answers, each fixed by the `docker` topic; `--server-setup`'s facts, a release's `--server-ready` and `--project-users add` refuse on them (`dockerReady`), and `--server-info` says them under docker, for every server.
- A release reads Docker's answers only where the record's `docker-floor:` line (`setup.Record.Floor`) names another devopsy than its own or none (`floorNoted`), and never writes the record: each apply (`--server-setup`, `--upgrade`) writes the line as its last read finds Docker, this devopsy's version at the floor, none below it (`floorNote`), apart from the `devopsy:` line, which a floor missed does not hold back; a note that differs from the facts' read is something to apply (`setup.Facts.FloorNote`), an apply with no step going (Docker refused whole) included, which takes it off.
- A development build (`update.IsRelease` false) notes nothing and trusts no note: its version names no one build, so another checkout's of the same name would be trusted.
- A `--server-setup` whose only change is the note applies it quietly and ends on the words of one with nothing to change.
- Accepted: a Docker put back below its floor after the note is not seen by a release until the next devopsy version, only a new devopsy raising the floor; `--server-info` reads Docker live and says it.
- The classic image store is refused in words that say devopsy needs the containerd image store, its fix a Docker set up with it on a new server, and moving a Docker to the containerd store is documented nowhere.
- What a refusal stopped of a change is said by one line (`refusedLine`, `setup.Facts.Stopped`), in the first session's question, a run with nothing to apply and an apply's end, a warning under `--upgrade`.
- A step a refusal stops whose change cannot be computed (`setup.Facts.change`, its `known`) counts as a change it stopped (for example `daemon.json`'s parts and the restart beside a file devopsy cannot judge, the mounts drop-in beside a root a unit file cannot hold, the root's making beside a root refused).
- With no step going (Docker refused), nothing is applied, no util image built and no chains read, the record not made, and the apply ends on `refusedLine` as the first session does.
- The first session shows the differences and the refusals together, its question covering what goes and naming what a refusal stops (`refusedLine`); with nothing to apply it ends there, failing.
- A failure of one step's apply goes on to the next independent one: the root run puts in order, `daemon.json` last, and a put that fails, by its check (exit 4) or its write (exit 5), ends that run with what came before put, the record keeping no part that did not go in and the answers asked again; the firewall's run follows.
- A restart not confirmed in time leaves the firewall's step to go when Docker answers, and fails naming it when Docker does not; the run raising the reboot flag failing is said as its own error, Docker not answering only when `docker info` says so.
- The mounts drop-in's put is followed by a daemon-reload whatever comes after it, and with no restart queued the apply says Docker starts only once the root's filesystem is mounted, with a detail that nothing is asked of the operator.
- What the apply leaves for later (the drop-in, a `daemon.json` for Docker's next restart) says what happened and whether the operator has anything to do (`pendingWords`).
- The check after the apply judges only what went; a refused step is no "what was applied did not hold".
- devopsy checks and never installs: packages, Docker, the deploy user and devopsy itself are the admin's, and what devopsy checks of them has a topic of `--server-setup-howto`.
- systemd is assumed, not a distribution: the one convention used is the system's restart flag (`remote.RebootRequired`).
- Every state comes from the server's devopsy, which applies it (`readSetup`, `setup.Facts`); the operator only words them and asks.
- Every item is idempotent: a second run in a row changes nothing and restarts nothing.
- After an apply every item's check runs again, and what was applied and does not read in sync is an error naming the item.
- A file the setup writes whole sits at a path of its own and starts with `setup.Header` (`setup.DoorHeader` for `--project-users setup`'s own, the mounts drop-in both keep keeping `Header`), the firewall's aside; devopsy writes or removes no other file, the deploy user's `config.yaml` aside (`--project-users setup`), and none until its want is retired.
- The firewall's files, which `--project-users add` writes too, start with `firewallHeader` instead, which says neither command, checked by one test in Go and the removal's shell (`FirewallPiece`, `firewallPieceSh`).
- The release root is never asked or saved by devopsy: it comes from `releases: root`, else the home, and `/` is refused by `remote.ReleaseSettings` in every command.
- The release root and the tools are checked by one function each, `releaseRootCheck` and `toolsRefusal`, which `--server-setup`'s facts and the upload's `--server-ready` (stats and path lookups, Docker's own answers unless the record notes its floor, then the firewall's read where one is marked, never building the util image) both call; `--project-users add` checks the door's tools first, then the release root (`releaseRootReady`), and `--project-users setup` refuses on the release root as a required item of its own (`releaseRootRefusal`, which `releaseRootReady` words), its fix `--server-setup` on the session's address.
- The tools are one list, `serverTools`, the required ones marked, the door's too (`sudo`, `visudo`, `setfacl`), and every lookup of them is one function with a filter (`missingTools`): the setup's refusal and a release's check read the required ones, `--server-setup` warns of the others missing (`setup.Facts.Missing`), the door's only on a server with project users, `--server-info` says each one missing once, as a warning but for the door's on a server with no project user, a line with a hint as a `/proc` without hidepid is, and the door's tools' fix is the project-users topic, which installs them, never the tools topic, and `--project-users add` refuses first without the door's (`doorTool`), which refuse no release.
- The release root has one form, its links followed by what they say as far as its parts are there, each `..` walked from where the part before it led, the rest as written (`resolveRoot`): a root behind a link, made or not, its volume mounted or not, gives one want.
- The release root is made when missing and given to the deploy user only when root owns it and it is empty, a filesystem's own `lost+found` aside (`emptyDir`), never recursively: a root-owned directory with files is a system's (`/var`, `/opt`), and refuses, as another user's or one that is no directory does.
- A root that resolves to `/`, through a link, refuses as `/` does.
- The mounts drop-in's want comes from the release root, each path in its one form, the home included, by one function for `--server-setup` and `--project-users setup` (`mountsDropInWant`): `RequiresMountsFor` on `/` is `-.mount`, always there, and a want that moved with the release root's mounts would remove the drop-in while a volume is not mounted.
- The door's space is in the drop-in only where the config names it, or `--project-users setup`'s run names it there, and the host's mounts show it with `nosuid` and `nodev` (`spaceMount`), or that run mounts it: a `RequiresMountsFor=` of a mount that fails keeps Docker from starting at the next boot, so `--server-setup` and `--upgrade` take a space whose mount went out of it, and `--project-users setup` puts it back once it mounts it again.
- The root run puts the drop-in after the space's mount, with the space only once the mount went, else as `--server-setup` wants it without the space; a config append that fails after a mount that went leaves the two wanting different drop-ins until the setup runs again, which appends it.
- A root systemd reads otherwise is written escaped as systemd reads it back (`systemdPath`), and one a unit file cannot hold refuses.
- The metadata firewall is an item of devopsy's own (`setup.JudgeFirewall`): put back, never asked keep or replace, loaded through the door's one loader and its unit, the containers' chain alone without a door.
- A piece devopsy puts no more (the firewall's timer, `remote.FirewallRetired`) is retired: the install and the removal stop it and remove it by its header, the link to it with it, and the facts read one left as to load again.
- The firewall's want is `firewall: metadata:` in the deploy user's config, `block` by default, never an address: on one server the address is the provider's, so naming it would be turning the block off.
- The firewall's kind is the door's where `door:` is set or the door's is loaded (its mark, or a loader naming the door's chains), else the containers' alone (`setup.FirewallWantsDoor`): devopsy never takes a door's firewall off a server.
- `allow` where the door's kind is wanted refuses before anything changes, a project user's containers never reaching a metadata service.
- `allow` otherwise removes what devopsy put, files by their header only (`FirewallRemove`), finishing a removal cut before, the unit stopped under the lock, and a loader that then gets the lock with its own file gone loads nothing.
- The firewall's state for the deploy user, who cannot read iptables, is its files against devopsy's, modes included (`remote.FirewallFiles`), the boot's link to its unit (`remote.FirewallUnitLink`), and the mark (`remote.FirewallMark`).
- The mark is written by rename once a load went in and removed when one fails, whoever ran it, a load under way leaving the last one's: through a change of kind it says the old kind until the new is in.
- The unit's result is words only, never the judge: a load the unit did not run leaves it as it was.
- The full read of the chains is root's (`firewallRun`, the firewall's own root run, `firewallJudged` judging it): the apply's after a load, `--project-users add`'s, and, wherever devopsy's firewall is installed, `--server-setup`'s facts and apply and `--server-info`'s (`readChains`), judged by the kind loaded; none where nothing is installed, and none as a project user (`readsChains`).
- Only an apply readies the util image for a root run (`--server-setup`'s second session, `--project-users add`); the facts session, `--server-info` and a release read only with it there, the chains else said unread.
- Every root run holds `--pull never` (`hostRun.dockerArgs`): the util image is the deploy user's build, readied before, never a registry's.
- A read judges the chains once for both kinds (`firewallChainsWrong`), and chains not as devopsy loads them make a firewall in sync by its files and mark one to load again (`setup.FirewallFact.Chains`), in its one line: nothing loads it again between a boot and an install, so a wipe is shown, never healed.
- Every load and removal holds the firewall's lock (`firewallLock`, a minute at most): a load deletes its jump's other copies by number, which another load between its read and its delete makes another rule's.
- The lock is in a directory of root's no one else enters (`remote.FirewallLockDir`, 0700, made or closed again by each load): flock locks a file opened for reading, so a lock others could open is one they could hold.
- Every iptables call waits for xtables' lock (`xtablesWait`), which iptables-legacy fails without.
- The install loads through `devopsy-firewall.service` where systemd answers from the chroot, so its result is the load's own and its failure the install's; it runs the loader itself only where systemd does not answer.
- Without a door the Docker drop-in is not put: it serves the daemon's cgroup jump, while the containers' chain goes by interface, and its jump, inserted first, stays first through Docker's start, which appends its own rules to raw's PREROUTING.
- `--upgrade` only loads the firewall again as the kind loaded (`setup.FirewallState.Upgrade`): a first load, the door's chains added to the containers' alone and a removal for `allow` change what the server's apps reach, so they are `--server-setup`'s, shown and confirmed (`--yes` confirms).
- Each firewall state is worded once (`firewallLines`), for `--server-setup`'s differences, `--server-info` and what `--upgrade` leaves, a firewall to load again by W0001 with a line for each difference (`setup.FirewallFact.Differs`, `Wrong`).
- A release warns of one thing of the setup's, the metadata firewall not as devopsy loads it (`warnReleaseFirewall`, `report.FirewallNotLoaded`), never refusing: nothing else shows a wipe to an operator about to put something live.
- A release judges the firewall as the facts do by stats (`releaseFirewall`, `firewallHere`): none installed, or `allow` waiting for its removal, says nothing; installed with no mark, its last load failed, warns with no Docker call; marked, its chains are read as root by the mark's kind (`remote.FirewallChainsRead`, the chains alone).
- A release's read runs only with the util image there (never built) and Docker this host's (`hostRun.Here`, a `docker info` after the image's inspect, within the read's bound), within `firewallReadWait`, a failure or another host's Docker a debug line: it costs a release little and never fails it.
- A release sees only the chains and a failed load, never the setup's files, links or a retired timer, which `--server-info` says; `docs/codes.md` says which W0001's causes a release sees.
- A project user's release asks the door (its `firewall` request, `warnDoorFirewall`), which answers right, wrong or unknown from the deploy user's own read (unknown through another host's Docker), and says W0001 for the admin; on a server with project users a wipe is seen in the deploy user's releases, the project users' and `--server-info`.
- A run raises a live socket buffer only when lower, never lowering it; one that cannot be raised fails the second check, naming the reboot that loads the file.
- The sysctl file sets 7500000 at each boot, over an earlier file's higher value: a higher one belongs in a file sorting after `90-devopsy-net.conf`.

## `daemon.json` and the record

- `daemon.json` is three parts, each the sub-object of its keys (`setup.Parts`), compared in canonical JSON (`setup.Canonical`): spacing and key order never read as a change.
- The merge keeps every other key as the file has it (`json.RawMessage`), puts the file only when the canonical form differs, and leaves a part devopsy stops wanting in the file; the merged file gets no header and stays as its admin has it (`hostPut`'s `keep:`): a link stays, the file it names written, with its own mode and owner, 644 root's only for a file devopsy makes.
- A part's state comes from its observed value, the want, the record and the daemon's flags, by `setup.StateOf`'s rules in order, and what each command does with each state is `PartState.Upgrade` and `PartState.Setup`, which the facts carry (`setup.FactOf`), and what each shows `setup.ShowSetup` and `ShowInfo`: never a second judgment.
- The daemon's flags are a fact, read from the unit's command (`systemctl show -p ExecStart`, `setup.DaemonCommand`, `DaemonFlags`), never inferred from what docker info shows: the unit's command is what Docker starts with next, beside the file.
- A part one of whose keys a flag sets is the flags' (`setup.Outside`), whole: never put, never asked, said, out of pending and of the restart's confirmation, since dockerd refuses to start on a key both in a flag and in the file.
- A `--config-file` of the unit's naming another file refuses the Docker item: `daemon.json` is not what that Docker reads.
- dockerd's check of `daemon.json` runs with the unit's flags, so it checks what Docker starts with.
- A value someone else set is never put over unasked: `--server-setup` asks keep or replace, Enter and `--yes` keeping it.
- An answer acts only while the part still holds the value whose sha256 it names (`setup.Digest`): a part changed between the sessions is left unrecorded, said, and asked at the next run.
- `server.yaml`, beside `remote.UserConfigFile()`, is devopsy's record alone, never config, never in the schema, mode 0600, written by rename, its entries canonical JSON as quoted strings, so a comparison is exact text.
- The file is put first and the record written after, whatever the restart does next: every state a cut leaves reads in sync, which needs no record, and a restart not confirmed loses no answer.
- A server is set up by devopsy once `server.yaml` exists; the first apply writes it even with nothing to change.
- A `daemon.json` devopsy cannot judge (not a JSON object, a value of the wrong type, unreadable by the deploy user) has none of its parts judged (`judgeDaemon`): `--server-setup` refuses its parts and a restart, `--upgrade` warns, and no command rewrites it.
- Docker's facts and `daemon.json` are read once for `--server-info`'s facts and the setup's (`readHostDocker`), and each fact is worded once for every command (`refusalWords`, `daemonWords`, `rootWords`).

## Root on the host

- Every root step on a host is one `hostRun`, declaring what it needs (a writable root, the host's network, `NET_ADMIN`, the pid and cgroup namespaces) and getting nothing more; `remote.EndUserArgs` is apart, as it runs devopsy itself.
- An apply is one root run of `SetupRootScript`, its arguments what to put, the root to make or give, the buffers to raise, and the restart or the marker; it prints a line per change, which the server's devopsy words.
- That run has the host's network and `NET_ADMIN`, for `sysctl`, and its pid namespace, for `systemctl`: systemd refuses a peer it cannot see. Docker's own AppArmor profile, `docker-default`, refuses neither.
- The root script's system paths sit under its host root argument, "" on a host (`remote.HostRootEnv` in tests), so its tests run it on a temporary directory; the release root is passed as the host names it.
- `daemon.json` is put through `hostPut` with `dockerd --validate` as its check, last of the root run's puts: a refused file leaves the one there, and the puts before it stand.

## Restarting Docker

- `--server-setup` offers a restart when the run changes `daemon.json` or Docker has yet to take it (`setup.Pending`), and the operator passes its answer as a condition (`--restart`, `--yes`'s `--restart-idle`, only with no container running): the apply judges it under its locks, restarting only when this run put `daemon.json` or something is pending then, else saying why not.
- Pending is read only where a restart could go (Docker answering and this host's, the restart's step going), never hidden by a refusal that stops nothing.
- Pending is worded once (`pendingWords`) for `--server-setup`'s differences, its end, `--server-info` and the operator's "nothing to change": the restart Docker needs, the parts `docker info` shows it has yet to take (`setup.Visible.Differ`, none when only the marker tells), and what does it, the reboot the server needs where the system's restart flag is raised (`setup.Facts.Reboot`), else whoever restarts Docker.
- `--server-setup` sooner is a hint (`soonerHint`), never a fix: waiting may be the operator's choice. In `--server-info` pending is a warning while nothing is to restart Docker, and an info line once a reboot is asked for, the reboot's own warning keeping exit 3 for a server that waits on it alone.
- A restart is refused, with nothing changed, while a release holds a lock in the deploy user's environments: the apply tries each `$base/.lock` before anything changes and holds them all until the restart is confirmed or given up.
- The restart's locks are the deploy user's own projects' alone (`deployEnvBases`, `ownProjects`, `--server-info`'s filter), a project user's tree being that user's to change: never walked or locked, and the run says those releases are not waited for.
- Docker is never restarted on a `daemon.json` dockerd refuses, whoever wrote it: it would stay down.
- The restart is queued with `--no-block`, `daemon-reload` first, after the root run writes the marker with the `InvocationID` read just before the run and the run's own token after it (`runToken`): a restart that comes ends pending by its new id, the marker left to be read so (`/run` empties at a boot), and one that does not leaves Docker pending.
- Pending compares the marker's id alone (`setup.Pending`); a marker with no token (a change marked, an older devopsy's) is pending and never a restart asked.
- The root run clears `docker.service`'s start counter (`systemctl reset-failed`) before it asks for the restart, and the wait ends at once on a unit `failed`, naming its `Result`, read with its `InvocationID` in one `systemctl show`: a restart asked is no crash loop, and Docker refused a start does not come back by itself.
- A root run that fails once its restart was asked (its `asked` line, or the marker holding its own token) goes on to the bounded wait, which tells whether the restart came: a restart cuts the run's container, and its client's words then go unsaid; a run ended on the script's own exit (4, 5, `scriptExit`) never was.
- A drop-in put without a restart is followed by a `daemon-reload`, failing quietly: else systemd says at each call that `docker.service` changed on disk.
- A restart is done once `docker.service`'s `InvocationID` changed and `docker info` shows the file's values, those set outside it aside, waited for through `boundedWait`, bounded (`restartWait`); one not confirmed in time (`remote.RestartWaitEnv` shortens it for tests) is an error naming the journal.
- The system's restart flag after a restart not confirmed is raised then, by a second root run, never before the restart, which would ask a reboot for nothing; with Docker down that run cannot start, and the error says nothing was flagged.
- A change not restarted now raises the restart marker (`setup.RestartMarker`, with the `InvocationID` read just before the run, the one source of it) and the system's flag, through `restart_flag`, only when the run changed `daemon.json`.
- systemctl refusing from the chroot never leads to a privileged container in the host's pid namespace (internals/door.md): the run marks the change and names the restart for the admin.

## Sessions

- `--server-setup` is two sessions as the deploy user: `facts`, read-only, no lock, no util image, carrying the apply's needs (`WithAlsoNeeds`) so an older server refuses before anything; then `apply`, under the apply lock (`setup.LockFile`, `boundedWait`), whenever there is something to put, an answer to record, a restart, or no record yet.
- A project user is refused through `askedAsProjectUser`, the same exit as `--ssh-keys --for`, and `refuseProjectUser` names the deploy user's address.
- Declining saves nothing; `--yes` goes through the same two sessions, and without a terminal a question fails naming `--yes`.
- `apply --upgrade` asks nothing and restarts nothing: a changed part is left and said, a missing release root said and never made, every failure a warning, exit 0.
- A server is one whose `server.yaml` exists, from its first `--server-setup` on, with no other sign: only there does `--upgrade` apply (`serverApply`), and `--server-info` warns where it is missing.
- `--upgrade` applies once per devopsy version (`upgradeApplies`), when the record's `devopsy:` line, written by an apply that ended with no failure and no change a refusal stopped, names another version or none; drift on a server applied already is `--server-setup`'s.
- `--server-setup` and `--upgrade`'s apply are one path, the level of what they say and the exit the only differences.
- `--server-info` shows the same facts and items as `--server-setup` (`setupItems`), never a second judgment.
- A project user's `--server-info` gathers no setup facts, reads nothing of Docker and makes no root read (`asProjectUser`): the server's setup is its admin's, and the door would refuse Docker's reads and log each; it asks the door's `firewall` request instead and shows W0001 for the admin on wrong (`projectUserFacts`).

## --project-users setup

- `--project-users setup` sets the door's items alone (the tools, Docker, the release root, the space, the config, the processes), in two sessions as `--server-setup`'s, facts then apply under the same apply lock (`applyLock`), an older server refusing in the first (`ProjectUsersSetupFeature`), and neither `--server-setup` nor `--upgrade` runs it: project users are a choice.
- Its facts are `setup.DoorFacts`, its steps `setup.DoorSteps`, what stops each `doorNeeds`, on the model's own helpers (`refusedItems`, `blocks`): the tools, Docker and the release root stop every step, so nothing is applied, and a server it calls ready is one `add` goes on; the space refused, or a `door:` without `space:`, stops the space, the drop-in and the config; `/proc` set another way and wrong stops the processes alone.
- A setting there another way is in sync: the space's mount and `/proc`'s hiding are read from the host's `/proc/mounts` (`mountOf`, `spaceMount`, `procMount`), never from whose file made them, and nothing of devopsy's goes beside them; a unit of devopsy's found there is judged as devopsy's.
- Accepted: a setting made live only, by hand, with nothing that restores it at boot (a hand remount of `/proc`, a hand bind of the space) reads in sync and is lost at the next reboot: the checks go by what the mounts say, never by what made them.
- The setup's `/proc/mounts` and the door's `statfs` of the space are two reads, the setup's telling also whose mount it is and reading under the host root, judged by one function of the options (`guards`), so they never disagree on what guarded means.
- The space is the config's `door: space:` where it has one, another directory named refused, else the one named, else `setup.DefaultSpace`, taken as named, a link in its path refusing; a refusal of the config's directory says what to change of it, or to move it by hand and set `door: space:` to the new path, never to name another; a path devopsy writes in a unit or the config is plain (`setup.PlainPath`).
- The root run's lines are said as it prints them, so a failure it says reads in its place among them; the check after it leaves out a drop-in that lacks only the space, the space's own lines saying that failure.
- The space refuses as the release root does (another user's, no directory, root's with files), by the one judgment of a directory devopsy makes or gives (`dirOwner`), and as someone's mount without `nosuid` and `nodev`, devopsy stacking none on the admin's; one that holds files on no mount of its own is bound on itself as an empty one is, since a bind of a directory on itself hides nothing, so a space whose mount went is mounted again.
- The space refuses, in the facts (`swappable`) and again in the root run right before it acts (`safe_path`), where another user could swap a part of its path for a link between the two: a part that is a link, a parent owned by anyone but root or the deploy user, or one others may write unless it is sticky and holds the next part as root's or the deploy user's; the run's make, `chown -h`, `chmod` and mount then act on the space itself, since once it holds only root and the deploy user can change a part.
- The space's mount is a unit of devopsy's (`setup.SpaceUnit`, named as `systemd-escape --path` names it), never a line in `/etc/fstab`.
- `/proc` is remounted by `devopsy-proc.service`, its text holding the group's number, which the root run reads once it made the group (`setup.GIDMark`), run again by a restart, since an active oneshot runs again by nothing else; polkit's drop-in goes only where `polkit.service` is loaded.
- The deploy user's membership is read from the group file (`groupOf`, through `getent`), never from its process's groups, which count from its login, and the apply says that a session open meanwhile sees every process only once opened again.
- The config is appended as text (`setup.AppendDoorConfig`) only where the file has no `door:` and the lines read back as `door: space:`, once the facts read again after the root run find the space made and mounted, whatever else of the run failed (each step judged by its own result), its two lines shown before the question.
- The differences say what is so and, for a step that goes, what devopsy does about it (`doorItemLines`), a refused step's only what is so; the first line of the space names what it is for (where devopsy keeps project users' data), and a drop-in of devopsy's that lacks only the space is said as Docker not waiting for it yet.
- The words say the project users' directory, never the door's space, but where the config key is meant (`door: space:`).
- An apply with no failure ends on the server ready for project users, offering `--project-users add` by the session's address while the door has no user.
- One root run (`ProjectUsersSetupScript`, `doorSetupRun`): the host's root writable and its pids, for `systemctl`, no network and no capability added; every mount goes through systemd from the chroot (`daemon-reload`, `enable --now`), never `mount` in the container, whose namespace a mount would not leave; `enable` runs `--quiet`, the run saying its own line per change, never systemd's own lines.
- That run has no `set -e`: each command that fails, a `put`'s exit in its subshell included, fails its step alone, said, the rest of that step left and the other steps going on, and the run then exits `remote.DoorSetupSaid`, a code no tool returns through it, so a tool's own exit never passes for a failure devopsy worded.

## --server-setup-howto

- `--server-setup-howto [<topic>]` is local and prints only, on stdout, plain: the topics without one, a topic's steps with its name; it needs no server, project or Docker, so a fix's command runs wherever it is copied.
- A topic is one thing devopsy checks on a server and cannot set up, a `howto.Topic` in `howto.Topics`, its name a `howto.Name` constant; what one command or one package fixes, or devopsy fixes itself, has none.
- Every fix for a topic's setting offers `howto.Command` of its constant, never the flag spelled again (`TestFlagSpelledOnce`, `TestConstantsAreTopics`), through `stepsFix` or `stepsHint`, whose text says what to set and ends `; this prints the steps:`, or `byHandHint`, the other way to a fix that sets it up, said after it; never `as root:`, since the command only prints and runs as anyone.
- A refusal of the setup names its topic in `setup.Refusal.Howto`, since it crosses the wire as JSON with its fix a string, and the operator's devopsy offers the topic's command after the fix's text (`fixWords`).
- A topic's commands are copyable as they are: a value the admin chooses is a variable set on the step's first line with its usual value, a system's value computed, never a `<word>` to replace.
- A topic's steps are generic for Debian and Ubuntu with systemd, say where the two differ, and leave out choices of one way to set up a server (the deploy user's making, swap, unattended upgrades); no topic names a tool that does them.
- Each topic ends with its check: the `--server-info` line that goes away, else a command whose output shows it.
- What the flag prints is Markdown that reads as it is (a heading, paragraphs, a numbered list, commands in fenced blocks), with no markup in a topic's sentences: it is read raw in a terminal more often than rendered.
- `--all` in place of a topic prints every topic under one title with a table of contents (`howto.All`), each a section named as its topic, and `docs/server-setup-howto.md` is that output whole (`TestDocsPage`): a change to a topic changes the page in the same commit.
