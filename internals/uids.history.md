History, not rules: internals/uids.md wins where they differ.

- Containers of every project ran as 10001 (and a database as its image's 999) until 2026-11-12. On a test machine a host process as 10001 with no capabilities and no_new_privs, standing for an escape from one project's container, read another project's environment (a registry's secret), read and wrote its files through `/proc/<pid>/root`, and signalled it; the same process could open nothing of the door's directories directly. No sysctl closes it: Yama checks only an attach, and `hidepid` never hides a process from its own uid. A different uid and gid is enough.
- A uid per environment, not per project, so a `pr-*` environment's branch code reaches nothing of prod's; a project's own uid beside it for an image that builds one in. A uid derived from the project user's id was set aside (it differs per server and does nothing for the deploy user's projects), and so were a uid the admin assigns, a hand-picked range with claims, and a project salt as the way out of a collision: a uid a tenant writes could be another tenant's, and a tenant who names its environments finds a name hashing onto any slot in seconds, so the hash only spreads honest owners, and the claims keep tenants apart.
- The ranges sit inside the block systemd's UIDS-GIDS table leaves unused (1879048192 to 2147352575): above systemd-nspawn's container blocks, where `useradd`'s subordinate ranges also fall, below the foreign OS image range and 2^31. One range per domain, so a bare project's uid, whose name only the admin gives, cannot be pushed by another tenant's names.
- Claims are keyed by owner, not by uid: with a file per uid, an owner probed to h+1 slid back to h once its neighbour was freed, changing a live environment's uid.
- Only the server computes a uid, at each load, stored nowhere: a value in devopsy-target.env would come back with a restore from another environment, and one an operator sends would be a value to trust.
- Starts and frees exclude each other through start locks rather than claims kept forever: kept claims leaked a slot per `pr-*` environment, and a free without a lock raced a start, leaving a container on a freed uid a tenant could aim another's next environment at. The lock is a flock handed to compose across the exec, so the kernel drops it whatever ends compose.
- Behind the door a start's uid follows both the request's directory and the file's name: following the name alone let a branch name itself prod (first review, 2026-11-12); following the directory alone let a file in prod's directory under another of the project's names run on prod's uid and outlive prod's free, which downs by name (second review).
- The free reads the environment from its directory, never the caller's words, and downs nothing without a claim: both let a project user take another project's flat compose name down (first review).
- Copies map uids by range and carry nothing: the receiving side knows its own two uids, and the range says each owner's kind; a child on the same server reports its own, which the door checks against the project's claims.
- Every mount of an owned volume needs `nocopy`: Docker fills an empty volume, owner and mode of its root included, when a container mounting it is created, which a chowned empty root does not stop. A release's prepare does not make owned volumes: its steps run before the labels are read, and a volume with options is made by compose's create, which would make the new release's containers before the switch.
- Checked on a test machine, 2026-11-11: every template image ran as a uid near 2 billion with no passwd entry; GNU tar and rsync keep such a uid, busybox tar writes a wrong one without an error (devopsy runs none), and rsync refuses `--usermap` beside `--chown`.
- Set aside at the build, 2026-11-12: checking the claims directory against the configured release settings beyond a release reached under the root (devopsy reaches every release there); `--project-users remove` freeing claims (its environments stay, and each one's `--destroy` frees it); a feature gate of its own for owned volumes (a project reading neither uid owning volumes behaves as before on an older server); `cli.ReadsUIDs` seeing `include:` and `extends:`, since `cli.ComposeVariables` reads only `compose.yaml` and its override, which the secret-like names' check and `--missing-vars` share.
- A second caller of `freeUIDs` (2026-11-12): a removed project user's claims had no way to go, its `--destroy` needing a key it no longer had, so `--project-users remove --destroy` frees them as the deploy user, each under its start lock as a `--destroy`'s free does.
