# Reload

`devopsy @<target> --reload` runs the current release with its variables as they are now and its imports read again, then its `reload:` step. Code: `cmd/devopsy/reload.go` (`runReload`), `cmd/devopsy/checkimages.go` (`--check-images`), `internal/remote/reload.go` (`ReloadScript`), `internal/images/reload.go` (`ReloadCheck`, `BuildKey`).

- One flag, with no `--stop` or `--start`: a flag needs a mechanic of devopsy's behind it (here the lock, the guards, imports, owners, the images check and the log), stopping is compose's word, and a stop with a maintenance page is a template's policy.
- `reload:` is a step of its own (a single command, in `defaults:` and per environment), read from the release's own config on the server, never the run step: a sync reruns the run step because its data moved, a reload's data stays, and a run step may do far more than apply variables and is not promised to be idempotent.
- Without a `reload:` devopsy runs `remote.ReloadDefault` (`up -d --wait --no-build --pull never` through `devopsy --`, which only devopsy can pass); a project whose deploy is what applies its variables sets `reload: deploy` itself.
- A reload is checked as an activation is before its switch: the release lock, `recoverFetch`, `settleSync`, `markRefusal` (a marked environment refuses), then in `current` `--prepare-release reload`, `--missing-vars`, `--check-names`, `--check-mounts` and `--check-images`; until `waitBeat` a session gone or a signal changes nothing.
- From `waitBeat` on, `followOutput` into the release's server log, the imports moved into place, `--mnt-owners`, the step, `img ran`; a step that fails is said and restarts nothing, since the release did not change.
- Imports are read again without touching the release until the checks pass: `cli.PrepareRelease` with `reload` counts a value whose winning definition was imported (`EnvImported`) as unset and writes the release's own lines and the new imports into `devopsy-target.env.reload` (`TargetReloadFile`), which every command reads in place of `devopsy-target.env` while `TargetPendingEnv` names it (`loadProject`), as a sync's pending inherit file stands in for `inherit.env`.
- A reload never builds or pulls, so `--check-images` (`images.ReloadCheck`) requires, with the variables as they are, each default service's image name to be the listing's, a built one's build key too (naming the arguments that changed), and no service new (a profile turned on): `--no-build` leaves a build argument applied by half (a container running as the new UID on files of the old), and a project's step without `--pull never` would pull a new name outside a release, held by no bookmark.
- The same check runs wherever a run step starts the current release's images on variables that may have changed: a `--sync`'s holder before anything stops (with the pending inherited variables; its fix is `--release-sync`, `--check-images --sync`) and a `--no-code` restore before its data step (with the snapshot's `shared.env` and `inherit.env` under `--with-env`, through `DotenvPendingEnv` and `InheritPendingEnv`, the stand-in passed to compose as `--env-file`; its fix is the full restore, `--check-images --restore <id>`).
- A full restore `--with-env` needs no check: its release's `.env` and `inherit.env` link to the snapshot's from its checks to its data step, so its images are listed and fetched for the variables it leaves; a release that syncs fetches anew.
- `--vars set|unset` and `--inherit` say what applies the change and refuse nothing (`varsApply`, `--check-images --hint`, `ParseVarsApplied`, `VarsHintScript`): on an environment with a current release, under the lock, with the imports read again (`--prepare-release reload` into the pending file, removed after) and the env capability's values (`MissingVarsIn`), a reload (exit 0), a release (3, with the images' lines), or nothing until a required variable is set (4, a warning); the instance's and the project's files, several environments', get the plain line, and `--inherit` the `--reload` line.
- A plain directory, an environment not released yet and a marked one (`--inherit` into one too) say so, never `--reload`, which refuses there.
- `reload:` and `destroy:` go with the release and run on the server, so `checkStepScopes` checks their scope with the release's: a command that only runs locally would fail a reload past its checks.
- A release cut off past its switch is refused (`cutRefusal`, `ActivatingFile` while the reload holds the lock), in `--status`' words with what finishes it (`Activating.Cut`), and `--vars` and `--inherit` say so too (`cut`): an `up` alone would start its code without its run step.
- Rollbacks, the restart after a failed run step and a full restore build again an own image whose build key differs from what today's variables give (`rebuilt`, from the release's code, before the switch but for the restart, which runs after current went back), only when a `build:` input changed and only in build mode; any other variable is the run step's.
- The restart's build failing, `img restore --as-built` puts the bookmarks back as they are; the image a rebuild replaced is left without a name, freed by the `img prune` after any removal.
- `devopsy --reload` in a release on a server runs that environment's `reload:` (`reloadStep`, as `destroyStep` does), unguarded, as any command typed in `--shell-host` is.
- `check-images` is a feature flag, so an older server refuses a reload, a sync, a `--no-code` restore and `--vars set` until upgraded, before anything changes.
