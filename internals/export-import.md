# --export and --import

Code: `cmd/devopsy/data.go`, `cmd/devopsy/writers.go`, `ExportScript`, `ImportScript`, `ResolvedCheckScript` and `ResolvedScript` in `internal/remote/sync.go`, the export's record in `internal/images/sync.go`, `ImportLanding` and `ResolvedLanding` in `internal/images/landing.go`.

## The contract

- One service's data goes to stdout or comes from stdin, the way its data label says, and the label is the contract (internals/data-labels.md): a service without data or with `copy=none` is refused, `custom` runs the capability's `export` and `import` (`runDataHook`, the lists in their environment), `volumes` moves a tar of the service's entries of `mnt` and its named volumes.
- The `volumes` tar is made in `UtilImage` as root with `--numeric-owner`, each entry and volume mounted at `/x/<name>`, exclude honored, file entries included, only files, directories and links (`find ... | tar --null --no-recursion -T -`), hard links as files of their own and holes kept (`--hard-dereference --sparse`): a FIFO, or a hard link to a link or across entries, makes a tar the import refuses, and a database's holes came back as zeros.
- The set (`cli.DataStops`, `ExportOne` or `ImportOne`) is stopped around either and restored (`stopSet`) up to the first write, after an interrupt or a stop that failed too, since the stop may have stopped them all the same.
- A `custom` import of a service not in the set brings it up alone (`upFor`), always `--no-deps`, and down again after when it was down, an `up` that failed too: a retry's set is empty, since nothing runs, so passing `--no-deps` only with a set would start a half-imported dependency (a sync's import has its own rule, internals/syncs.md).
- stdout is the data: `--export` refuses a terminal, and `--import` refuses one as stdin.
- `--import` spools its stdin whole before stopping anything (`importSpool`: in a release a temporary `$base/.devopsy-sync.stream.<service>.*`, locally `.devopsy/.devopsy-sync.stream.*`, which `excluded` keeps out of releases) and refuses an empty one; the spool always goes, and one a devopsy killed outright left goes with the next import of its service or `--resolved` (`removeSpools`).
- On a target the local side asks on `/dev/tty` (`confirmImport`, the target's full name, internals/data.md), since stdin is the data; no terminal and no `--yes` fails.
- On a target the server runs the same code: `ExportScript` holds the release lock shared and `SyncLockFile` exclusive, as a sync's push does, and passes stdout through as it is, never colorized; `ImportScript` holds the release lock exclusive and runs `devopsy --import <service> --yes` without exec, so its holding file goes on its way out.
- `--export` and `--import` need the server's `export-images` feature (found by the flags, internals/releases.md): an older server would export without the images' record and import unchecked.

## The tar's checks

- A `volumes` import, and a snapshot's restore through the same code (internals/snapshots.md), check the whole tar before anything changes (`tarEntries`, read with `archive/tar`): a truncated tar fails, and so does one without its end-of-archive blocks, since `tar -t` takes a tar cut at a member boundary for complete.
- A top-level name the service neither mounts from `mnt` nor has as a named volume (by key, `tarEntry.volume`; a volume carried as a file refused), an entry its label excludes, `./`, `mnt` itself, and a member reaching out of its entry (`tarMember`, which refuses a `..` or absolute path, a hard link out of its entry, and a top-level entry that is no directory or file) are refused: GNU tar extracts those into another entry or, for `../x` into `.`, the container's root.
- Nothing is written through a link (`tarLinks.check`, once the whole tar is read): a member below a link of the tar or sharing a link's name, and a hard link to a link or below one, are refused; then every name is where it lands.
- A symbolic link's target is the data's own, wherever it leads: the extraction mounts its entry alone, so nothing of the host is in its way, and an app's absolute links are normal.
- A bind source of the current code that the tar's links make lead out of its entry is refused (`linkAtBind`, locally too), walked through the tar's own links as the host resolves them in `mnt` (`tarLinks.walkMnt`, 40 links at most, Linux's own limit, through `mnt` only back into the entry), never lexically: Docker follows the links on the host, and a lexical walk reads as inside the entry a path the host resolves outside it.
- What the tar does not carry is a directory to the walk: the entry is emptied first.
- At most one pax global header, first, holding only the export's record (`images.ExportKey`) or git's `comment`: GNU tar applies a `path` or `linkpath` record to every member after it, renaming members and retargeting links the checks never saw.
- Any member but a file, a directory or a link is refused (`tarTypes`, `errMember`): GNU tar as root makes device nodes on the host, where bind mounts are not nodev, and the owners' step then gives one to the entry's owner.
- Member names are plain paths, `././` and `//` refused (`tarEntry.forms`): the extraction takes an entry's members by name, and GNU tar matches `./storage/x` only by `./storage`.
- An entry that is a symbolic link is refused both ways: tar carries only the link, and the image's `/mnt` never reaches its target.

## Extracting

- Each carried entry is emptied, never removed, and extracted with `--overwrite`: a running container bind-mounts the directory's inode.
- Each entry is extracted in a util container of its own (`extractEntries`, its task `import`, `--network none`) that mounts that entry alone, made first when missing as the tar has it (a directory or an empty file, one of the other kind refused before anything changes), and takes only its members from the whole spool: the service may run meanwhile, and its owner swapping a directory just made for a link to `../<other entry>` would otherwise have GNU tar plant files there as root; the spool read once per entry is the accepted cost.
- The spool (a restore's `.tar.zst` decompressed there) is mounted read-only into the container and read there, never sent on the container's stdin, with what tar leaves past its end blocks drained so zstd never gets SIGPIPE: Docker's stream is many times slower than a mounted file.
- What an entry or a volume's extraction wrote is mapped to the environment's own uids in the same container (`emptyAndExtract`, `uids.MapScript`, the uids read before anything stops), a snapshot's restore's too: GNU tar maps owners only when it creates a tar.
- An owned entry extracted goes to its owner before the import counts as complete, in a container of its own (`ownMnt`, its task `import`, so a leftover import's end removes it with the extracting ones), never locally on macOS (internals/data.md).

## The first write, the mark and the record

- The first write is devopsy asking Docker to start the writer (the import hook, or the util container), checked against its context right before; from then on the import counts as written, a Docker error that started nothing included.
- Before the first write a failure restores the set; from it a failure ends the write (`endImport` removes the one-offs and the environment's `import` containers, internals/data.md, and stops the service and its dependents) and keeps the set down, the imported service stopped and recorded too when it ran before, one rule with a sync's `endWriters`: a `custom` import may drop the database first, so a cut one restored serves an empty site.
- Locally there is no mark and no record: the error names what it left down and `devopsy start`.
- On a target (`cli.InRelease`) the record goes first, at the stop (`stopSet` with the sync's `syncState`), the mark right before the writer (`IncompleteImport`, its second field the service, `markIncomplete`'s `from`), and a `writer <pgid>` line before the hook runs: the hook's devopsy, in its own process group, waits for a byte on fd 3 that `runDataHook` sends once the line is written (`hookStartEnv`, `awaitHookStart`) and runs nothing without it, so a devopsy killed between the two never leaves a loader nobody recorded.
- A complete import restores the record's `stop` lines (`restoreServices`, never `stopSet`'s set, which is empty on a retry) and removes the mark (`clearImportMark`, only while still its own) and the record only once all are healthy; a start that fails keeps both; on a retry `upFor`'s `down()` is skipped for a service in the record.
- The local side sends the data, then an end line with a nonce (`ImportEndEnv`), and keeps stdin open; the server finds the line in the stream (`spoolUntil`), prints `remote.ImportMarker` and waits, bounded by `dataQuiet`, for one byte (`awaitByte`), which the operator's devopsy sends on the marker unless interrupted; without the byte the set is restored and nothing is imported: a session cut halfway reaches the server as a plain EOF, and one lost between the spool and the first write is otherwise seen only through SIGPIPE, asynchronously.
- From the byte on nothing from the session interrupts the import, as after a release's switch: `signal.Ignore` of SIGPIPE, SIGHUP and SIGINT (dropping `interruptible`'s `Notify` alone would let Go's runtime kill devopsy on its next write to the gone fd 2), `errOut.keep` into `$base/.devopsy-sync.log`, and the import's own result decides; a Ctrl-C after the marker says the import goes on, a second ends the session.
- The writer never holds the release lock, since devopsy sets fds 8 and 9 close-on-exec (`syscall.CloseOnExec`), so the hook and the util container's client get neither, and keeps them to its end: a load orphaned by a killed devopsy held the lock to its end, and every lock-taker waited 600 s and failed.
- An import's devopsy killed outright is ended by its script, which lives on (`--sync-services end-import`, `importOnTarget`), since a release is refused before anything else stops what runs on the data; with the script gone too, by the next lock-taker.
- An import's leftover writer is ended by the next lock-taker (`endLeftoverImport`: the record's writer groups get SIGTERM while `/proc` shows the data capability's import started with this environment's `COMPOSE_PROJECT_NAME` (`isDataImport`), then SIGKILL; the import containers go; `endImport` records the imported service only when it ran before, its writer line ending ` down` when `upFor` brought it up), run by an import of that service, `--resolved` and a child's prepare; `--destroy-data` removes the containers too, by their labels (internals/data.md), since compose's `down --remove-orphans` leaves them.
- The restore's compose calls run in their own process group (`compose`, not `composeContext`): a terminal's Ctrl-C reaches the whole foreground group and would leave the larger sets down without a word.

## Marks

- While an import's mark is there only its service can be imported (`ImportScript` in shell under the lock after its `settle`, before devopsy reads stdin, and again in Go), and any import refuses on a sync's mark: two partial services would need a rule per combination, and an import's mark over a sync's would lift the guard off its partial copy.
- A sync's mark replaces an import's, never the reverse (`markIncomplete`: `keep` keeps a sync's only, the holder's `copy` line writes over it, `finish partial` keeps any mark when nothing was written), and from then on only a sync clears it.
- A sync clears an import's mark only by copying that service (`copiesService`: a `custom` one, or every entry the child's service mounts, from the child's list, copied and present on the parent), refusing before it stops anything otherwise; a sync whose parent writes nothing stays partial.
- A failed data write under a mark goes through one function per side of the mark, never its own words at each site (for example `before` and `importRun.failed`, `before` and `stayDown`): a site on its own forgets the ways out.
- Every reader of a mark branches on its code (`markRefusal`, `partialGuard`, the restart skip, `PushScript`, `syncBlock`, `--status`, `--export`'s warning, `syncPreflight`, the operator's release check, `UploadScript`) and says "the import of <service> did not complete" with its ways out (`remote.ImportFixes`), `--sync` among them only on a child.
- "Importing" is `SyncImportingFile` with the lock held (`ImportRunning`), never `LockBusy` alone, which any holder of the lock would make read as an import; a script holding the lock knows no import runs, so `releaseLock` removes a holding file a shell killed outright left, an import's and a sync holder's alike.
- A release of a marked environment refuses before its upload and without a new session: `UploadScript` checks the mark under the lock before `LockedMarker`, refusing only what `partialGuard` would (a release that syncs goes on); a child's `CurrentExistsScript` prints the mark's line (`remote.ParseCurrent`), "incomplete" alone for a killed holder's files.

## --resolved

- `--import <service> --resolved` (`runResolved`, `runRemoteResolved`) is the way out when the dump itself cannot complete, on a target only: locally nothing tells a failed import's stops from deliberate ones.
- A read-only session (`ResolvedCheckScript`, never waiting on the lock) refuses with no mark, another service's, a sync's, a killed holder's sync files (which make it a sync's) or an import running; the prompt names what starts (the record's `stop` lines, the imported service only when it ran before) and asks for the full name.
- A second session under the lock settles a killed holder's sync (`settleLeftover`, as `ImportScript` does), checks again, ends a leftover writer, gives a `volumes` service's owned entries to their owners (`resolvedOwners`, its containers an import's owners'), starts the record and only then removes the mark and the record.
- On the server it is `devopsy --import <service> --resolved --yes` (`ResolvedScript`), so the `data-copy` feature gates it.

## The images in an export

- A `volumes` `--export` carries its service's data's window, as a pax global header before the members (`ExportData`: on a target `ParentData`'s lines, locally its label's version and tag as one line; `exportHeader`, `images.ExportKey`), which GNU tar and bsdtar skip.
- A `custom` export is the hook's stdout and carries none, and a `custom` import or its `--resolved` checks nothing and leaves the history and the hold: its script loads the dump through the image that runs.
- An `--import` on a target reads the header (`tarRecord`, `DataFor`) and is a landing (`ImportLanding`, internals/images.md): its service's labels judged against the export's window before anything stops, the window taken over once the data is in, first line `import` timed at the import.
- A tar without the header starts the history over, as data of no known version, and what next runs on it says its version; locally there is no history.
- A failed landing stops what ran through the import (`endImport`) as a failed write does, and keeps the mark.
- `--resolved` keeps a window that starts with an `import` or `forced` line written since the mark (`ResolvedLanding`), else starts it over, and an import's mark is timed at its latest write (`markIncomplete`): an earlier import's window is none of what a retry wrote over.
- The check and the take-over run under the server's image lock, shared, taken from Go in two short windows (`imagesShared`), never across the load: a removal elsewhere waits only for them.
- The import's `Set` is `serverImages`', with the project's record, as `img`'s is (internals/images.md): without the record the names the take-over gave up leak.
