History, not rules: internals/server-setup.md wins where they differ.

- The root run shares the host's pid namespace, and is no privileged container: tried on a Debian 13 machine with systemd and Docker, `systemctl` from the chroot failed ("Failed to connect to system scope bus via local transport: No data available") until the run had the host's pids, since systemd refuses a peer outside its pid namespace; the firewall's run already declared them.
- Docker is never restarted on a `daemon.json` dockerd refuses: on that machine, a pending file with a key Docker did not know, written by someone else, kept Docker down after the restart, so the root script checks the file before any restart.
- A drop-in put without a restart is reloaded: otherwise systemd said at every call that `docker.service` changed on disk.
- Whether Docker restarts is the apply's to judge under its locks, the operator passing only the condition: a part changed between the sessions left the apply with nothing for Docker to take while the operator's answer still asked for a restart, and `--yes`'s "no container running" was counted in the first session.
- One judgment of each part, the model's, carried in the facts: the operator's plan judged the states a second time and missed recording devopsy's value for a kept part back in sync, so the kept value written again later read as kept.
- A part set outside `daemon.json` is a state of its own: a part the file did not set read as devopsy's while `docker.service`'s flags set it, and putting it would keep Docker from starting.
- The release root has one form, its links followed: the facts resolved links only once the root was there, so a root behind a link and not made yet got two drop-ins on two runs.
- The record is written right after the file, before the restart's wait: a wait not confirmed in time used to return first, losing a first run's record and its keep answers.
- The deploy user's environments are walked through `--server-info`'s own filter: the restart's locks walked a project user's tree in the release root, opening a lock there that user could change.
- Tried on cloud Debian 13 and Ubuntu 26.04 with AppArmor enforcing Docker's `docker-default` profile: `--server-setup --yes`, a restart from the chroot confirmed in a second, `--upgrade` and `--server-info` worked with no `apparmor=unconfined`, so `hostRun`'s way to declare it went, having no user.
- The daemon's flags are read from the unit's command, never inferred from `docker info`: the inference missed a flag docker info cannot show (`--log-opt`) or one holding Docker's default, so a part was put beside its flag and Docker refused to start, and a part half in flags was pending for ever. The unit's command was taken over the running daemon's `/proc` command line, since it is what Docker starts with next.
- The marker is written before the restart is asked: a restart that cut its own run left the apply reading the old `InvocationID` while the old daemon stopped, and a second run raising the marker could not start with Docker down. The system's restart flag after a restart not confirmed still needs that second run: raised before the restart, a restart that came would ask a reboot for nothing.
- A root-owned release root is given only empty: `releases: root: /var` would have handed a system directory to the deploy user.
- `--upgrade` applies the setup once per devopsy version, by the record's `devopsy:` line, rather than at every run: an upgrade that says devopsy is the latest should not write under `/etc`, while an apply that failed must still be taken again, which a version noted only after an apply with no failure gives. Drift on a server applied already became `--server-setup`'s, `--server-info` warning of it.
- A retest on a cloud host hit systemd's start limit (`StartLimitBurst=3` in a minute): Docker had been started three times in the minute before, by its install and restarts by hand, so the restart devopsy asked stopped the daemon and its start was refused (`start-limit-hit`), and devopsy waited its whole bound before saying so. The root script now clears the unit's start counter before the restart, and the wait ends on a failed unit, naming its result and the commands that start Docker again.
- The metadata firewall became an item of every server's: only `--project-users add` loaded the containers' chain before, where project users were, while a cloud server with none kept its containers able to read the instance's credentials. The door's loader serves both, so the two never disagree; the want is per server, on or off, never an address, and its first load is confirmed by `--server-setup`, which is why `setup.Item` gained `ConfirmFirst`. A trial on a Debian 13 machine with systemd showed the chain holding through a restart of Docker with no drop-in, loaded again at boot by its unit, and the timer, only linked, waiting for the next boot, so the install now starts it and a removal stops it.
- The firewall's first review round found two loads at once losing another tool's rule: the install started the timer, which fires at once on a host up past its `OnBootSec`, and then ran the loader itself, and each load deletes its jump's other copies by numbers read earlier, so the second delete took the rule that moved there (195 of 200 rounds on nf_tables), and on iptables-legacy one load failed on xtables' lock in every round. Every load and removal now holds one lock, every iptables call waits for xtables', and the install loads through the unit, the timer after it. The same round found the unit's result judging a load the unit did not run: after one failed run, the apply's own load went fine and its check said it did not hold until the timer's next run. The mark, cleared at every load's start and written at its end, became the judge, the result kept as words. It also found `--upgrade` overwriting a door's loader with the containers' alone once `door:` left the config; the decision was that `--upgrade` keeps the kind loaded, and a door's firewall loaded stays the door's for `--server-setup` too, `allow` refused there, since devopsy never takes a door's firewall off a server; a removal for `allow`, being a change of kind, became `--server-setup`'s alone as well, `--upgrade` saying so. `setup.Item.ConfirmFirst` gave way to the state's own rule, which says the same of every change of kind. Smaller: a loader that lost its exec bit read in sync and failed at every run (`hostPut` now sets a mode that alone differs, and the facts compare modes); the removal stopped the timer after taking the chain out, against its comment; the door's check took its groups' ids from the deploy user's lookup, now from the root read, as the loader takes them. A trial on Docker 29.9.3 showed Docker adding its own DROP per published container to raw's PREROUTING, after devopsy's jump, which its restart leaves first.
- The firewall's second review round found the lock open to any local user: made 0644 in `/run`, and flock locks a file opened for reading, so a project user could hold it and fail every load; it moved into a directory of root's, 0700. It found the mark cleared at each load's start making a load beside an apply's check (the timer's first run, which an install's start set off at once on a host up past its delay) read "to load again" with the rules in all along: the mark is now written by rename and removed only on a failure. It found round 1's mode fix reporting a mode alone as a new text, so `--project-users add` asked a reboot for an sshd drop-in whose mode alone changed: `put` now reports only a new text. It found a load waiting on the removal's lock loading again after it: the removal stops the unit, and a loader whose file is gone loads nothing. A trial on Docker 29.9.3 had shown Docker appending its own DROP per published container to raw's PREROUTING, after devopsy's jump.
- The firewall's timer was retired after the second review round, on every server, the door's included. Its one reason was a reload of a firewall manager, or an `iptables -F`, dropping devopsy's rules, which takes root on a server whose setup runs no firewall manager. It cost a second load set off beside every install (its first run, at once on a host up past its delay), a lock and a mark built to survive that, the facts reading its links and state, and the removal racing a loader it started. A wipe is now made visible instead of healed: `--server-info` reads the chains as root wherever devopsy's firewall is loaded and warns, and the next `--server-setup` loads it again. A timer an earlier install left is a retired piece, stopped and removed by its header.
- "No release warns for a tunable" gave way for the firewall alone, once its timer was retired: nothing else heals or shows a wipe, and a release is the moment an operator reads the output before putting something live. The read is bounded so it costs a release little (the mark first, the util image never built, a few seconds) and fails nothing.
- Until the firewall's third review round any refusal stopped the whole apply with "nothing changed". A review found W0001's one fix, `--server-setup`, loading nothing on a server whose `daemon.json` devopsy could not judge, the firewall being no part of it. The setup's items are independent settings, and the fix offered for one must not wait on another's, so a refusal now stops only the steps that need what it refuses; Docker, which every root run needs, still stops them all, and the run fails while anything was refused.
- The firewall's fourth review round found the dependency model filing every Docker refusal under one item: its unit's config file and its missing plugins stopped every step though only `daemon.json`'s parts, or none, need what they refuse; a release root a unit cannot hold stopped its making; a chains' read went through a Docker refused as another host's. Refusals now say what they stop (`Refusal.Stops`). It also found a restart not confirmed in time ending the apply before the firewall, unsaid; the drop-in's daemon-reload skipped when a restart was asked and the `daemon.json` put after it then failed, a regression of putting `daemon.json` last; a `daemon.json` devopsy cannot judge leaving no change to name, so the question named an empty list and `--upgrade` noted its version; a refused `allow` silencing a wiped door's firewall; and a refusal said by both sessions.
